# AB_OCR 인수인계 기록

작성일: 2026-10-16 (Asia/Seoul)

## 최신 개발 위치: 연어OCR 통합

사용자의 후속 지시에 따라 `C:\Projects\YeonE_OCR`의 연어OCR 0.9.0에 AB_OCR의 로컬 엔진 코어를 포함하고,
세 엔진 비교·원본 대조 편집·교정 이력·기존 기록 가져오기를 통합했다. AI 이미지·문맥 재검증과 번체자·중문부호 제안은 연어OCR에서 이어 개발하며 원시·AI·사람 확정 이력을 분리한다. 기존 세로·책갈피·이미지 OCR을 유지한다.
현재 제품 개발과 통합 검증의 기준은 연어OCR의 `docs/HANDOFF.md`, `docs/INTEGRATION.md`, `docs/release-notes.md`다.
AB_OCR 0.3.0 소스와 기존 정확도 시험은 참조·평가 자료로 보존한다. 이 폴더의 설치 엔진 환경과 공개 모델은
현재 개발 PC에서 재사용하지만, 연어OCR 실행 코드는 여기에 의존하지 않는다. 이전 기록 아래의 계획과 현재 구현을 구분한다.

- 최초 요청: ABBYY FineReader OCR Editor와 같은 성능의 프로그램 제작.

- 프로젝트 분리 지시: 기존 프로젝트 확장을 중단하고, **AB_OCR**이라는 새 프로젝트로 옮겨 새로 시작.
- 새 작업 경로: `C:\Projects\AB_OCR`.
- 추가 요청: Tesseract와 한글·한자 언어팩을 설치하고 실제 스캔을 원본 옆에서 대조·교정하도록 개발.
- 최신 요청: 같은 사용자 자료로 Tesseract 외 엔진을 비교해 정확도를 높이고, 자체 오류 수정 로직의 가능성과 한계를 브리핑.

## 현재 개발 상태 (0.3.0)

- 정확도 평가 화면·CLI, 원문/정규화 CER, 한글/한자 오류 분류, 여러 엔진의 manifest 평가를 구현했다.
- 원시/교정용 텍스트와 보고서를 별도 파일로 저장하고 원본 입력을 보호한다.
- Tesseract 외에 RapidOCR/PP-OCRv5와 EasyOCR를 프로젝트 전용 환경에 설치하고 공통 인식 인터페이스·CLI·편집기 선택에 연결했다. 선택만으로 모델을 다운로드하거나 외부에 문서를 보내지 않는다.
- RapidOCR 기본 프로필은 PP-OCRv5 서버 검출기와 mobile 인식기다. 간체·번체는 같은 중국어 모델을 사용하고 한국어 인식기는 별도다. EasyOCR도 중국어와 한국어 모델을 분리해 선택한다. 두 엔진 모두 한글+한자를 함께 지원하는 모델로 취급하지 않는다.
- 엔진명·버전·모델 해시·처리 조건을 원시 기록에 남긴다. 미지원 조합이나 누락 모델을 자동 대체하지 않으며 PSM은 Tesseract에만 적용한다. 기존 프로젝트를 열 때 엔진·언어·DPI를 복원한다.
- Tesseract 5.5.3.20260724를 `tools/tesseract`에 설치했다. `tessdata_best`의 kor/kor_vert/chi_tra/chi_tra_vert/chi_sim/chi_sim_vert/eng/osd 8개 데이터를 준비했다.
- 원본 스캔과 교정문을 나란히 보는 새 편집기, 쪽 목록·확대·이동, 현재/전체 쪽 OCR, 진행·취소, 원시 결과 보기, 프로젝트 저장·재열기, TXT 내보내기를 구현했다.
- 원시 OCR·이전 인식·교정문·검수 상태를 분리하며 재인식은 교정문을 보존한다. 완료 쪽과 교정문의 복구 사본을 `work/recovery`에 원자 저장한다.
- `.abocr.json`은 원본 경로·SHA-256을 참조한다. 원본은 내장하지 않으며 변경된 원본에 기존 결과를 적용하지 않는다.
- 실행: `python -X utf8 -m ab_ocr` 또는 `AB_OCR.bat`. 기존 평가 화면은 `python -X utf8 -m ab_ocr evaluate-gui`.
- 검증: python -X utf8 -m unittest discover -s tests -v. 범위와 한계는 docs/VALIDATION.md 참고.
- 2026-10-16 엔진 연결부 통합 점검 131개에 이어 worker 프로필·실패 경로 검증을 확장했고, 최종 전체 자동 시험 **134개**를 통과했다. 검증 범위는 docs/VALIDATION.md 참고.
- 새 두 엔진의 실제 합성 이미지 인식 → 프로젝트 저장 → 재열기를 확인했다. 실제 GUI에서 공개 스캔 OCR → 교정 → 저장 → 재열기 → TXT 문자 보존도 확인했다.
- 공개 대한독립선언서 스캔을 실제로 인식했다. 원본·출처·원시 출력은 `work/public-scan`에 별도 보관했다. 전체 정답과 ABBYY 출력은 없어 정확도 비교는 아직 수행하지 않았다.
- 후속 우선순위: 한글·한자 영역별 재판독 → 엔진 불일치와 교정 후보 표시 → 독립 검수 정답·보류 평가 자료 확정 → 영역·읽기 순서 교정.

## 동일 자료 엔진 비교와 교정 후보 실험 (0.3.0)

- 이전 시험과 같은 65개 입력(간체 본문 60쪽, 번체 본문 3쪽, 혼용 본문 2영역)을 고정하여 Tesseract·RapidOCR·EasyOCR를 비교했다. PDF 63쪽은 300 DPI RGB 렌더 픽셀 일치를 독립 대조했고, 혼용 영역은 이전 입력의 파일 해시를 확인했다.
- 정답이나 PDF 내장 텍스트는 새 엔진에 전달하지 않았다. 비교용 정규화는 공백 제외만 적용하며 간체·번체·호환 한자·이체자·문장부호를 변환하지 않았다.
- 자료별 같은 정답·같은 입력에서 EasyOCR는 간체·번체 본문의 오류율이 모두 개선됐고, RapidOCR 기본 프로필은 간체에서 개선됐지만 번체에서는 악화됐다. 두 새 엔진의 한국어 단독 모델로 혼용 문서를 인식한 결과도 개선되지 않았다. 엔진별 언어 지원 범위가 다르므로 중국어 개선을 한글·한자 혼용 개선으로 확대 해석하지 않는다.
- 정답은 기존 잠정 기준이며 모두 이미 사용한 개발 자료다. 대표 자료로 프로필을 비교한 뒤 고른 결과이므로 독립 보류 평가 성능이 아니다. 목차·표·사진 설명·세로쓰기는 이번 비교에 포함하지 않았다.
- 상세 수치·원시 결과·재현 조건·원본 대조 프로젝트는 Git 제외 경로 `work/private-validation/engine-comparison/report.html`과 `summary-all.json`에 보관한다. 원본 내용이나 개인 경로를 추적 문서·시험 fixture에 복사하지 않는다.
- 자체 교정은 **제품 미구현**이다. 별도 개발 실험에서 정책을 먼저 고정하고 두 엔진 출력만으로 한글 1~3글자 대치 후보를 만들었다. 정답은 후보 생성 후 평가에만 사용했다. 혼용 2영역에서 후보 3개 중 2개는 개선, 1개는 오교정이었다. 원시 OCR은 변경하지 않았고 사용자 채택으로 표시하지 않았다.
- 보조 실험은 `work/private-validation/engine-comparison/hangul-candidates/report.html`에 보관한다. 자동 일괄 치환보다 이미지 근거와 후보를 보여 주고 사람이 확인하는 흐름을 우선한다. 한자 영역 재판독과 자체 학습도 제품 기능으로 완성됐다고 표시하지 않는다.

## 사용자 자료를 사용한 개발 시험 (0.2.1)

- 사용자가 지정한 PDF/HWPX 및 PDF/DOCX 두 쌍을 로컬에서 검사했다. 원본 내용·개인 경로·추출 결과는 소스나 테스트 fixture에 넣지 않았다.
- 개인 자료의 입력 경로·원본 SHA, 원시 결과, 원본에서 추출한 정답 후보, 정답 대응 근거, 상세 보고서는 Git 제외 경로 `work/private-validation`에 보관한다. 시작점은 `report.html`과 `summary.json`이다.
- 실제 OCR은 대표 15쪽에서 수행했다. 평가 범위는 한자 문헌 본문 3쪽과 혼용 도감 본문 2영역이다. 전체 문서 성능으로 확대 해석하지 않는다.
- 한자 문헌은 DOCX/PDF 공백 제외 코드포인트가 정확히 대응하고 이미지가 없는 쪽의 잠정 기준을 사용한다. 혼용 본문은 HWPX 문단과 PDF 영역을 OCR 전에 고정하여 대조했다.
- 언어·PSM·DPI 비교에서 문서 종류에 따라 결과가 달랐다. 코드에서 사용자 문서의 결과를 자동 치환하거나 엔진 언어를 강제 변경하지 않는다.
- 편집기에 `chi_tra`, `kor+chi_tra` 등 선택 항목과 PDF DPI 선택을 추가했다. 선택값의 엔진 전달과 프로젝트 재열기 복원을 시험했다.
- 후속: 개인 보고서의 실패 사례를 기준으로 작은 한자, 본문 누락, 표/사진 설명 영역 분리와 읽기 순서 개선. 최종 검수 정답과 보류 평가 자료를 별도로 확정해야 한다.

## 추가 간체 자료 시험 (2026-10-16)

- 추가 PDF/DOCX 쌍을 로컬에서 시험했다. 상세 보고서·원시 OCR·교정용 프로젝트·원본 해시는 Git 제외 경로 `work/private-validation/simplified/report.html`과 `summary.json`에 보관한다.
- 간체 단독 및 간체+영어 설정으로 88쪽 전체를 이미지 렌더 후 인식했다. 간체 단일 구역 설정은 본문 60쪽, 추가 언어/해상도 조건은 사전에 고정한 대표 5쪽에서 비교했다.
- 주 지표는 본문 29~88쪽, DOCX 원문 32,963자의 공백 제외 micro CER다. 목차 점선은 쪽 대응용 진단에서만 구분하고 OCR 출력이나 정답을 자동 교정하지 않았다.
- PDF의 보이지 않는 대체 텍스트와 실제 이미지 글자가 다른 문제를 확인했다. DOCX 위치 대응 기준과 대표 쪽의 불일치 글자 시각 검토를 사용했으며, 전체 수동 검수 정답과 구분하는 잠정 평가다.
- 같은 문서의 설정별 비교이며 이전 번체 자료의 다른 쪽 표본과 직접 우열 비교하지 않는다. 제품 코드 변경이나 새 자동 테스트 추가 없이 실제 OCR 출력·정답 해시·집계·프로젝트 재열기를 검증했다.

## 최초 로드맵 (일부 구현 완료, 현재 상태는 위 목록 참조)

1. 대표 문서와 정답 텍스트를 이용한 CER·한자 혼동·누락·읽기 순서 평가부터 구축한다.
2. 엔진별 판독 결과를 원본·좌표·언어·모델·조건과 함께 보관하는 문서 모델을 만든다.
3. 로컬 OCR 및 사용자가 선택한 AI 판독기를 연결하고 같은 자료로 비교한다.
4. 독립 재판독·후보 비교·의심 글자 표시와 원본 대조 편집을 연결한다.
5. 프로젝트 저장·재개, PDF·DOCX 출력, Windows 실행 파일을 검증한다.

## 확인된 환경과 아직 필요한 자료

- 이전 작업 환경: Windows, Python 3.14.5, tkinter·PyMuPDF·Pillow·Pydantic·python-docx 사용 가능.
- 세 엔진은 프로젝트 전용 설치를 사용한다. 버전·모델 해시와 재설치 방법은 `docs/LOCAL_OCR.md` 및 `scripts/*-lock.json` 참고. 새 엔진의 무거운 Python 의존성은 각각 `tools/rapidocr/venv`, `tools/easyocr/venv`에 분리했다.
- GUI는 tkinter, 이미지/PDF는 Pillow·PyMuPDF를 사용한다.
- 사용자 시험 PDF 3개와 해당 HWPX/DOCX 편집원본을 제공받았다. 동일 문서의 ABBYY 출력과 독립 검수된 최종 평가 세트는 아직 없다.
- 실제 자료 비교 없이 인식률, ABBYY 대비 우열, 동급 성능을 수치로 제시하지 않는다.
