- AI가 지원되지 않는 기타 문단 스타일 연결을 제안하거나 규칙 버전을 빠뜨리면 경고를 남기고 분석을 계속합니다. 검증할 수 없는 응답은 해당 쪽을 한 번 더 요청합니다.

# 연어OCR 1.2.51 · 원본 목차 배치와 문자 PDF 호환성

- 총목 항목의 쪽번호를 오른쪽에 맞추고 점선으로 연결합니다. 상세 목차는 PDF와 OCR 좌표를 비교해 같은 줄의 항목을 열별로 배치합니다.
- **이 책 설정 → 구조 분석**이 목차·색인·본문·문헌 목록·각주 쪽을 책별 규칙에 기억합니다. HWPX를 만들 때 원본 배열을 확인하고, 미리보기에서 여러 유형의 대표 쪽을 확인할 수 있습니다.
- 문자 PDF의 내장 글꼴 형식을 바로잡았습니다. 먼저 임시 파일을 열어 글꼴·쪽 수·추출문을 확인한 뒤 저장합니다.
- HWPX와 문자 PDF를 함께 만들면 두 파일에 같은 기본 이름과 시각을 붙입니다.

# 연어OCR 1.2.50 · PDF에서 양식 HWPX 만들기와 재판독 확정

- 책을 고른 뒤 **이 책 설정**에서 참고 OCR, 양식 HWPX, 책별 규칙을 지정합니다. 양식을 고르면 내용별 편집 문서로 전환되며, 대표 쪽을 실제 HWPX로 미리 만들어 스타일을 확인할 수 있습니다.
- **HWPX 만들기**에서 새 책을 판독하거나 저장된 판독에 현재 양식을 적용합니다. 문자 PDF와 다른 작업 폴더의 OCR은 **내보내기**에서 사용할 수 있습니다.
- 재판독 결과를 원본 이미지와 대조해 변경을 채택하거나 기존 교정을 유지할 수 있습니다. 확정하면 별도 작업 폴더에 새 HWPX와 선택 내역을 저장합니다.
- **현재 결과**에서 기본 작업·재판독본·확정본을 전환합니다. HWPX 열기와 대조·편집은 선택한 문서를 따르며 책을 다시 열어도 선택이 유지됩니다.
- 양식에서 직접 지정한 개요·번호 스타일을 출력 검사에서 인정합니다. 새 쪽번호 꼬리말에 제목 번호가 따라붙던 문제도 고쳤습니다.

# 연어OCR 1.2.49 · 기존 OCR 재판독과 통합 책 설정

- 기존 OCR 재검수·재판독에서 의심 부분 우선 또는 전체 재판독을 선택합니다. 의심 모드는 확인 항목·낮은 신뢰도·미완료 기록이 있는 쪽 전체를 다시 읽습니다.
- 원본 작업과 교정 이력은 보존하고 별도 폴더에서 새로 판독합니다. 보존 사본·파일 해시·이전/새 판독 비교 보고서·새 문서를 저장하며 기존 결과에 자동 병합하지 않습니다.
- 이 책 설정과 설정 → 이 책의 자료·규칙 값을 공유하고 서로 이동하도록 연결했습니다. 참고 OCR·양식 HWPX·규칙·재판독을 한곳에서 관리합니다.
- 책별 규칙 자동 생성에 참고 OCR HWPX의 대응 본문을 함께 사용합니다. 대응하지 못한 쪽은 표시하며 자료 변경 시 이전 분석 적용을 차단합니다.
- AI 사용량·비용은 현재 설정에 따릅니다. 검증은 모의 판독과 실행본 검사로 수행했으며 실제 인식률 개선을 보장하지 않습니다.

# 연어OCR 1.2.48 · 책 전체 분석으로 책별 규칙 자동 생성

- 책별 규칙 만들기에서 연결된 구독 AI가 책 전체를 처음부터 끝까지 분석합니다. 쪽 범위를 비우면 전체 분석, 지정하면 부분 시험을 실행합니다.
- 전체 쪽 이미지와 확대 이미지로 목차·본문·각주·문헌 목록·색인 등 유형을 찾고 모든 쪽의 규칙 후보를 통합합니다. 충돌·미확정·미지원 항목은 검토 목록과 분석 보고서에 남깁니다.
- 완료 쪽을 저장해 중지·실패 후 재사용합니다. 원본·양식·해당 OCR이 달라지면 관련 분석을 다시 수행합니다. 결과를 확인한 뒤 새 규칙으로 저장·적용하며 기존 규칙과 OCR 기록은 보존합니다.
- 쪽별 AI 요청으로 구독 사용량과 시간이 필요합니다. 유료 API로 자동 전환하지 않습니다. 전체 분석이 모든 규칙의 정확성을 보장하지 않으며 각주 연결 자동 복원 등 미지원 기능은 확인 항목으로 표시합니다.
- 현재 개발 소스에 반영된 목록 정렬·색인 배치 보완도 포함합니다.

검증은 모의 AI 응답 기반의 전체 쪽 순회·희귀 유형 보존·중지·이어하기·규칙 검사 및 실행본 자체 검사로 수행합니다. 실제 계정별 AI 응답 품질은 별도 확인이 필요합니다.

# 연어OCR 1.2.43 · 본초명 스타일과 목차 자동 탭

- 목차·차례·색인은 단의 오른쪽 끝 자동 탭을 사용합니다. 점선이 기본이며 원본 여백이 비어 있는 항목은 채움선 없이 맞춥니다. 두 단의 항목이 한 OCR 줄에 합쳐진 경우 원본 대응이 확인되면 분리합니다.
- PDF 좌우 여백에 인쇄된 반복 제목을 위치 근거로 제외합니다. 서로 어긋난 로컬 판독 때문에 글줄 전체에 붙던 형광펜을 줄이고, 구독 AI의 쪽 판독 형식 오류는 한 번 다시 요청합니다.
- 백출·창출을 뜻하는 術/术에는 朮을 적용하고 의술·기술을 뜻하는 문맥에는 術을 사용합니다.
- 구독 자동 배분은 Antigravity·ChatGPT·Claude 순으로 비중을 높게 둡니다. 세 계정에 모두 여유가 있으면 3:2:1로 배정하고 각 쪽의 담당 계정을 진행 기록에 표시합니다.

# 연어OCR 1.2.40 · 긴 문서 저장 한계와 종료 진단

- SQLite 증분 프로젝트의 한도를 기존 전체 JSON의 1GB 합계 제한·256MB 파일 제한과 분리했습니다. 증분 저장은 파일 2GB·확장 데이터 합계 8GB·쪽별 확장 데이터 128MB까지 허용하며, 크기·해시·무결성 검사와 원자적 교체를 유지합니다. 구형 전체 JSON/gzip 제한은 유지합니다.
- 복구본을 쓰기 전에 오류 진단 JSON을 우선 저장합니다. 복구 실패도 진단 파일에 기록하여 같은 저장 한계로 복구가 실패할 때 원인이 사라지지 않게 합니다.
- Windows GUI의 실행 버전·시작·진행 내용·GUI 종료를 세션 로그에 기록하고 네이티브 오류 추적을 활성화합니다. 환경의 API 키와 알려진 인증 형식은 가립니다.
- OCR 실행·재개의 SQLite 프로젝트를 쪽별로 불러옵니다. 최초에는 한 쪽씩 검증하고, 정상 체크포인트 저장 후 저장된 쪽 객체를 메모리에서 해제합니다. 미저장 쪽은 보존합니다. 저장본의 동시 변경과 해시 오류는 거부합니다.
- 시스템 커밋 여유 1GB 미만 또는 물리 메모리 여유 256MB 미만이면 새 쪽 OCR·다음 구간 검증을 시작하지 않고 안전 중지합니다. 진행 중인 요청은 즉시 강제 종료하지 않습니다.
- 기존 프로젝트 형식과 교정 이력을 유지합니다. 1GB를 넘은 증분 프로젝트는 이번 버전 이상으로 열어야 합니다. 명시적인 전체 내보내기나 비교 편집 창 등 다른 전체 로딩 경로까지 모두 변경한 것은 아닙니다.
- 실제 중단 자료는 확장 데이터 996,500,486바이트로 기존 1GB 한계에 근접했으며 무결성 검사는 통과했습니다. 저장 오류 가능성은 높지만 앱 창이 닫힌 직접 원인은 이전 실행 로그 부재로 확정하지 못했습니다.

# 연어OCR 1.2.39 · 바로 이어가기 선택 유지

- HWPX 시작창이 실행 카드에서 선택한 바로 이어가기를 끝나지 않은 쪽만 점검으로 덮어쓰던 오류를 수정했습니다. 중복 시작창을 제거하고 실행 카드의 선택을 그대로 실행 명령에 전달합니다.
- 바로 이어가기는 앞선 기록과 보류 검증을 그대로 두고 기록 없는 쪽을 처리합니다. 끝나지 않은 쪽만 점검과 모두 다시 점검은 실행 카드에서 명시적으로 고릅니다.
- 바로 이어가기에서 이전 기록 상태를 재확인한다고 잘못 안내하는 메시지를 제거했습니다. 기존 OCR·교정·AI 응답은 삭제하지 않습니다.
- GUI에서 바로 이어가기 선택 후 실제 HWPX 실행 명령을 생성하고 CLI로 해석했을 때 continue가 유지되는 통합 테스트를 추가했습니다.

# 연어OCR 1.2.38 · 재개 분류와 진행 표시 수정

- 같은 조건에서 자동 검증이 끝나고 사람 판단만 남은 쪽은 재개 시 자동 검증을 반복하지 않습니다. 검수 경고와 기존 기록은 유지합니다. 실패·중지·남은 묶음·엔진 오류는 계속 재개 대상입니다.
- 쪽 전체 검증 상태를 개별 AI 제안 응답의 상태로 덮어쓰던 오류를 수정했습니다. 이전 버전의 해당 기록은 저장 응답을 재사용해 상태를 다시 확인합니다. 해당 응답이 없거나 조건이 달라졌으면 새 요청이 필요할 수 있습니다.
- 바로 이어가기는 앞선 기록을 그대로 두고 새 쪽을 처리하며, 모두 다시 점검은 기존 쪽도 명시적으로 재점검합니다. 사람 검수 대기와 보류 경고를 건너뛴 뒤에도 유지합니다.
- 진행 숫자를 작업 처리 기준으로 표시하고 저장 기록 확인·새 쪽 OCR·기존 쪽 OCR 보완·AI 판독 및 미완료 검증을 구분합니다. 쪽 칸의 설명에도 같은 활동을 표시합니다.
- 저장본 확인 중에 처음부터 읽는다는 안내를 제거했습니다. 새 쪽 AI 요청도 호출 집계에 포함하고 캐시 재사용은 새 호출로 세지 않습니다.
- 실행 중인 구버전에는 소급 적용되지 않습니다. 정상 중지 또는 완료 후 업데이트하고 원하는 재개 옵션을 선택하십시오.

# 연어OCR 1.2.37 · 긴 문서의 구독 검증 호출 상한 수정

- 구독 구간 검증의 기본 1,000회 고정 상한을 제거했습니다. 기본값 0은 프로그램 자체 상한 없음이며, 구독 서비스 한도는 그대로 적용됩니다.
- `--local-ai-subscription-calls N`의 양수 상한과 유료 API 호출 제한을 유지합니다. 음수는 실행 전에 거부합니다.
- 상한 보류 사유에 구간 검증 상한·완료·진행 예약 수와 쪽 판독 별도 집계를 표시합니다. 다음 묶음 대기를 상한 도달로 잘못 기록하지 않습니다.
- 완료한 검증은 재사용하며 기존 OCR·교정 기록을 보존합니다. 실행 중인 이전 버전에는 소급 적용되지 않습니다.

# 연어OCR 1.2.36 · 본초 제목 복원과 영문 오인식 검수

- 양식에 등록된 본초명이 첫 출전 앞에 붙은 경우 독립된 제목으로 분리하고 본문의 검수 표시 위치를 보존합니다.

- 실제 문서의 감수 제목과 영문으로 손상된 6개 행을 원본 대조하고, 수정 HWPX의 한글 열기·저장·재열기 및 화면 배치를 확인했습니다. 이 검증이 다른 쪽의 판독 정확성을 보증하지는 않습니다.

# 연어OCR 1.2.35 · 저장소 손상 진단과 안전 중지

- SQLite 증분 프로젝트를 직접 갱신하는 대신 일관된 임시 스냅샷을 만들고, 변경된 쪽만 직렬화한 뒤 닫기·동기화·재열기·무결성 검사를 거쳐 원자적으로 교체합니다. 교체 전에 실패하면 기존 프로젝트를 보존합니다.
- 저장소 오류는 OCR 엔진 실패와 구분합니다. SQLite 오류 코드와 파일 헤더 대비 부족한 바이트 수를 진단하고, 새 쪽 판독·AI 요청을 중지합니다.
- 저장 실패 당시 메모리에 남은 OCR·교정·AI 기록은 작업자료/storage-diagnostics에 별도 복구본으로 저장합니다. 작업 드라이브에 쓸 수 없으면 사용자 로컬 앱 데이터의 YeonE_OCR/recovery로 재시도합니다. 복구 저장 실패가 원래 오류를 가리지 않습니다.
- 병렬 AI 검증 도중 체크포인트가 실패하면 새 요청을 보내지 않고 이미 진행 중인 응답을 메모리에 보존한 뒤 오류를 전달합니다. 유료 API 전환이나 자동 재호출은 추가하지 않습니다.
- 실제 손상 사례에서 파일 끝이 헤더 선언 크기보다 짧은 것을 확인했습니다. 파일을 자른 외부 주체까지 확인된 것은 아니며, 이번 수정이 모든 디스크·시스템 장애를 예방한다고 보증하지 않습니다.

# 연어OCR 1.2.34 · 시작 위치 선택·문맥별 한자·제목과 부호 편집

- 기존 로컬 판독 기록이 있으면 ‘한 번에 인식 (HWPX 만들기)’ 실행 전에 ‘중단 지점부터 이어서’와 ‘처음부터 전체 점검’을 고릅니다. 처음부터 점검해도 완료 OCR·AI 응답은 재사용하며, 두 선택 모두 강제 재판독을 끄고 기존 교정·검증을 보존합니다. 취소하면 실행하지 않습니다.
- 문맥 판별 규칙을 별도 분류로 모읍니다. 松/鬆·干/乾/幹·着/著의 뜻을 구분하고 확실하지 않으면 기존 문맥 판별·검수로 보냅니다. 특정 긴 구절 하나만 치환하는 방식은 사용하지 않습니다.
- `此藥質极黏膩→此藥質極黏膩`, `土旺則能胜溼→土旺則能勝濕`을 판별 예시로 보존합니다. 溼→濕은 편집 가능한 자동 자형 통일 규칙입니다.
- 약재명 干姜·干薑→乾薑과 사용자 지정 髒→臟 일괄 치환을 기본값에 포함합니다.
- 책별 于/於 표기 기준을 추가합니다. 기본 고전은 일반 문장의 于→於, 1900년 이후 출판물·현대 중국 백화문은 于를 보존합니다.
- 문장부호의 빨간 검수 표시도 기본적으로 제외합니다. 한자 검수 색상·부호 불일치의 원시 기록은 유지합니다.
- 본문 중간 생략은 ` … `로 통일하고 목차의 쪽번호 연결 점선은 보존합니다.
- 동규자처럼 한 글자씩 띄어 읽은 고밀도 한자 OCR 문단의 실제 공백을 정리합니다. 제목·출전의 한자 내부 공백도 제거하며 쉼표 뒤 공백, 한국어·영문 띄어쓰기와 한자 검수 범위는 보존합니다.
- 본문에 붙은 번호·제목·출전은 참고 HWPX의 제목/목차 근거가 있는 경우 분리합니다. 번호의 ○/〇/0과 공백 차이는 대응에만 사용하며 출력 글자는 보존합니다.

# 연어OCR 1.2.32 (내부 검증) · 완료 AI 대응 근거를 우선하는 검수 표시

- 완료된 쪽 AI 판독과 현재 출력의 확실한 대응 구간은 다른 로컬 엔진의 불일치만으로 다시 노랗게 표시하지 않습니다. 대응이 확인된 기존 빨간 범위는 배경 없는 파란 글자로 구분하고 기존 초록·파랑 표시는 유지합니다.
- 과거 기록은 저장된 AI 응답으로 당시 반영 결과·검증 요약이 정확히 재현되는 경우에만 재사용합니다. 새 외부 호출은 하지 않으며 여러 응답이 서로 다르게 대응하면 적용하지 않습니다.
- AI 직접 의심, 명시적 구간 AI 제안, 사람의 교정·판정, 대응 불명 장문은 보호합니다. 이 정책은 전체 글자 정확도를 보증하거나 긴 AI 문장을 통째로 강제 채택하는 기능이 아닙니다.
- 아래 내부 검증본의 부호·공백 표시, 人蔘葉 제목 복원, 炮制→炮製 규칙도 포함합니다. 1.2.31은 내부 검증 후 이번 버전에 통합했습니다.

# 연어OCR 1.2.31 (내부 검증) · 부호·공백 검수 표시와 부속 본초 제목 복원

- 쉼표·세미콜론 등 의심 문장부호는 빨간 글자로만 표시하고 검수 배경색·추가 굵기·밑줄은 붙이지 않습니다. 공백에도 검수 배경색을 붙이지 않습니다. 한자 검수 색상과 메모 위치·내용은 유지합니다.
- 기존 엔진 후보가 쉼표 폭·공백만 다르게 읽었거나 혼합 구간의 같은 자리 쉼표에 동의하면 출력 사본에서 해당 쉼표의 검수 표시를 정리합니다. 실제 부호 차이·누락과 AI 제안이 겹친 자리는 보수적으로 유지합니다. 새 OCR의 같은 표시도 개선합니다.
- 원본 양식의 `人蔘(附：參須, 人蔘葉)` 같은 제목에서 부속 약재와 소속을 읽습니다. 같은 상위 약재 아래의 독립된 약재명 뒤에 첫 출전이 이어지는 경우 소분류 제목으로 복원하여 人蔘葉이 앞 인용문에 붙지 않게 합니다. 본문 단어와 소속 불명 항목은 제목으로 추정하지 않습니다.
- `炮制→炮製`를 기본 어구 규칙에 추가하며 한자 규칙 설정에서 수정·삭제할 수 있습니다.
- 기존 OCR·교정·AI 응답·판정·완료 이력과 한자 검수 강조는 보존합니다. 긴 강조 구간은 이번 변경으로 일괄 해제하지 않습니다. 출력 파일명은 `원본 PDF 이름 - YYMMDD_HHMMSS`를 유지합니다.

# 연어OCR 1.2.30 · 본문 경계와 원본 스타일 유지·출전 및 주석 편집

- HWPX 출력 파일명을 `원본 PDF 이름 - YYMMDD_HHMMSS`로 통일합니다. 같은 초의 충돌은 다음 빈 초로 구분하여 기존 파일을 보존합니다. 이전 파일명도 결과 열기에서 인식합니다.
- 반복 머리말을 원본 위치·간번체·문장부호 차이와 함께 확인하여 제외합니다. 여러 상자로 나뉜 머리말과 세 번째 상자의 쪽번호도 처리하고, 본문과 합쳐진 머리말은 확인된 접두부만 제외합니다.
- 참고 양식의 목차에만 있는 약재도 원본의 가운데 제목 위치·높이와 첫 출전 번호를 함께 확인하여 제목으로 복원합니다. 목차 단어만으로 본문을 제목으로 바꾸지 않습니다.
- 본문·인용문은 원본 HWPX 스타일의 줄 나눔·정렬·간격을 그대로 사용합니다. 스타일 이름과 실제 문단 서식이 달라 재지정 시 흐름이 바뀌던 문제를 수정하며 글꼴과 검수 색상은 유지합니다.
- `元素 曰 : 原文`을 `元素曰: 原文`으로 정리하고, 별도 출전 제목 줄 끝의 콜론은 제거합니다. 해당 출전의 `『綱目』`은 `『本草綱目』`으로 통일합니다.
- 본문에 붙은 `【注】`·`【註】`와 번호별 주석을 별도 문단으로 나누고 해당 글자의 검수 표시·메모를 보존합니다.
- 기본 한자 규칙에 `本草征要→本草徵要`, 이름·지명을 보존하는 `于→於`, 확실한 맛 표현만 바꾸는 `咸→鹹`을 추가합니다. 설정에서 편집·삭제할 수 있으며 불명확한 문맥은 검수 대상으로 남깁니다.
- 위 편집은 출력 사본에 적용하며 기존 원시 OCR·사람 교정·완료된 AI 검증 기록과 문자 PDF는 변경하지 않습니다.
- 손상된 목차는 같은 원본 이미지 해시의 완료 AI 캐시와 별도 로컬 판독에서 약재명·쪽번호 쌍이 양쪽 모두 80% 이상 일치할 때만 출력 사본을 복구합니다. 미일치 항목은 검수 색상을 유지하고 사람의 교정·판정이 있는 쪽은 자동 복구하지 않습니다. 목차의 괄호 쪽번호를 인식하여 항목끼리 이어 붙이지 않습니다.

# 연어OCR 1.2.29 · 원본 양식의 제목 계층과 편집하는 한자 변환 규칙

- 설정 → 자동 교정에 한자 변환 규칙 편집기를 추가합니다. 검색, 추가·수정·삭제, 순서 변경, JSON 저장·불러오기, 내장 규칙 복원과 MSR 가져오기를 지원합니다. 저장한 경로를 설정에 유지하고 CLI·실행 전 어림에도 같은 규칙을 전달합니다.
- MSR에 있던 `產→産`, `飲→飮`, `顏→顔` 등 누락된 한국 표준 자형 31쌍을 보완합니다. 편집형 HWPX의 `牛膝春夏用叶`는 `牛膝春夏用葉`로 변환합니다.

- 설정 → 이 책 → 양식 스타일에서 HWPX의 스타일을 책·권·장, 약재·절, 소분류 제목, 본문, 인용 출전·인용문에 연결하고 책별 JSON 규칙으로 저장·재사용합니다. 선택한 양식의 글꼴·크기·기본 색상은 그대로 쓰고 검수 색상만 덧입힙니다.
- 양식의 제목 스타일과 상위 약재를 함께 확인하여 소분류를 구분합니다. 같은 단어가 다른 약재의 본문에 등장했다는 이유로 제목으로 바꾸지 않습니다. 책·권·장만 새 쪽으로 시작하며 소분류는 이어 씁니다.

- 기본 HWPX·DOCX·문자 PDF 파일명은 `원본 PDF 이름 - YYMMDD`이며 같은 날 다시 저장하면 ` - v2`, ` - v3`를 붙여 이전 파일을 보존합니다. 사용자가 CLI 출력 이름을 직접 지정한 경우는 그 이름을 따릅니다.

- 구독 간 병렬 쪽 분배를 유지합니다. Gemini 한도 소진 시 잔여 한도가 확인된 다른 Gemini 모델로 먼저 전환하며, 가능한 모델이 없으면 다른 로그인 구독을 사용합니다. 유료 API 자동 전환·추가 AI 크레딧은 차단합니다.

# 연어OCR 1.2.20 · 오인식 장부의 활용·동시 저장·검증 범위 집계

- 2~4글자로 읽힌 오류도 검증 대상과 AI 참고 정보로 활용한다. 단어 경계에 걸친 문자열도 저장된 좌표로 연결하며 원문을 자동 치환하지 않는다.
- 장부 읽기·수정·원자적 저장 전체를 운영체제 파일 잠금으로 보호한다. 새 버전의 여러 실행이 동시에 저장해도 서로의 문서 기여를 덮어쓰지 않으며, 비정상 종료 시 잠금이 해제된다.
- 분모는 실제 검증한 기준 판독의 범위로 제한한다. 수동 교정 범위·사람의 전체 쪽 검수·현재 기준 판독에 연결되는 확실한 이미지 검증만 포함하고, 중복 범위는 한 번만 센다.
- 구형 장부는 보존하고 최초 갱신 시 `.before-verified-spans.json` 백업을 남긴다. 확인되지 않은 구형 분모는 비율로 표시하지 않는다. 프로젝트를 다시 수집하면 같은 문서의 기여를 새 범위로 재계산한다.
- GUI에는 「검증구간 비율」로 표시한다. 이는 선택된 구간의 가중 참고 통계이며 책 전체 OCR 정확도가 아니다.
- 기존 OCR·교정·AI 이력 및 1.2.19의 미완료 검증 전용 기능을 유지한다.

# 연어OCR 1.2.19 · 위치 연결 보완·미완료 검증 전용 GUI

- 저장된 다른 엔진의 좌표와 고유 문구를 대조해 좌표가 없는 OCR 구간을 연결한다. 모호한 위치와 사람이 교정한 구간은 추측하지 않는다.
- 실행 카드와 설정의 「이어서 할 때」에서 「미완료 검증만 · 기존 결과 보존」을 선택할 수 있다. 기존 OCR·쪽 AI 판독·교정문·출력 문서를 보존하고 새 제안만 저장한다.
- 추가 검증 대상 때문에 동일한 완료 요청을 반복하지 않도록 재개 처리를 보완했다. 위치가 남은 쪽은 검증 완료로 표시하지 않는다.
- 설치 실행본 자체 검사에 GUI 선택→CLI 전달, 전용 모드 중단·재개와 중복 호출 방지, 기존 판독 보존 검사를 포함했다.
- 1.2.18의 증분 저장·사용량 집계 수정도 모두 포함한다.

# 연어OCR 1.2.18 · 증분 저장·사용량 집계·안내 수정

- 원본 64쪽 이상인 비교 프로젝트는 SQLite의 쪽별 압축 기록으로 저장한다. 반복 저장은 변경된 쪽만 갱신하고, 원시 판독·교정·AI 응답·채택/기각 이력과 이어하기 판정을 보존한다.
- 기존 JSON/gzip은 계속 읽는다. 최초 저장 시 전환하며, 전환 실패는 기존 파일을 보존한다. 전환 후 파일은 이 변경이 포함된 실행본에서 열어야 한다(기존 1.2.17은 새 저장 형식을 지원하지 않음).
- 정식 저장·복구 저장의 변경 추적을 분리하고, 저장 오류·강제 종료의 롤백, 다른 창의 변경 감지, 원본·하드링크 보호를 유지한다. 자세한 동작과 성능 측정 방법은 [로컬 우선 인식](LOCAL_FIRST.md#긴-책의-증분-저장)을 참고한다.
- AI 쪽 판독 사용량 누락을 수정하고, 실제 구독 자동 동작과 안내 문구를 맞췄다. 설치 관련 테스트는 PC의 구독 CLI 설치 여부에 의존하지 않도록 격리했다.
- 실행본 자체 검사에 기존 JSON/gzip 프로젝트 전환, 교정 이력 보존, SQLite 증분 저장, AI 응답 직후 중단·이어하기를 추가했다. 외부 AI 응답은 모의 처리하며 구독 자동 선택을 금지한다.

# 연어OCR 1.2.17 · 수백 쪽 책의 비교 프로젝트 저장

1.2.16을 고치는 판이다. 긴 책을 로컬 우선 인식으로 돌리면 300쪽 무렵부터 쪽마다 「프로젝트가 허용 크기를 넘습니다」로 실패하던 문제를 고쳤고, 전체 코드를 보안·폴백·불필요한 코드 기준으로 점검(독립 검토 세 갈래, Codex 전체 검토 1회와 수정 재확인 8회)해 찾은 것을 모두 고쳤다.

- **수백 쪽 책에서 "프로젝트가 허용 크기를 넘습니다"로 쪽마다 실패하던 문제 수정**: 로컬 우선 인식의 비교 프로젝트(`작업자료\comparison\local-first-*.yeone-compare.json`)는 엔진 판독 전부와 AI에 보낸 요청 전부(검증 묶음마다 그 쪽의 원문 대조 근거를 함께 보존)를 담아 한 쪽에 1 MB 가까이 된다. 462쪽 책이 300쪽쯤에서 파일 상한 256 MB에 닿았고, 그 뒤로는 저장할 때마다 실패해 남은 쪽이 모두 「실패」가 됐다.
  - 이제 32 MB를 넘는 프로젝트는 gzip으로 압축해 저장한다(같은 파일 이름 · 약 10분의 1 · 200 MB 기준 저장 1초 남짓). 압축을 푼 JSON의 상한은 1 GB(이 밀도로 약 1,100쪽), 파일 상한은 그대로 256 MB다. 압축을 풀 때도 1 GB에서 멈춰, 손상되거나 부풀린 파일이 메모리를 채우지 않는다.
  - 작은 프로젝트는 지금처럼 일반 JSON으로 저장하고, 예전 판이 만든 프로젝트도 그대로 연다. 압축된 큰 프로젝트는 1.2.16 이하에서 열리지 않는다(그 판에서는 이 크기의 프로젝트를 저장할 수 없었다).
  - 이미 실패한 쪽은 새 판에서 [한 번에 인식]을 다시 누르면(「끝나지 않은 쪽만 점검」) 이어서 처리된다. 마지막으로 저장된 프로젝트(256 MB 이하)는 그대로 열린다. 끝난 쪽의 판독 기록(`readings`)은 프로젝트와 따로 저장되어 있어 그대로 쓴다.
- **AB_OCR 0.3.0 보존 사본 삭제**: 통합 전 소스를 그대로 보관하던 `references/AB_OCR_0.3.0`(52개 파일)을 저장소·소스 ZIP·CI에서 뺐다. 실행에는 쓰이지 않았고, 그 안의 옛 GUI 시험 2개가 Windows CI에서 임시 파일 잠금(WinError 32)으로 실패해 배포를 막았다. 앱이 쓰는 엔진 코드(루트 `ab_ocr`)는 그대로다. 1.2.16 이하의 소스 ZIP과 Git 이력에는 남아 있다.

- **보안**: 문서·AI 응답·심어 둔 파일이 닿을 수 있는 길을 막았다.
  - 판독 모델이 정하는 영역 id에 경로·마크업 글자를 넣을 수 없게 하고(새 응답), 그림 조각 파일 이름은 정리한 id로 만들며, 검수 화면(review.html)은 id·좌표·열 번호·조각 경로를 모두 escape한다 — 스캔 쪽에 심은 지시로 결과 폴더 밖에 JPEG를 쓰거나 검수 화면에서 스크립트를 실행할 수 있었다.
  - Codex 구독으로 검증할 때 셸·명령·브라우저·앱·플러그인·이미지 도구를 끈다(읽기 전용이어도 셸로 디스크 전체를 읽을 수 있었다). 옛 Codex 판은 모르는 이름을 경고만 하고 그대로 동작한다.
  - Windows: 시작할 때 현재 폴더에서 실행 파일을 찾지 않게 하고(`NoDefaultCurrentDirectoryInExePath`), taskkill·powershell·cmd는 System32의 전체 경로로 실행한다 — 포터블을 내려받기 폴더에서 돌릴 때 같은 이름의 심어 둔 파일이 대신 실행될 수 있었다.
  - API 키(`*_API_KEY`)를 엔진 작업자·엔진 설치(pip)·npm/winget 설치·다른 회사 CLI의 환경에 넘기지 않는다.
  - 크기: 아주 큰 PDF 쪽은 1억 화소 안으로 줄여 렌더링하고(UserUnit·정수 화소 올림까지 확인), 사람이 고른 HWPX는 여는 모든 길(양식 선택 안내·양식 확인·문서 양식·책갈피 교정·한글 이동 위치·구조 검사)에서 풀었을 때의 크기를 먼저 본다(1 GB · 항목 하나 256 MB, `yeone_ocr/ziplimits.py`). DOCX·HWPX에 넣는 글의 XML 제어 문자는 빼서 문서 전체가 실패하지 않게 했다. 시작 로그는 Gemini `AQ.` 키와 시작 뒤에 정한 키도 가린다.
- **폴백(조용히 나빠지던 자리)**:
  - 엔진 일부가 실패하면 진행 기록과 쪽 기록에 남기고, 그 때문에 판독이 하나만 남은 쪽은 「AI 검증 필요 없음」이 아니라 「사람 확인 필요」로 둔다(이어 하기에서도 다시 판정).

  - [중지]를 누르면 실패한 요청을 다른 구독이나 유료 API로 다시 보내지 않는다(재시도 대기·한도·로그인 실패·연결 전환·클라이언트 시작 실패 어느 경우든).
  - AI 쪽 판독: 응답 모양이 틀리면 엔진 판독으로 돌아가고(쪽 전체 실패 대신), 저장본(캐시)을 쓰지 못해도 이미 받은 판독은 쓴다.
- **불필요한 코드 정리**: 아무도 쓰지 않는 `ab_ocr/benchmark.py`, 함수·메서드 18개, import 24개를 지웠다(문자열 호출·라이브러리 콜백·시험의 바꿔치기 대상은 하나씩 확인하고 남김).

# 연어OCR 1.2.16 · 엔진 혼동 장부와 글자 이미지 조각

1.2.15를 갱신하는 판이다. 로컬 엔진이 자주 틀리는 글자를 스스로 기억해 다음 검증에 보태고, 나중에 엔진을 추가 학습시킬 자료를 모은다. 어느 기능도 글자를 대신 바꾸지 않는다(지침 21).

- **엔진 혼동 장부**: 로컬 엔진이 읽은 글과 사람·AI가 확정한 글이 다른 자리를 엔진별로, 모든 책에 걸쳐 모은다(`%LOCALAPPDATA%\YeonE_OCR\confusions.json` — 결과 폴더마다 두는 보고용 `confusion.json`과 다른 파일).
  - 쌓이는 때: 비교·교정 창의 [저장]·닫으며 저장, 로컬 우선 인식이 끝날 때. 같은 문서를 다시 거두면 그 문서 몫을 바꿔 넣는다(두 번 세지 않음). 아무도 확인하지 않은 쪽은 넣지 않는다.
  - 가중치: 사람이 직접 고친 글 1 · 사람이 고른 엔진 후보·AI 제안 또는 사람이 검수 완료한 쪽의 기계 제안 0.7 · 사람 확인 없이 자동 반영된 제안 0.3(AI 오답의 자기 강화를 줄이려고). 간체·번체, 전각·반각, 부호끼리의 교정은 세지 않는다.
  - 의심 글자(가중 오류 2 이상이고 그 엔진이 읽은 횟수의 5% 이상 틀림)가 든 낱말은 엔진 신뢰도가 높아도 AI 검증에 보낸다(`learned-confusable`, 쪽마다 최대 20곳). AI에는 과거에 확정된 글자를 "이 쪽의 근거가 아닌 참고 자료"로 함께 보낸다. AI 제안은 기존 안전 검사와 채택 절차를 그대로 거친다.
  - 장부가 비었거나 꺼져 있으면 검증 계획은 이전 판과 똑같다.
  - 채택 기록에 채택한 주체(`actor`: 사람 클릭 human · 실행 옵션 auto)를 남긴다. 표시가 없는 예전 채택은 자동 반영으로 센다.
- **글자 이미지 조각**: 엔진이 준 낱말·줄 상자를 그대로 잘라(글자 위치는 추측하지 않음) 확정 글과 함께 `%LOCALAPPDATA%\YeonE_OCR\glyph_samples`에 모은다 — 고친 줄과, 사람이 검수한 쪽에서 맞게 읽은 줄(쪽마다 4개). 편집 규칙에서 온 교정·줄 경계에 글이 끼어든 자리·쪽 전체 상자·원본이 바뀐 문서는 넣지 않는다. 비교·교정 창의 [저장]과 로컬 우선 인식이 끝날 때 새 조각이 있는 쪽만 렌더링하고, 되돌린 교정의 조각은 지운다. 원본 문서의 일부이므로 이 PC에만 둔다.
  - 내보내기: PaddleOCR 인식 학습 형식(`images/` · `rec_gt.txt` · `samples.jsonl`), 등급·엔진·종류로 거르고 세로 줄은 선택적으로 90° 돌린다. 기본은 사람이 고쳤거나 고르거나 검수한 것만.
- **관리**: [더 보기] → **[엔진 혼동 장부…]** 창에서 표 보기 · 잘못 쌓인 쌍 제외(다시 쌓이지 않음) · 검증 경로 사용 끄기 · 장부 비우기 · 조각 모으기 켜고 끄기 · 조각 내보내기·지우기. 명령줄 `confusions` · `glyph-samples`, 한 번의 실행에서 장부를 끄는 `--no-local-learned-confusions`.

**검증**: Linux(화면 시험은 Xvfb · Tk 8.6 · Python 3.12)에서 `tests/` 전체 2,536개 통과 · 29개 건너뜀 · 실패 31개. 실패 31개는 모두 이 변경 전 소스(1.2.14)에서도 같은 환경에서 똑같이 실패하는 화면 배치·글꼴 측정·16비트 그림 시험이다. 새 시험: `tests/test_confusion_memory.py`(22개) · `tests/test_glyph_samples.py`(15개) · 로컬 우선 인식 통합 3개 · [엔진 혼동 장부…] 창 1개. 같은 기능 커밋의 Windows CI(`tests.yml`)도 통과했다. 장부를 켰을 때와 껐을 때 실제 문서의 글자 오류율·AI 호출 수 비교와, 모은 조각으로 엔진을 추가 학습시킨 결과는 아직 없다. Windows 설치본 확인은 배포 CI와 [Windows 배포 안내](windows-release.md)의 목록을 따른다.

# 연어OCR 1.2.15 · Antigravity(Gemini) 구독을 실제 계정에서 확인한 방식으로

1.2.14를 갱신하는 판이다. 1.2.14에서 Gemini 구독을 Antigravity CLI(`agy`)로 옮겼지만 실제 계정으로는 확인하지 못했다. Windows · agy 1.5.9 · Google AI Pro 계정에서 직접 실행해 본 결과대로 연결을 다시 만들었다.

- **Auto 모드로 돌던 문제**: agy는 저장된 모드가 없으면 **Auto 모드**(파일 수정·명령 실행을 묻지 않고 함)로 시작한다. 1.2.14는 모드를 정하지 않아 요청마다 Auto 모드로 돌았다. 이제 이번 실행에만 쓰고 저장하지 않는 설정(`--settings`)으로 **Default 모드**를 쓴다 — 파일 수정·명령은 승인이 필요해 거절되고, 자기 임시 폴더 안만 읽는다. 사용자의 agy 설정은 바꾸지 않는다. (`--mode`에는 Default가 없다: `default`를 주면 경고만 내고 Auto로 돈다.)
- **창의 Gemini 모델 이름 때문에 Gemini 구독이 빠지던 문제**: 설정의 Gemini 모델(`gemini-3.1-pro-preview` 등)은 API 키용 이름인데, 1.2.14는 이것을 agy에 그대로 넘겼고 agy는 모르는 모델이라 실행에 실패해 그 실행에서 Gemini 구독을 뺐다. 이제 넘기지 않고 agy가 계정에 맞춰 고른다(Google AI Pro는 지금 Gemini 4 Argon). `YEONE_OCR_AGY_MODEL`로 고른 모델이 그 계정에 없으면 agy의 기본 선택으로 다시 보낸다. API 키로 검증할 때의 모델 설정은 그대로다.
- **로그인 상태를 실제로 확인**: 1.2.14는 agy가 설치만 되어 있으면 「사용 가능」으로 보였다. 이제 `agy -p /quota`(agy가 직접 답함 · 모델을 부르지 않고 사용량도 쓰지 않음)로 로그인을 확인한다. 로그인이 안 되어 있으면 「로그인 필요」와 방법을 보인다.
- **요청 방식**: `agy -p … --output-format json --json-schema …`. 그림은 지시문의 `@image1.png`로 첨부된다(실측: 도구를 쓰지 않고 한 번에 답함 — 1.2.14는 에이전트가 파일 보기 도구로 그림을 열게 했다). 답은 스키마에 맞춘 `structured_output`을 쓴다. 지시문이 길면 파일로 넘긴다.
- **이름**: 화면과 진행 기록에서 이 구독을 **Antigravity**로 보인다 — 로그인 상태 「Antigravity ● 사용 가능」, 계정 선택·설치·로그인 「Antigravity (Google 계정 · Gemini)」, [다음 구독으로 넘기기] 「Antigravity 구독」. 기업용 Gemini CLI로 연결될 때만 「Gemini」.
- **실행 파일 찾기**: `%LOCALAPPDATA%\agy\bin\agy.exe`(공식 설치 위치)를 먼저 찾고, PATH에서는 `agy.exe`만 쓴다 — Antigravity 데스크톱 앱의 실행기(`agy.cmd`)가 같은 이름이면 창만 열리기 때문이다.
- **[업데이트 확인]이 새 판을 못 보고 「최신 버전입니다」라고 하던 문제**: 릴리스 저장소(`kyengilam-coder/YeonE_OCR_release`)가 비공개면 GitHub는 로그인하지 않은 프로그램에 404로 답한다. 연어OCR은 이것을 "아직 릴리스 없음"으로 읽어 v1.2.14가 올라와 있는데도 「현재 버전 1.2.13이 최신 버전입니다」라고 했다. 이제 저장소 자체도 확인해, 찾을 수 없으면 「업데이트 저장소를 찾을 수 없습니다 — 비공개로 바뀌었거나 주소가 바뀌었습니다」와 릴리스 페이지를 알린다. **업데이트 확인이 되려면 릴리스 저장소가 공개여야 한다** — 이미 설치된 1.2.13·1.2.14도 저장소가 공개되면 그대로 새 판을 찾는다.
- **자동 순서: Google(Antigravity) → ChatGPT → Claude**: 구독 계정을 「자동」으로 두면 로그인된 것 중 Google 계정(Antigravity)을 먼저 쓰고, 그다음 ChatGPT, 그다음 Claude다(전에는 Claude → ChatGPT → Gemini). 한도에 닿아 넘어갈 때도 이 순서다. 계정을 직접 고르면 그것부터 쓰는 것은 그대로다.
- **ChatGPT [연결 시험]이 「Codex CLI 0.139.0이 오래되었습니다」로 실패하던 문제**: [설치](npm)로 Codex CLI를 올려도, PATH에서 먼저 보이는 오래된 `codex.exe`(따로 설치한 것)가 있으면 연어OCR은 그것을 계속 실행했다(최신은 0.169.0). 이제 이 PC의 Codex CLI(PATH의 `codex.exe`·`codex.cmd`와 npm 전역 폴더)를 모두 찾아 `--version`이 가장 높은 것을 쓰고, 그래도 거부되면 안내에 실행한 파일과 다른 Codex CLI의 경로를 함께 보인다. OpenAI의 설치 프로그램(`irm https://chatgpt.com/codex/install.ps1 | iex`)으로 깐 Codex(npm 밖의 `codex.exe`)가 있으면 [설치]는 npm 대신 그 설치 프로그램으로 올린다(실측: `codex`가 직접 그 명령으로 올리라고 안내함).
- **설정 화면 정리**: 단계가 한눈에 갈리게 했다 — 섹션 제목(큰 글, 설명은 아래 줄) > 묶음 머리(옅은 남색 띠 · 왼쪽 색 막대 · 굵은 남색 제목, 설명은 아래 줄) > 설정 줄(묶음 머리보다 들여 씀). 「인식」은 방식 · 엔진 · 판독 기록이 있을 때로 묶었고, AI 판독기의 「세부 설정」과 「판독 뒤 모델 단계」도 같은 묶음 머리로 바꿨다. 「이 책」·「책갈피 OCR 교정」 제목도 다른 섹션과 같은 크기다.
- **「로그인 상태」의 [연결 시험]이 잘리던 문제**: 자세히 보기(두 열)처럼 좁을 때 상태 글과 단추 둘이 한 줄에 들어가지 않아 [연결 시험]이 잘리고 줄 이름이 사라졌다. 상태 글은 설명 줄 자리로 옮겨 줄바꿈되고, 오른쪽에는 단추 둘만 둔다. 잘리던 계정 선택 칸의 글도 줄였다(「자동 (… )」, 「Antigravity (Google 계정)」).
- **오류 구분**: agy의 `AGY_ERROR` 줄로 한도(주간·5시간 · 크레딧 부족 — 쉬었다 다시), 로그인·자격(`Eligibility check failed` — 이번 실행에서 빼고 다음 구독으로), 모델, 일시 오류를 가린다.

**검증**: Windows · Antigravity CLI 1.5.9 · Google AI Pro 계정에서 — `agy -p /quota` 종료 코드 0, `agy -p /config --settings …`에서 `agentMode`가 `auto`에서 빈 값(Default)으로 바뀜, 연어OCR이 보내는 옵션 그대로 빨강·파랑 반쪽 그림을 보낸 요청이 경고 없이 `SUCCESS`와 두 색을 맞힌 `structured_output`(1턴 · 17초 · 종료 코드 0). Linux 가상 화면(Xvfb, Tk 8.6, Python 3.12)에서 `tests/` 전체를 돌렸다(결과는 아래 PR 설명). 설치판 안의 [상태 확인]·[연결 시험]·실제 책 쪽은 아직 누르지 못했다 — [AI 검토 문서](AI_REVIEW.md)의 확인 목록을 따른다. 그 밖의 코드는 1.2.14와 같다.

# 연어OCR 1.2.14 · 엔진 관리, Gemini는 Antigravity CLI로, 구독 연결 시험 바로잡기

설치판에서 큰 OCR 엔진을 설치하고, 막힌 구독 경로를 바르게 알리는 판이다.

설치판은 앱과 PP-OCRv6만 담고, Surya · GLM-OCR · PaddleOCR server 같은 큰 엔진은 명령줄(`scripts/install_*.py`)과 별도 Python이 있어야 설치할 수 있었다. 이제 창에서 설치한다.

- **[설정] → 인식 → OCR 엔진 [엔진 관리…]**: 이 PC의 NVIDIA GPU(이름 · VRAM · 드라이버)를 점검하고, 설치할 엔진을 고른다. 쓸 만한 GPU가 있으면 전부, 없으면 아무것도 미리 고르지 않는다(GPU 전용 선택지는 고를 수 없음).
- **고를 수 있는 것**: PaddleOCR server(CPU)와 그 GPU 가속(CUDA 12.8) · Surya OCR 2(CPU)와 그 GPU 가속(CUDA 12.4) · GLM-OCR(GPU). GPU 가속을 고르면 바탕 엔진이 함께 골라진다. 이미 설치한 것은 "설치됨"으로 보인다.
- **설치 위치**: `%LOCALAPPDATA%\YeonE_OCR\local-engines`(설정에 엔진 폴더를 정해 두었으면 그곳). 앱 폴더 밖이라 업데이트·제거해도 남고, 따로 지정하지 않아도 인식 때 찾는다.
- **별도 Python이 필요 없다**: 설치판은 함께 설치된 PP-OCRv6의 Python을 `local-engines\python313`으로 복사해 설치용으로 쓴다. 소스로 실행하면 지금의 Python을 쓴다.
- **진행 · 실패 · 취소**: 단계와 내려받기 진행, 설치기 출력이 창에 보이고 `local-engines\engine-manager\install-*.log`에 남는다. 실패하거나 취소한 것은 체크된 채 남아 [설치]를 다시 누르면 이어서 한다(받은 파일은 다시 쓴다). [취소]는 설치기와 그 하위 프로세스(pip · Ollama)를 함께 끝낸다.
- **설치 뒤 확인**: 설치 기록과 모델 해시를 확인하고, GPU 가속은 실제로 CUDA로 뜨는지 본다(ONNX Runtime의 CUDA 세션 · llama.cpp의 장치 목록). 확인에 실패하면 "설치됨 · 확인 실패"로 알린다.
- **설치 프로그램**: 추가 작업에 "설치 뒤 엔진 관리 열기"(기본 끔). 켜면 설치가 끝나고 앱이 엔진 관리 창과 함께 열린다(`YeonE_OCR.exe --open-engine-manager`).
- **명령줄**: `python -m yeone_ocr.engine_manager`(점검만) · `--install recommended` 또는 선택지 이름.
- 설치할 때만 공개 파일을 내려받는다. 문서 · 설정 · API 키는 읽지 않는다. 엔진과 가중치는 여전히 설치파일에 넣지 않는다(Surya 가중치는 Modified AI Pubs Open RAIL-M — 설치 전 창에서 알린다).
- **GPU 엔진 켜고 끄기**: [설정] → 인식에 **GPU 엔진 — GPU 엔진도 함께 읽기 (느림)**를 넣었다. 엔진 관리로 CUDA 엔진을 설치하면 로컬 우선 인식이 쪽마다 그중 하나(번체·간체는 GLM-OCR, 한글·한자 혼용은 Surya)를 더 돌리는데, 생성형 모델이라 쪽당 시간이 크게 늘고 그 엔진 결과가 없는 이미 읽은 쪽도 이어서 할 때 다시 처리한다(GTX 1660에서 이어 읽던 462쪽 책이 1쪽부터 다시 시작했다). 끄면 기존 엔진만 읽고 이미 읽은 쪽은 저장된 결과로 건너뛴다. 명령줄 `--local-gpu-engines` / `--no-local-gpu-engines`. 설정에서 바꾸지 않았으면 전처럼 환경 변수 `YEONE_OCR_GPU_ENGINES`(기본 켬)를 따른다.
- **Gemini 구독을 Antigravity CLI로**: Google이 2026-06-18부터 개인 계정(무료, Google AI Pro·Ultra)의 Gemini CLI를 끝내 Gemini 구독이 "no longer supported for Gemini Code Assist for individuals"로 실패했다. 후속인 Antigravity CLI(`agy`)가 설치되어 있으면 그것으로 Gemini 구독을 쓴다(답 형식 강제·이미지는 폴더로 전달). 설정 「AI 판독기」 ①의 Gemini [설치]는 Google 공식 설치 스크립트로 agy를 설치하고, [로그인 창 열기]는 agy를 연다. 실제 계정으로는 아직 확인하지 않았다 — 확인 목록은 docs/AI_REVIEW.md 끝.
- **문서는 한국 표준 한자체로**: 자동 교정에 **한국 표준 한자체**(기본 켬)를 더했다. 간체→번체 변환 뒤에 KS X 1001 자형으로 맞춘다 — 為→爲, 真→眞, 説→說, 教→敎, 即→卽, 黄→黃 등(`korean_forms.py`의 표). 한국 자형에 함께 있는 글자(余·餘 등)는 바꾸지 않고, 번체가 여럿인 글자(当→當/噹)는 전처럼 문맥 판단에 맡긴다. 바꾼 글자는 교정 보고에 "한국 표준 한자체"로 남는다. 끄려면 설정 「자동 교정」의 체크 또는 `--no-korean-forms`. 판독 기록과 비교 프로젝트의 원문은 그대로다. 엔진·AI가 為와 爲처럼 이 표로 같아지는 자형으로 갈려 읽은 자리도 고칠 곳으로 표시하지 않는다(裏/裡처럼 표에 없는 이체자는 전처럼 표시).
- **간체·번체 차이를 "고칠 곳"으로 표시하지 않음**: PP-OCRv6는 간체·번체가 한 인식 모델이라 번체 책을 일부 간체(会·药·叶…)로 읽는다. 다른 엔진이 같은 자리를 번체로 읽으면 엔진끼리 다르다며 빨강(원본 확인 필수)으로 칠하고 AI 검증에도 보냈고, AI 쪽 판독(번체)과 맞춰 볼 때는 문단 전체가 길게 어긋나 엔진 줄을 통째로 빨강으로 남겼다. 이제 한쪽이 간체 글자이고 간체로 접으면 같아지는 차이(会/會, 复/復)는 같은 글자로 본다 — 빨강도 AI 검증 대상도 아니고, AI 쪽 판독과는 글자끼리 맞춰 AI가 원본을 보고 고른 번체(叶→葉, 复→復)를 쓴다(표시 없음). 이체자(爲/為)·문장부호·진짜 다른 글자는 전처럼 표시한다. 붙어 있는 차이 덩어리 안에서도 진짜 다른 글자만 빨강으로 칠한다. 판독 원문(비교 프로젝트의 엔진 판독)은 그대로다. 이미 읽은 쪽은 "이어서 할 때: 모두 다시 점검한 뒤 이어가기"로 한 번 돌리면 표시가 바뀐다(엔진·AI 쪽 판독은 저장된 것을 씀).
- **GPU 엔진을 끈 뒤 "성공한 로컬 기준 판독이 없습니다"로 쪽이 실패하던 문제 수정**: GPU 엔진(GLM-OCR)으로 읽은 쪽에 AI 교정이 반영되면 사람·AI 작업을 지키려고 그 판독을 기준으로 고정하는데, GPU 엔진을 끄고 이어서 하면 그 엔진이 이번에 돌지 않았다는 이유로 쪽이 실패했다. 같은 조건(문서 종류·방향·해상도)으로 끝까지 읽어 저장된 판독이면 그대로 기준으로 쓴다.
- **Claude 구독 `error_max_turns` 줄이기**: 의심 구간이 100개가 넘는 쪽에서 Claude Code가 형식(JSON 스키마)에 맞는 답을 다듬다 턴 상한(4)을 다 써 실패하고, 같은 요청을 처음부터 다시 보냈다. 상한을 10으로 올렸다.
- **구독 오류를 끝없이 다시 보내던 문제 수정**: Gemini CLI·Claude Code·Codex CLI가 실패하면 오류 출력의 끝 400자만 보고 종류를 가렸다. Node 프로그램은 오류 이름·이유를 맨 앞에, 긴 호출 경로를 뒤에 쓰므로 계정 문제(Gemini `IneligibleOrProjectIdError`)나 사용량 한도도 "일시 오류"로 보여 3초·10초 간격으로 계속 다시 보냈다. 이제 출력 전체로 가리고, 진행 기록에는 호출 경로 줄을 빼고 오류 내용만 보인다. Gemini가 "이 계정은 쓸 수 없다"고 답하면 다시 보내지 않고 이번 실행에서 뺀다.
- **네트워크 드라이브의 책에서 [한 번에 인식]이 멈추던 문제 수정**: `Z:`처럼 드라이브 문자로 연결한 NAS·SMB 공유에 있는 PDF는 "프로젝트와 원본은 다른 파일이어야 합니다"로 중단됐다. 이런 공유는 모든 파일의 파일 번호를 0으로 알려 주어, 원본 덮어쓰기를 막는 검사가 서로 다른 파일을 같은 파일로 보았다. 이제 파일 번호가 없으면 크기와 수정 시각으로 가린다(같은 파일을 다른 경로로 가리킨 경우는 여전히 막는다). 비교·교정, 책갈피 교정(메모 정리·구획 편집), 보고서 저장의 같은 검사도 함께 고쳤다.
- **[연결 시험]에서 「사용 가능」인데 실패하던 구독을 바르게 알림**: 로그인 상태는 세 구독 모두 「사용 가능」인데 [연결 시험]에서 ChatGPT·Gemini가 실패했다.
  - Gemini CLI만 설치된 PC: Google이 개인 계정을 거부하면(`UNSUPPORTED_CLIENT`) 안내가 Antigravity CLI [설치] → [로그인 창 열기]를 가리키고, 로그인 상태는 「쓸 수 없음(Antigravity CLI 설치 필요)」로 바뀐다(예전에는 "GOOGLE_CLOUD_PROJECT가 필요할 수 있다"는 틀린 안내나 호출 경로만 보였다).
  - ChatGPT(Codex): 기본 모델(`gpt-5.5`)이 "not supported when using Codex with a ChatGPT account"로 거부되면, Codex가 OpenAI에서 받아 둔 이 계정의 모델 목록(`~/.codex/models_cache.json`)부터 차례로 시도한다. 모두 거부되면 OpenAI가 "새 Codex가 필요하다"고 답했을 때는 설치된 Codex CLI(버전)가 오래되었다며 [설치]로 올리라고, 아니면 요금제와 `codex` → /model 확인을 안내한다. 로그인 상태는 「쓸 수 없음(Codex CLI 업데이트 필요 / 모델 거부)」로 바뀌고, Codex를 업데이트하면 저절로 풀린다.
- **Surya 설치 오류 수정**: Surya 설치기가 판 번호 없는 `get-pip.py`를 고정 해시로 확인해, pip 새 판이 나온 뒤로 "Public download SHA-256 mismatch"로 멈췄다. 이제 판 번호·해시가 고정된 pip 휠(26.2.1)을 쓴다.
- EasyOCR · RapidOCR · Tesseract는 대상이 아니다(GPU 선택지가 없고, 기본 인식은 내장 PP-OCRv6가 맡는다).

**검증**: Linux(Python 3.13, 화면 시험은 Xvfb · Tk 8.6 · Python 3.12)에서 새 시험 `tests/test_engine_manager.py`(nvidia-smi 출력 파싱 · 추천 · 설치 위치 · 명령 구성과 실제 설치기의 인자 대조 · 설치용 Python 복사 · 진짜 프로세스로 실행·취소·다시 시도)와 `tests/test_gui_engines.py`(진짜 Tk 창)를 포함한 `tests/` 전체 — 2,428개 통과 · 29개 건너뜀 · 실패 31개(책갈피·미리 보기·작은 주석 화면 시험 6개 모듈 — 변경 전 소스에서도 같은 환경에서 같은 수로 실패). 엔진 관리로 PaddleOCR server(CPU)를 실제로 설치해 보아 venv 생성과 고정 패키지 설치까지 되는 것을 확인했고, 모델 내려받기는 시험 환경의 네트워크 제한(modelscope.cn 차단)으로 끝내지 못했다. GitHub Actions의 Windows 실행기에서 전체 시험(2,488개)이 통과했고, Windows PC에서 새 PP-OCRv6 번들을 만들어 그 Python을 앱처럼 복사한 것으로 venv + pip가 만들어지는 것을 확인했다. 개발 PC(GTX 1660, 별도 Python 없음)의 설치본에서 다섯 선택지를 모두 설치했고, Surya GPU 가속은 llama.cpp가 CUDA 장치(GTX 1660)를 찾는 것까지 확인했다. **새 엔진으로 실제 문서를 인식하는 확인은 아직이다** — 배포 전 [설치판 문서](windows-release.md)의 확인 목록을 따른다.

# 연어OCR 1.2.13 · 중간에 멈춘 뒤 읽은 쪽까지 HWPX 만들기

1.2.12를 갱신하는 판이다.

[한 번에 인식 (HWPX 만들기)]를 [■ 중지]로 멈추면 판독 기록만 남고 문서는 만들어지지 않았다. 이제 그때까지의 기록으로 HWPX를 만들 수 있다.

- **멈춘 직후**: "지금까지 판독 기록이 있는 N쪽으로 HWPX를 만들까요?"라고 묻는다. [예]면 바로 만들고, 다 만들면 열지 묻는다.
- **나중에**: 실행 카드의 중지 단추 아래 **[읽은 쪽까지 HWPX 만들기]**. 판독 기록이 있고 남은 쪽이 있는 책(또는 방금 중지한 실행)에서만 보인다.
- **만들어지는 파일**: 판독 기록이 있는 쪽만 들어가고 이름에 쪽 범위가 붙는다(`이름_p001-193.hwpx`). [HWPX 열기]는 가장 최근에 만든 것을 연다. 쪽 범위를 적었으면 그 범위 안의 읽은 쪽만.
- **모델을 부르지 않는다**: 요금·구독 사용량이 없고 API 키도 묻지 않는다. 문맥 교정 모델 단계는 빠진다(규칙 변환은 그대로).
- **AI를 기다리던 쪽**: 엔진만 읽고 AI 검증 차례를 기다리던 쪽은 엔진 판독 그대로 들어간다.
- **이어서 하기**: [한 번에 인식]을 다시 누르면 남은 쪽부터 읽고, 끝나면 전체 문서(`이름.hwpx`)가 따로 만들어진다. 부분 문서 파일은 그대로 남는다.
- 명령줄에서는 전부터 되던 `yeone-ocr build 원본.pdf --no-context-model`과 같다. 「한 번에 인식 (문자 PDF 만들기)」를 멈췄을 때는 묻지 않는다.

**검증**: Linux 가상 화면(Xvfb, Tk 8.6, Python 3.12)에서 화면 시험을 포함한 `tests/` 전체 — 2,420개 통과 · 29개 건너뜀 · 실패 1개(`test_bookmark_section_editor`의 지연 표시 시험 — 변경 전 소스에서도 같은 환경에서 실패). 6쪽 모의 책을 4쪽째에서 멈춘 뒤 실제 문서 만들기를 돌려 1~3쪽만 든 `book_p001-003.hwpx`가 만들어지는 것을 확인했다. 단추와 물음 창을 실제 Windows 앱에서 눌러 보지는 못했다 — Windows 설치판은 배포 CI의 회귀·설치 검사가 첫 확인이다. 그 밖의 코드는 1.2.12와 같다.

# 연어OCR 1.2.12 · 엔진은 AI를 기다리지 않고, 구독은 쉬었다 돌아온다

1.2.11을 갱신하는 판이다. 구독 계정(Claude · ChatGPT · Gemini)으로 판독·검증하는 실행이 대상이다.

**더 빠르게**

- **엔진은 AI의 답을 기다리지 않는다**: 엔진을 마친 쪽은 판독을 먼저 저장하고 쪽 차례대로 AI 차례를 기다리며, 엔진은 다음 쪽을 계속 읽는다. 쪽 띠에 「AI 대기」 칸이 생겼고, 진행 수는 엔진이 읽은 쪽이 아니라 AI 부분까지 끝난 쪽이다. [중지]를 누르면 차례를 기다리던 쪽은 엔진 판독만 남고, 다음 실행에서 엔진을 다시 돌리지 않고 이어 검증한다.
- **계정 하나가 여러 쪽을 함께**: 설정 「AI 판독기」 ① 「계정이 함께 맡는 쪽」(기본 2, 1~4, `--local-ai-pages`). 「쪽 나눠 보내기」를 끄거나 계정이 하나뿐이어도 적용된다.
- **쪽 판독과 검증을 함께**: 한 쪽 안에서 AI 쪽 판독과 의심 구간 검증을 동시에 보낸다(서로의 결과를 쓰지 않고 기록에서 만난다).
- 총 사용량은 같고 한도(5시간·주간·하루)가 그만큼 빨리 찬다. 계정당 동시 요청은 기본 설정에서 최대 8개(2쪽 × (검증 3 + 쪽 판독 1))다 — 줄이려면 「계정이 함께 맡는 쪽」을 1로.
- "엔진으로 전부 읽은 뒤 AI에 보내기"만으로는 전체 시간이 줄지 않는다(전체 시간은 AI가 정한다). 줄이는 것은 AI 쪽의 동시 처리다.

**구독 계정이 실행에서 빠지던 문제**

- **일시 오류는 다시 보낸다**: 서버 혼잡·네트워크·알 수 없는 실패 한 번으로 그 계정을 실행 끝까지 쓰지 않던 것을 고쳤다. 같은 계정에 3초·10초 뒤 다시 보내고, 그래도 실패하면 10분(되풀이되면 20분, 40분 …) 쉬게 한 뒤 다시 쓴다. 같은 요청이 다른 계정에서도 실패하면 요청 탓으로 보고 그 요청만 실패로 남긴다.
- **한도는 풀리면 돌아온다**: 한도에 닿은 계정은 그 프로그램이 말한 초기화 시각("resets 12:10am", "try again in 3 hours")까지 쉬고 다시 쓴다. 시각을 말하지 않으면 30분 뒤 다시 확인한다. Claude Code의 "You've hit your 5-hour limit" 문구를 한도로 읽는다. [다음 구독으로 넘기기]로 직접 넘긴 연결은 저절로 돌아가지 않는다.
- **Codex CLI(ChatGPT)**: 그림 뒤의 `-`(표준 입력 표시)를 Codex가 그림 파일로 읽어 "could not read the local image at `-`"가 요청에 섞이던 것을 고쳤다(실제 Codex CLI 0.167.2로 확인). 기본 모델이 거부되면 오래된 CLI가 내는 옛 모델 목록 뒤에 지금의 모델 이름도 이어 시도하고, "newer version" 요구는 CLI를 올리라는 안내로 알린다.
- **잘못 읽던 오류**: 시간 표기·요청 번호 속의 401·429를 로그인·한도 문제로 읽지 않는다. Gemini CLI가 매번 찍는 "Loaded cached credentials."를 로그인 문제로 읽지 않는다. 순간적인 `rate_limit_error`·과부하는 한도가 아니라 일시 오류로 다룬다.
- **계정이 빠지는 순간의 쪽 오류**: 한 계정이 빠질 때 그 계정에 나가 있던 다른 요청의 답이 잘못된 완료 표시로 기록되어 그 쪽이 "AI 위치 복원 기록…" 오류가 되던 것을 고쳤다(1.2.2부터 있던 문제).
- **Gemini CLI 찾기**: `npm prefix -g`가 알려 주는 전역 폴더, Scoop · Chocolatey · winget · bun의 실행 파일 폴더에서도 찾고, `--version`이 느려도 설치된 것으로 본다. 못 찾으면 찾아본 곳을 알려 준다.

**무슨 일이 있는지 보이게**

- **[연결 시험]**(설정 「AI 판독기」 ① 「로그인 상태」, 명령줄 `yeone-ocr plans --test`): 쓸 수 있는 구독마다 작은 요청 하나를 실행 때와 같은 방식으로 실제로 보내, 답한 모델·걸린 시간 또는 그 프로그램이 말한 실패 이유를 보여 준다(구독 사용량에서 조금 차감).
- **AI 연결 줄**: 쪽 나눠 보내기의 모든 연결과 쉬는 계정(몇 분 뒤 다시 · 이번 실행 제외)을 보이고, 마우스를 올리면 이유가 나온다. [다음 구독으로 넘기기]는 같은 계정을 쓰던 다른 연결도 함께 옮긴다.
- 진행 기록의 「AI 쪽 판독」 줄에 답한 연결을 적는다.

**검증**: Linux 가상 화면(Xvfb, Tk 8.6, Python 3.12)에서 화면 시험을 포함한 `tests/` 전체 — 2,417개 통과 · 29개 건너뜀 · 실패 1개(`test_bookmark_section_editor`의 지연 표시 시험 — 변경 전 소스에서도 같은 환경에서 실패). Codex 호출은 실제 Codex CLI 0.167.2를 가짜 Responses 서버에 붙여 요청 본문(그림 · 지시문 · 스키마)과 모델 거부 · 한도 · 서버 오류의 문구를 확인했다. 속도는 엔진과 AI를 가짜로 바꾼 모의 실행(24쪽, 엔진 0.05초 · 쪽 판독 1.2초 · 검증 1회 0.6초)으로 쟀다: 한 계정 33.9초 → 15.8초, 두 계정 17.3초 → 8.1초, 세 계정 12.1초 → 5.8초. 세 계정에 일시 오류 · 한도 · 로그인 만료를 섞은 모의 실행도 모든 쪽이 검증됐다. **실제 ChatGPT · Gemini 계정으로는 시험하지 못했다** — 1.2.11에서 ChatGPT가 빠진 실제 오류 문구는 확인하지 못했고, 위 수정은 재현한 결함에 대한 것이다. ChatGPT · Gemini의 검증 정확도는 아직 재지 않았다. Windows 설치판은 배포 CI의 회귀·설치 검사가 첫 확인이다.

# 연어OCR 1.2.11 · 쪽 띠의 「기록 있음」을 옅은 파랑으로

1.2.10을 갱신하는 판이다.

- **쪽 띠의 「기록 있음 · 건너뜀」 칸**(앞선 실행에서 끝나 이번에 건너뛴 쪽)을 회색 점선에서 **옅은 파랑 채움**으로 바꿨다. 「끝남」(이번 실행에서 처리, 진한 파랑)과 같은 계열이라 끝난 쪽 전체가 파랑으로 보이고, 진하기로 "이번에 했는지 · 전에 해 두었는지"를 가른다. 범례도 같다. 회색은 아직 끝나지 않은 것처럼 읽혀 헷갈렸다.

**검증**: Linux 가상 화면(Xvfb, Tk 8.6, Python 3.12)에서 화면 시험(진행 카드 · 설정 · 로컬 우선) 66개 통과, 새 색으로 쪽 띠와 범례를 그려 확인했다. 그 밖의 코드는 1.2.10과 같다. Windows 설치판은 배포 CI의 회귀·설치 검사가 첫 확인이다.

# 연어OCR 1.2.10 · Codex 모델 거부 시 다른 모델로

**1.2.9는 배포 회귀 시험에서 멈춰 게시되지 않았다**(새 시험 둘이 Windows에서 건너뛰도록 되어 있었고, 배포 회귀는 건너뛴 시험을 실패로 본다 — 두 시험이 Windows 경로로도 돌게 고쳤다). 그래서 1.2.10에 1.2.9의 변경이 모두 들어 있다:

- **구독 프로그램 설치·로그인**: 설정 「AI 판독기」 ①의 설치·로그인 줄 — [설치]는 확인 뒤 공식 설치 명령(`npm install -g @google/gemini-cli` · `@openai/codex`)을 실행하고, npm이 없으면 winget으로 Node.js LTS 설치를 묻거나 내려받기 페이지를 연다. [로그인 창 열기]는 공식 프로그램을 새 창으로 연다(로그인은 그 회사 화면에서).
- **로그인 상태 원인 표시**: Gemini CLI를 찾았지만 실행되지 않으면 「설치 안 됨」이 아니라 「실행 실패」와 종료 코드·오류 문구·경로. Codex CLI·Gemini CLI를 PATH 밖(npm 전역 폴더·Node 설치 폴더·nvm·Volta·pnpm)에서도 찾는다. 「로그인 상태」에 마우스를 올리면 계정마다 이유와 해결 방법.
- **쪽 나눠 보내기 기본 켬**: 1.2.8에서 저장된 '끔'(그때의 기본값)은 한 번만 켬으로 옮기고, 그 뒤 직접 끈 값은 지킨다.

그리고 ChatGPT 구독(Codex CLI)으로 판독·검증할 때 "The 'gpt-5.5' model is not supported when using Codex with a ChatGPT account (model_not_found)"로 쪽마다 실패하던 문제를 고쳤다.

- **원인**: 연어OCR은 모델을 정하지 않고 Codex가 계정에 맞춰 고르게 둔다. 그런데 Codex가 고른 기본 모델(gpt-5.5)을 그 ChatGPT 계정이 쓸 수 없었다(예전 판 Codex일 때 흔함 — 최신 0.167의 기본은 gpt-6.1-sol). 또 오류 문구에 `invalid_request_error`가 들어 있어 연어OCR이 이를 "요청 자체의 거부"로 잘못 나눠, 다른 모델로도 다른 구독으로도 넘기지 않고 쪽마다 같은 실패를 되풀이했다.
- **다른 모델로 다시**: 기본 모델이 거부되면 `codex debug models`로 그 계정이 쓸 수 있는 모델 목록을 받아, 이미지를 받는 모델을 Codex의 우선순위대로 같은 요청에 다시 써 보고, 답한 모델을 그 뒤 요청에 바로 쓴다(목록을 내지 못하는 예전 Codex는 짧은 내장 목록). 모두 거부되면 계정 문제로 보고 다음 구독으로 넘긴다(Codex를 최신으로 올리라는 안내와 함께). `YEONE_OCR_CHATGPT_MODEL`로 직접 정한 모델은 바꾸지 않는다.
- **오류 나누기 순서**: 로그인 · 사용량 한도 · 쓸 수 없는 모델 같은 계정 문제를 먼저 보고, 그다음에 요청 거부(스키마·입력)를 본다.
- Codex를 최신으로 올리려면 설정 「AI 판독기」 ①의 [설치](이미 있어도 최신판으로 다시 설치) 또는 PowerShell에서 `npm install -g @openai/codex`.

**검증**: Linux 가상 화면(Xvfb, Tk 8.6, Python 3.12)에서 화면 시험을 포함한 `tests/` 전체 — 2,393개 통과 · 29개 건너뜀 · 실패 1개(`test_bookmark_section_editor`의 지연 표시 시험 — 변경 전 소스에서도 같은 환경에서 실패). 기본 모델이 거부되면 계정 목록의 다음 이미지 모델로 같은 요청이 성공하고 기억되는지, 모두 거부되면 계정 문제(다음 구독으로)인지, 직접 정한 모델은 바꾸지 않는지, 모델 거부가 요청 거부보다 먼저 나뉘는지 시험한다. 판 번호 1.2.10은 업데이트 확인에서 숫자로 비교한다((1,2,10) > (1,2,9)). 실제 ChatGPT 계정으로는 이 환경의 네트워크 제한 때문에 확인하지 못했다. Windows 설치판은 배포 CI의 회귀·설치 검사가 첫 확인이다.

# 연어OCR 1.2.9 · 구독 프로그램 설치·로그인 · 로그인 상태 원인 표시 · 쪽 나눠 보내기 기본 켬

1.2.8을 갱신하는 판이다.

**설치·로그인을 창에서**

- 설정 「AI 판독기」 ①에 **설치·로그인** 줄을 더했다. 구독(Gemini · ChatGPT · Claude)을 고르고 **[설치]**를 누르면, 실행할 공식 설치 명령을 보여 주고 물은 뒤 이 PC에서 실행한다 — Gemini CLI `npm install -g @google/gemini-cli`, Codex CLI `npm install -g @openai/codex`. 과정은 진행 기록에 나오고, 끝나면 로그인 상태를 다시 확인한다. Claude Code는 Anthropic의 공식 설치 프로그램을 안내한다.
- npm(Node.js)이 없으면 Windows 패키지 관리자(winget)로 Node.js LTS를 먼저 설치할지 묻고, winget도 없으면 Node.js 내려받기 페이지를 연다.
- **[로그인 창 열기]**는 고른 구독의 공식 프로그램을 새 창으로 연다(Gemini는 'Login with Google', ChatGPT는 'Sign in with ChatGPT'). 로그인은 그 회사 화면에서 직접 하며 이 프로그램은 비밀번호·토큰을 보지 않는다. 로그인한 뒤 [상태 확인].

**로그인 상태: 「설치 안 됨」과 「실행 실패」 구분**

- 이전에는 Gemini CLI를 찾았어도 `gemini --version`이 실패하면(낮은 Node.js · 시간 초과 등) 이유 없이 「설치 안 됨」으로 보였다. 이제 찾으면 설치됨으로 두고, 실행이 안 되면 **「실행 실패」**와 종료 코드 · 오류 문구 · 찾은 경로를 보인다.
- Codex CLI · Gemini CLI를 PATH 밖에서도 찾는다: npm 전역 폴더(`%APPDATA%\npm`) · Node 설치 폴더 · nvm · Volta · pnpm · Homebrew · `~/.local/bin`.
- 「로그인 상태」에 마우스를 올리면 계정마다 경로 · 이유 · 해결 방법이 나온다. 명령줄 `yeone-ocr plans`도 같은 구분과 경로를 보인다.
- 참고: Gemini 구독(Google AI Pro 등)이 있어도 연어OCR은 **Gemini CLI**를 통해서만 쓴다 — 설치와 'Login with Google'이 필요하다.

**쪽 나눠 보내기 기본 켬**

- 「쪽 나눠 보내기」(1.2.8)를 기본으로 켠다(명령줄도 기본 켬, 끄려면 `--no-local-ai-split`). 1.2.8에서 저장된 '끔'(그때의 기본값)은 한 번만 켬으로 옮기고, 그 뒤 직접 끈 값은 지킨다. 로그인된 구독이 하나뿐이면 한 계정으로 진행한다.

**검증**: Linux 가상 화면(Xvfb, Tk 8.6, Python 3.12)에서 화면 시험을 포함한 `tests/` 전체 — 2,390개 통과 · 29개 건너뜀 · 실패 1개(`test_bookmark_section_editor`의 지연 표시 시험 — 변경 전 소스에서도 같은 환경에서 실패). 설치 명령 · npm 찾기 · 설치 출력 흐름 · 운영체제별 로그인 창 · 설치 단추의 확인·Node.js 안내 · 찾았지만 실행되지 않는 CLI · PATH 밖 npm 폴더 · 기본 켬 옮기기를 시험한다. 실제 Windows에서 npm 설치·로그인 창은 이 환경에서 실행하지 못했다. Windows 설치판은 배포 CI의 회귀·설치 검사가 첫 확인이다.

# 연어OCR 1.2.8 · 여러 구독에 쪽 나눠 보내기

1.2.7을 갱신하는 판이다. 로그인된 구독 계정이 둘 이상이면 계정마다 쪽을 맡아 AI 쪽 판독·검증을 함께 진행하는 선택을 더했다(기본 끔).

- **쪽 나눠 보내기**: 설정 「AI 판독기」 ① 「쪽 나눠 보내기」 · 명령줄 `--local-ai-split`. 켜면 로그인된 구독(Claude · ChatGPT · Gemini)마다 연결과 작업자를 하나씩 두고, 엔진이 다음 쪽을 읽는 동안 비어 있는 계정에 앞 쪽의 AI 작업(AI 쪽 판독 → 검증 계획 → 검증 → 제안 반영 → 기록)을 맡긴다. 계정 수만큼 쪽이 함께 진행되고, 각 계정 안에서는 1.2.7의 동시 AI 요청(기본 3)이 그대로 쓰인다.
- **한 쪽은 한 계정이 끝까지** 검증한다(묶음마다 모델이 섞이지 않음). 한도는 계정마다 나눠 쓴다. 한 계정이 한도에 닿으면 그 계정이 맡은 쪽은 1.2.2의 넘김으로 다음 구독 → API 키로 간다.
- 검증 계획의 제공사·모델 설정은 실행 전체에 하나로 둔다. 그래서 다음 실행에서 쪽이 다른 계정에 배정되어도 이미 끝난 검증 묶음을 다시 사지 않는다. 실제로 답한 계정·모델은 검증 기록(metadata의 transport · actual_model)에 남는다.
- 주의: 쪽마다 검증한 모델이 다를 수 있다. ChatGPT · Gemini의 검증 정확도는 아직 재지 않았다(기본 설정은 Claude로 잼). 그래서 기본은 끔이다. 로그인된 구독이 하나뿐이면 한 계정으로 진행한다. [다음 구독으로 넘기기]는 첫 계정의 연결을 옮긴다. [중지]는 계정마다 진행 중인 쪽을 마무리한 뒤 멈춘다.
- 이 선택을 끄면 쪽 처리는 예전과 같은 차례로 한 곳에서 한다(AI 단계를 함수로 옮기기만 함).

**검증**: Linux 가상 화면(Xvfb, Tk 8.6, Python 3.12)에서 화면 시험을 포함한 `tests/` 전체 — 2,379개 통과 · 29개 건너뜀 · 실패 1개(`test_bookmark_section_editor`의 지연 표시 시험 — 변경 전 소스에서도 같은 환경에서 실패). 두 계정이 쪽을 나눠 함께 진행하고 한 쪽은 한 계정만 맡는지, 바쁜 계정이 아니라 빈 계정에 다음 쪽이 가는지, 쪽 실패·[중지] 보고, 실제 실행에서 나눠 보내기가 켜지는지 시험한다. 실제 구독 계정 여럿으로 시간을 재지는 못했다(이 환경의 네트워크 제한). Windows 설치판은 배포 CI의 회귀·설치 검사가 첫 확인이다.

# 연어OCR 1.2.7 · 구독 검증 요청을 여러 개 함께

1.2.6을 갱신하는 판이다. 구독 계정으로 의심 구간을 검증할 때 한 쪽의 검증 묶음을 하나씩 차례로 보내던 것을 여러 개 함께 보내, 묶음이 많은 쪽을 빠르게 지나간다.

- **동시 AI 요청(기본 3)**: 설정 「AI 판독기」 ③ 「동시 AI 요청」(1~4) · 명령줄 `--local-ai-parallel`. 구독 계정으로 검증할 때 한 쪽의 검증 묶음을 이 수만큼 함께 보낸다. 묶음이 많은 쪽(예: 의심 구간 49개 · 13회)은 대략 2~3배 빨라지고, 묶음이 하나인 쪽과 AI 쪽 판독(쪽당 1회)은 그대로다. 1로 두면 예전처럼 하나씩.
- 요청만 함께 보내고, 이미지 준비 · 응답 확인 · 기록은 예전처럼 계획 차례대로 한다(기록 순서와 안전 검사는 그대로). 한 요청이 한도에 닿거나 실패하면 새 요청은 보내지 않고 이미 보낸 요청의 답은 기록한다. [중지]도 같다. 한도에 닿은 요청은 1.2.2의 넘김으로 다음 구독에 다시 간다.
- **총 사용량은 같고**, 같은 시간에 쓰는 양이 늘어 한도(5시간·주간·하루)가 그만큼 빨리 찬다. 각 회사는 공식 프로그램을 여러 개 동시에 쓰는 것을 막지 않으며 같은 사용량 한도에서 차감한다(Anthropic 도움말: Claude Code를 여러 개 동시에 쓰면 한도에 더 빨리 닿음 · Codex는 CLI·클라우드가 같은 한도 · Gemini CLI는 분당·하루 요청 한도). API 키로 검증할 때는 요금제별 속도 제한이 있어 하나씩 보낸다.

**검증**: Linux 가상 화면(Xvfb, Tk 8.6, Python 3.12)에서 화면 시험을 포함한 `tests/` 전체 — 2,374개 통과 · 29개 건너뜀 · 실패 1개(`test_bookmark_section_editor`의 지연 표시 시험 — 변경 전 소스에서도 같은 환경에서 실패). 요청 3개가 실제로 겹쳐 나가고 시간이 줄며 기록은 계획 차례인지, 하나씩 경로가 그대로인지, 치명적 실패·[중지] 때 새 요청 없이 이미 보낸 답을 남기는지, 구독은 3개·API 키는 1개로 보내는지 시험한다. 실제 구독 계정으로 시간을 재지는 못했다(이 환경의 네트워크 제한). Windows 설치판은 배포 CI의 회귀·설치 검사가 첫 확인이다.

# 연어OCR 1.2.6 · 빠른 이어하기 · 「이어서 할 때」 선택

1.2.5를 갱신하는 판이다. 중간에 멈춘 OCR을 이어서 할 때 이미 끝난 쪽을 빨리 지나가게 하고, 앞선 쪽을 어떻게 다룰지 고를 수 있게 했다.

**끝난 쪽은 바로 건너뜀**

- 이전에는 이어서 할 때 끝난 쪽에서도 엔진 판독·AI 호출만 건너뛰고, 쪽 그림을 다시 그려 저장하고, AI 쪽 판독 저장본을 찾으려 쪽을 다시 자르고, 의심 구간마다 조각 그림(1024화소 상세 조각 포함)을 만들어 검증 계획을 세우고, 비교 프로젝트와 쪽 기록을 두 번 다시 썼다(의심 구간이 많은 쪽은 몇 초씩).
- 이제 쪽 기록에 이어하기 열쇠(판독 조건 · 기준 엔진 판독 · 쪽 본문 지문 · AI 설정)를 남긴다. 다음 실행에서 엔진이 다시 돌지 않았고 열쇠가 같고 AI 검증(과 AI 쪽 판독)이 끝난 쪽은 이 준비 없이 바로 넘어간다 — 진행 기록 "N쪽: 끝난 쪽 — 같은 조건이라 건너뜀", 쪽 띠 「기록 있음·건너뜀」.
- 사람이 비교·교정 창에서 고친 쪽(본문 지문이 달라짐), 설정이 바뀐 쪽, 검증이 보류·실패·중지된 쪽은 예전처럼 처리한다. 이전 실행이 만든 쪽 그림은 다시 그리지 않는다.
- 1.2.5까지 만든 기록에는 열쇠가 없어, 새 판에서 한 번 더 예전 방식으로 지나가며 열쇠를 남긴다(그 뒤로 빠름).

**「이어서 할 때」 선택**

- 실행 카드(이 책에 판독 기록이 있을 때)와 설정 「인식」에서 고른다. 명령줄 `--local-resume`.
  - **끝나지 않은 쪽만 점검(기본)**: 위의 빠른 건너뛰기.

# 연어OCR 1.2.4 · 구독 검증 오류 수정 · 한국어 진행 기록

1.2.3을 고치는 판이다. 구독 계정으로 검증할 때 "Claude Code가 검증 스키마를 거부했습니다" → ChatGPT로 넘어감 → API 키로 넘어감 → "AI 검증 대상 식별자가 올바르지 않습니다"로 쪽이 실패하고, 이후 쪽이 API 키 상한에 걸려 보류되던 문제를 고쳤다.

- **겹친 검증 대상 식별자**: 한 단어 뒤에 글자로 읽지 못한 먹 자국(그림·표시 등)이 여럿 있으면 그 대상들이 같은 빈 위치를 갖고, 식별자가 위치·글자로만 만들어져 서로 같았다. 구독 기본값(한 호출에 4구간)에서 같은 식별자 둘이 한 묶음에 들어가면 응답 스키마에 같은 값이 두 번 들어가 Claude Code가 거부했고("enum must NOT have duplicate items" — Claude Code 2.1.322로 재현), 프로젝트도 그 검증 기록을 거부했다. 이제 겹치는 대상에만 먹 자국 위치로 다른 식별자를 준다(겹치지 않는 식별자는 그대로라 이미 검증한 기록을 이어 쓴다).
- **요청 거부는 계정 문제가 아님**: 프로그램이 요청 자체(스키마·입력)를 거부하면 그 요청만 실패로 두고 구독 계정은 그대로 쓴다. 이전에는 계정을 쓸 수 없다고 보고 다른 구독 → API 키로 넘어가, 실행의 나머지가 API 키 상한(기본 20회)에 걸려 보류됐다.
- **오류 원문 표시**: 구독 프로그램의 오류 안내 뒤에 프로그램의 원래 문구를 `(원문: …)`으로 붙인다. "쓸 수 없는 모델" 안내는 실제 모델 거부 문구가 있을 때만 낸다(이전에는 'model'이 든 아무 오류에나 냄). 잘못된 "`claude update`로 올리세요" 안내는 뺐다.
- **진행 기록 한국어 표기**: 쪽마다 끝에 적는 검증 상태를 한국어로 적는다 — AI 검증 필요 없음 · 사람 확인 필요(위치를 못 찾은 의심 구간) · AI 검증 보류 · AI 검증 끝 · AI 검증 일부 실패, "로컬 엔진 ppocrv6". 기록 파일의 상태 값은 그대로다.
- **보류 이유**: "API 키 이번 실행 상한(20회) 도달 — [다음 구독으로 넘기기]에서 구독 계정을 직접 고르면 이어서 검증" 또는 "쓸 수 있는 구독 계정도 API 키도 없음"처럼 원인과 할 일을 적는다.
- **AI 연결 줄**: "API 키 · gemini · 남은 18회"처럼 짧게 적어 옆 칸과 겹치지 않고, 남은 호출이 호출마다 줄어든다.

**검증**: Linux 가상 화면(Xvfb, Tk 8.6, Python 3.12)에서 `tests/` 전체 — 2,169개 통과 · 225개 건너뜀 · 실패 0개. 같은 빈 위치의 먹 자국 두 곳이 한 묶음에서 서로 다른 식별자 · 중복 없는 스키마 · 검증 기록 저장 · 다시 계획할 때 이어 쓰기를 확인하는 시험과, 거부된 요청이 계정을 바꾸지 않는 시험을 더했다. Windows 설치판은 배포 CI의 회귀·설치 검사가 첫 확인이다.

# 연어OCR 1.2.3 · [다음 구독으로 넘기기]

1.2.2를 갱신하는 판이다. 실행 중에 쓰던 구독 계정을 직접 멈추고 다른 구독 계정으로 옮기는 단추를 더했다. 안내는 [구독 계정 안내](SUBSCRIPTION_PLANS.md)의 「실행 중에 직접 넘기기」.

- **AI 연결 줄**: 구독 계정으로 연결된 실행 중에는 진행 카드 아래에 지금 연결(예: Claude 구독) · **넘길 곳** · **[다음 구독으로 넘기기]**가 나온다. 구독 연결이 없는 실행에는 나오지 않는다.
- **넘길 곳을 고르고 누르면**: 지금 쓰는 구독을 멈추고 고른 계정에 연결한다. 답을 기다리던 요청이 있으면 그 프로그램을 자식 프로그램까지 끄고(Windows `taskkill /T`), 같은 요청을 새 계정으로 다시 보낸다. 고른 계정이 로그인되어 있지 않으면 진행 기록에 알리고 정해진 순서로 고른다. 넘길 곳에는 다른 구독 계정과, API 키가 있으면 「API 키」가 있다.
- **고르지 않고(자동) 누르면**: 정해진 순서(Claude → ChatGPT → Gemini)의 다음 계정에 연결하고, 남은 구독이 없으면 API 키로 간다(1.2.2의 한도 넘김과 같은 상한). 목록의 「자동(순서대로) (다음: …)」이 갈 곳을 미리 보여 준다.
- 넘긴 계정은 그 실행에서 다시 쓰지 않는다(넘길 곳에서 직접 고르면 다시 씀). 넘길 곳이 없으면 지금 연결을 그대로 쓴다. 넘길 때마다 진행 기록에 적는다. 쪽 판독과 의심 구간 검증이 함께 넘어간다.
- 명령줄 실행에는 단추가 없고 1.2.2의 자동 넘김(한도·로그인 만료)만 동작한다.

**검증**: Linux 가상 화면(Xvfb, Tk 8.6, Python 3.12)에서 `tests/` 전체 — 2,165개 통과 · 225개 건너뜀 · 실패 0개. 새 시험은 실제 자식 프로세스로 답을 기다리는 중에 넘겨 프로그램이 꺼지고 같은 요청이 고른 계정으로 가는지, 자동 순서 · 로그인 안 된 계정 고름 · API 키 · 넘길 곳 없음, 창의 AI 연결 줄과 단추를 본다. 로그인된 실제 계정으로는 이 환경의 네트워크 제한 때문에 확인하지 못했다. Windows 설치판은 배포 CI의 회귀·설치 검사가 첫 확인이다.

# 연어OCR 1.2.2 · ChatGPT·Gemini 구독 계정 · 한도에 닿으면 다른 구독 → API 키

1.2.1을 갱신하는 판이다. 로컬 우선 인식의 AI 쪽 판독·의심 구간 검증을 Claude뿐 아니라 ChatGPT·Gemini 구독 계정으로도 할 수 있게 하고, 쓰던 구독의 사용량이 다 차면 다른 구독으로, 남은 구독이 없으면 API 키로 이어 가게 했다. 안내는 [구독 계정 안내](SUBSCRIPTION_PLANS.md).

**구독 계정 셋**

- **ChatGPT(Plus/Pro 등)**: 공식 OpenAI Codex CLI(`codex exec`)를 실행한다. `npm install -g @openai/codex` 뒤 `codex login`에서 'Sign in with ChatGPT'.
- **Gemini(Google 계정)**: 공식 Gemini CLI(`gemini -p`)를 실행한다. `npm install -g @google/gemini-cli` 뒤 `gemini`를 한 번 실행해 'Login with Google'.
- **Claude**: 1.2.0과 같다(Claude Code `claude -p`).
- **고르기**: 설정 「구독 계정 판독」(이전 「Claude 구독 판독」)의 계정 선택 — 자동 / Claude / ChatGPT / Gemini. 명령줄 `--local-ai-plan`, 환경 변수 `YEONE_OCR_AI_PLAN`. 자동은 로그인된 것 중 Claude → ChatGPT → Gemini 순이고, 계정을 고르면 그것부터 쓴다. `yeone-ocr plans`로 세 프로그램의 설치·로그인 상태를 본다(모델 호출 없음).
- 원칙은 Claude와 같다: 공식 프로그램만 실행하고 로그인 토큰 파일은 읽지 않는다(Gemini는 로그인 방식 확인에 `settings.json`만 읽음). 자식 프로그램에는 API 키 환경 변수를 넘기지 않고, 요청마다 빈 임시 폴더에서 도구·MCP·확장·사용자 설정을 끄고 실행한다. 개인 사용 전용.
- ChatGPT·Gemini는 각 프로그램이 요금제에 맞춰 고르는 기본 모델을 쓴다(`YEONE_OCR_CHATGPT_MODEL`, `YEONE_OCR_GEMINI_MODEL`로 바꿈). Gemini CLI에는 응답 스키마 옵션이 없어 지시문에 스키마를 넣고 받은 답을 JSON으로 검사한다.
- 기본 설정(쪽 판독 prefer, 4구간씩 1024화소 조각, 확신한 제안 반영)은 Claude로 잰 것이다. ChatGPT·Gemini에서의 정확도는 아직 재지 않았다.

**한도에 닿으면 다른 구독 → API 키**

- 실행 중에 구독의 사용량 한도에 닿거나 로그인이 풀리거나 프로그램을 실행할 수 없으면, 같은 요청을 로그인된 다음 구독으로 다시 보낸다. 이번 실행에서 실패한 구독은 건너뛴다. 쪽 판독과 검증이 한 연결을 같이 써서 함께 넘어간다.
- 쓸 수 있는 구독이 하나도 남지 않으면 **바로 API 키로** 넘어간다 — 설정에서 고른 제공사·모델·키로, 이번 실행 API 호출은 「로컬 뒤 AI 검증」의 횟수(`--local-ai-max-calls`, 기본 20)까지(쪽 판독과 검증 합산). 처음부터 로그인된 구독이 없을 때도 키가 있으면 키로 검증한다.
- API 키도 없거나 상한에 닿으면 AI 작업을 멈추고 결과와 검증 대상을 저장한다. 넘어갈 때마다 진행 기록에 적는다. API 요금을 쓰지 않으려면 `--no-local-ai-api-fallback`(예전의 구독 전용 동작).

**검증**: Linux 가상 화면(Xvfb, Tk 8.6, Python 3.12)에서 `tests/` 전체 — 2,161개 통과 · 225개 건너뜀 · 실패 0개. 새 시험은 가짜 CLI로 명령 인자 · API 키 제외 · 토큰 파일 미열람 · 오류 안내 · 계정 순서 · 다른 구독으로 넘어가기 · API 키로 넘어가기 · 키 없을 때 멈춤을 본다. 실제 codex-cli 0.167.2 · gemini-cli 0.68.0으로 인자 해석과 로그인 단계 도달까지 확인했으나, 이 환경의 네트워크 제한으로 로그인된 계정의 실제 호출은 하지 못했다. # 연어OCR 1.2.1 · 간단한 화면 · 메모 없는 문서 · 정리된 결과 폴더

1.2.0을 갱신하는 판이다. 1.2.0의 기능(세로쓰기 GPU 판독, Claude 구독 판독, 한국 표준 한자 모양, 단순 표시, 속도 개선)은 그대로 두고, 화면을 단순하게 고치고, 일반·이미지 OCR 문서에 메모를 넣지 않는 것을 기본으로 하고, 결과 폴더 맨 위를 정리했으며, 비교 프로젝트 저장을 빠르게 했다.

**화면**

- **명령 띠 한 줄**: 예전의 두 줄 머리띠(탭 넷 · 판 번호 · [업데이트 확인] + 둘째 줄 [OCR 모델 비교·교정])를 한 줄로 줄였다. 왼쪽에 **[일반 OCR]·[책갈피 OCR]·[이미지 OCR]** 알약 탭, 오른쪽에 **자세히** 미닫이 · **[설정]** · **[더 보기]** 메뉴를 둔다. [더 보기]에는 OCR 모델 비교·교정 · 비용 미리 보기 · 자세히 보기 · 고급 도구 · 도움말 · 업데이트 확인 · 패키지 점검 · 판 번호가 모여 있다.
- **간단히 보기(기본)**: 작업 탭에는 원본·쪽 범위 → 실행 → 진행(막대·단계 이름·쪽 띠) → 결과만 남긴다. '이 책의 설정' 판, 결과 저장 줄, 단계별 설명 줄, 비용 장부, 고급 도구, 책갈피 탭의 긴 안내문은 **자세히 보기**에서 본다. 쪽 범위는 두 보기가 같은 값을 쓴다.
- **설정 탭**: 간단히 보기에서는 왼쪽 갈래(판독 · 이 책 · 문서 만들기 · 자동 교정 · 모델 단계 · 책갈피 교정)에서 고른 섹션 하나만 보인다. 자세히 보기에서는 이전처럼 모든 섹션을 두 열(좁으면 한 열)로 펼친다.
- **결과 단추**: 실행 카드 안에 '결과' 구역을 나누고 [모델 비교·교정]을 [나란히 대조 편집] 옆에 두었다.
- **모양**: 종이·먹·인주 색을 차가운 중립 바탕 · 흰 카드 · 짙은 남색 명령 띠 · 남보라 강조색으로 바꿨다. 주 실행 단추 · 켜진 체크 · 진행 막대 · 단계 동그라미 · 쪽 띠의 '끝남·지금'이 같은 강조색을 쓴다. 대비는 본문 7:1 · 강조색 위 흰 글 6:1 이상을 지킨다. 구획 편집기 · 이미지 미리보기의 바탕색도 같은 색 체계로 맞췄다.
- 보기 선택은 설정 파일의 `simple_view`에 남는다(없으면 간단히 보기). 기존 설정 파일의 다른 값은 건드리지 않는다.
- 1.2.0의 문서 표시 선택(단순 표시)과 로컬 우선 설정(두 단 순서, 줄 다시 확인, EasyOCR, Claude 구독)은 설정 탭의 각 갈래에 그대로 있다.

**문서와 결과 폴더**

- **일반·이미지 OCR 문서도 기본은 색상만 표시(메모 없음)**: 책갈피 OCR(0.12.5)처럼 일반·이미지 OCR의 HWPX·DOCX(표준 표시)에도 기본으로는 한컴 메모와 글 속 고지를 넣지 않는다. 1.2.0의 **단순 표시**(`--display simple`, 괄호를 접고 형광 바탕·글자색만)는 그대로 선택으로 남고, 이 항목은 기본인 표준 표시의 메모만 바꾼다. 등급 색과 〔 〕 표기는 그대로이고, 고지(본문에 표시되지 않은 확인 항목 · 구조 검사 오류 · 로컬 인식 의심 구간)는 검수 화면(review.html)과 보고에서 본다. 이전에는 의심 구간이 있는 쪽마다 "[본문에 표시되지 않은 확인 항목] 로컬 인식 의심 구간의 AI 검증·수정 제안을 비교·교정 창에서 확인하세요" 메모가 하나씩 붙었고, 1.2.0에서 신뢰도 단위를 바로잡은 뒤로 그런 쪽이 크게 늘어 메모가 쪽 수만큼 쌓였다. [설정] → 문서 만들기 → 메모에서 '고지 사항만 메모' · '모든 표시에 메모' · '메모 없이 글 속 〔…〕'를 고르면 이전 방식으로 만든다. 저장된 설정의 이전 기본값(고지 사항만 메모)은 한 번만 색상만으로 옮기고, 그 뒤 다시 고른 값과 '모든 표시에 메모' · '글 속'은 보존한다. 명령줄 `--memo`의 기본도 `none`이다(이전 `notice`).
- **결과 폴더 맨 위는 셋만**: `<이름>_YeonE_OCR` 맨 위에는 `out`(문서) · `review.html`(검수 화면) · `report.md`(보고)와 `작업자료` 폴더 하나만 둔다. 판독 기록·쪽 이미지·글자층·도판 조각·비교 프로젝트·복구본·책별 설정·문맥·혼동 장부·교정 기록·이전 결과 보관(archives)은 모두 `작업자료` 안에 생긴다. 검수 화면의 그림은 `작업자료/pages`를 가리킨다.
- **이전 판의 결과 폴더**: 작업 자료가 맨 위에 펼쳐진 폴더는 저절로 옮기지 않고 그 자리에서 이어 쓴다(원본을 고르면 진행 기록에 안내 한 줄). **[더 보기] → [결과 폴더 정리…]**를 누르면 묻고 나서 `작업자료` 하나로 옮긴다 — 같은 폴더 안의 이름 바꾸기라 판독 기록을 다시 사지 않고, 하나라도 옮기지 못하면(다른 프로그램이 파일을 쥠) 모두 제자리로 되돌린다. 옮긴 뒤 검수 화면은 모델 호출 없이 다시 만든다. **옮긴 결과 폴더는 1.1.0 이하 판이 판독 기록을 찾지 못한다**(그 판으로 열면 처음부터 다시 판독).
- 명령줄에서 `--work` 로 이름이 `작업자료`가 아닌 폴더를 주면(기본 `work/<이름>` 포함) 그 폴더 하나에 이전처럼 모두 둔다.

**인식·저장**

- **공백만 다른 엔진 불일치는 자동으로 보내지 않는다**: 줄바꿈·띄어쓰기만 다르고 글자가 같은 불일치는 자동 선택 검증의 유료 호출 대상에서 뺐다. 비교·교정 창의 제안은 그대로 남고, 직접 골라 검증을 요청하면 이전처럼 보낸다.
- **비교 프로젝트 저장이 빨라지고 파일이 작아진다**: 저장할 때마다 전체를 복사하고 들여쓰기해 쓰고 기존 파일을 두 번 다시 읽던 것을, 복사·들여쓰기 없이 쓰고 기존 파일은 바이트가 그대로면 다시 읽지 않게 했다. 53.6MB 합성 프로젝트에서 저장 한 번 3.76초 → 0.43초, 파일 크기 34%. 예전(들여쓰기 있는) 프로젝트는 그대로 열리고 다시 저장하면 새 형식이 된다. 저장되는 값과 "다른 창에서 변경됨" · "다른 프로젝트" 보호는 같다.
- 신뢰도 단위(0–100) 수정은 1.2.0과 같은 값(85 · 55 · Tesseract 70)으로 합쳤다. 실제 워커의 출력 그대로 저신뢰 구간이 대상에 오르는지 보는 시험을 더했다.
- 오프라인 SDK 시험이 각 SDK가 실제로 쓰는 HTTP 모듈(httpx 또는 httpx2)을 쓰도록 고쳤다(최신 openai·anthropic·google-genai 에서 수집이 멈추던 문제).
- 1.1.0 소스를 읽고 정리한 인식률·속도 개선 방안(일부는 1.2.0에 이미 들어감 — 쪽 그림 한 번 그리기, 엔진 상주, 두 단 순서, 세로쓰기 GPU 엔진)은 [인식률·속도 개선 방안(1.1.0 기준)](인식률_속도_개선_방안_1.1.0.md)에 정리했다.

**검증**: Linux 가상 화면(Xvfb, Tk 8.6, Python 3.12, `packaging/requirements-windows.lock.txt` 버전의 패키지)에서 `tests/` 전체를 돌렸다 — 결과는 아래 「검증 수치」. Windows 설치판·실제 OCR 엔진·실제 API 로는 이 환경에서 확인하지 못했다(배포 CI 의 Windows 회귀·설치 검사가 첫 확인이다). 실패 1건(`test_bookmark_section_editor` 의 지연 표시 시험)은 1.1.0 소스에서도 같은 환경에서 실패한다.

검증 수치: 배포 잠금 버전 2,336개 통과 · 29개 건너뜀 · 1개 실패(위의 기존 실패) · `ruff check yeone_ocr ab_ocr tools --select E9,F63,F7,F82` 통과. `requirements.txt` 의 최신 패키지(openai 3.49 · anthropic 2.8 · google-genai 3.2)로는 2,141개 통과 · 225개 건너뜀(화면 시험 등) · 실패 0개.

# 연어OCR 1.2.0 · 세로쓰기 GPU 판독, Claude 구독 판독, 한국 표준 한자 모양

1.1.0을 갱신하는 후속 버전이다. 로컬 우선 인식의 정확도·속도·표시를 개선하고, PC에 로그인된 Claude Code(Claude 구독)로 쪽 판독과 어려운 구간 검증을 하는 경로를 더했다. 전체 구성은 [연어OCR 구성 정리](연어OCR_구성_정리.md), 옵션과 측정 기록은 [로컬 우선 안내](LOCAL_FIRST.md)에 있다.

- **Claude 구독 판독(로그인되어 있으면 자동)**: 공식 Claude Code(`claude -p`)를 실행만 하며 로그인 토큰을 읽거나 저장하지 않는다. 쪽 전체를 원래 해상도 띠로 잘라 처음부터 읽고 엔진 판독과 맞춰 짧은 차이는 AI 글자(초록), 부호·AI가 불확실하다고 한 낱말·긴 차이는 엔진 글자(빨강)로 둔다. 어려운 구간은 원래 해상도 조각과 함께 다시 본다. API 요금 없이 구독 사용량에서 차감되며 개인 사용 전용이다. 설정 「Claude 구독 판독」 또는 `--local-ai-page off --local-ai-auth api`로 끈다.
- **세로쓰기에도 GPU 엔진(Surya)**: 한글·한자 혼용 세로쓰기 6쪽 표본에서 Tesseract 단독 CER 34.44% → Surya 2.39% → 쪽 번호 분리 뒤 1.53% → Claude 구독 판독 0.76%(글자 모양 차이 제외 0.4%).
- **한국 표준 한자 모양(기본)**: 한글·한자 혼용 문서는 KS X 1001에 없는 모양을 그 안의 짝으로 맞춘다(説→說, 真→眞, 即→卽 등 286쌍). 한국 책에 쓰이는 글자는 바꾸지 않는다.
- **표시·정리**: 메모 없이 형광 바탕 + 빨강·파랑·초록 글자로 불확실 글자 표시(단순 표시), 인쇄된 쪽 번호를 본문에서 분리, 가로쓰기 두 단 본문은 왼쪽 단부터.
- **속도**: 쪽 그림 한 번만 그리기, 엔진 상주·동시 실행, GPU 세션 전용 스레드, 줄 다시 확인 기본 끔(의방집해 152.8 → 96.9초/쪽), 가로쓰기 EasyOCR 기본 끔.
- **의심 구간 AI 검증 수정**: 엔진 확신도 단위(0~1/0~100) 혼동을 고치고, 확신도 없는 엔진은 블록 단위로 한 번만 보내며, 보류 이유를 로그에 남긴다.
- **측정 도구** `tools/compare_local_options.py`: 정답 파일과 짝지어 세트별 CER(전체·부호 제외·글자 모양 무시), 오류 목록·AI 제안 목록을 만든다.

측정은 사용자 PC(RTX 4060)에서 실제 문헌으로 한 것이며 표본 쪽수가 적다. 소스 회귀 검사는 tkinter 화면 검사를 포함해 실행했고(가상 화면에서 원래부터 실패하는 화면 검사 1건 제외 전부 통과), 빌드·설치·업그레이드(1.1.0에서) 검증과 공개 게시는 배포 CI 결과로 확인한다.

# 연어OCR 1.1.0 · 로컬 먼저, 어려운 구간만 AI 검증

최신 배포판 1.0.6을 갱신하는 후속 버전이다. 배포 저장소의 저장·교정 보완을 통합한 소스를 기준으로 빌드·업그레이드를 검증하며, 개발 저장소의 이전 0.11.0 이력과 구분한다.

일반 OCR·이미지 OCR·CLI `run`의 기본 경로를 **로컬 인식 → 불일치·어려운 구간만 AI 검증 → 문서·검수 화면·보고**로 연결했다. PP-OCRv6 단독 판독도 검증할 수 있고, 위험 신호가 없는 결과는 API를 호출하지 않는다. 이전 전체 쪽 AI 판독은 설정 또는 `--ocr-strategy ai-full`로 선택한다. [새 흐름과 사용법](LOCAL_FIRST.md)

- 낮은 엔진별 confidence, 알 수 없는 글자, 엔진 불일치·누락을 이미지 크롭과 제한된 문맥으로 검증한다. confidence는 정확도가 아니며 엔진 간 비교에 사용하지 않는다. 좌표를 안전하게 연결하지 못한 곳은 검수 대기로 남기고 전체 쪽 API 판독으로 확대하지 않는다.
- 원시 OCR·AI 응답·수정 제안·사람의 채택·기각을 구분해 보존한다. AI 제안을 자동으로 본문에 덮어쓰거나 사람의 검수 완료로 표시하지 않는다.
- 선택 구간 API 호출은 실행 전체 기본 20회이며 공통 `--max-calls`도 적용한다. 호출 상한만 바뀌어도 완료한 답을 재사용한다. 키가 없거나 검증을 마치지 못해도 로컬 결과를 저장하고 대기 상태를 알린다. 로컬 전용 실행도 지원한다.
- 로컬 결과를 기존 HWPX·DOCX·검색 PDF와 검수·상태 보고에 연결한다. 이미지 묶음 입력, 중지·재개, 설정·진행 화면과 비교 프로젝트 열기를 포함한다.

# 연어OCR 1.0.4 · 일반·이미지 OCR 대조 편집과 교정 색상 일치

- 교정 HWPX에 저장된 글자 색·배경색·굵게·밑줄을 읽어 대조 편집창에 표시합니다. 글자가 원본과 같아도 확인 표시는 유지합니다.

- 기존 저장 오류 수정, 구획 전체 복사, 본문 내보내기, 수동 수정 기록과 원본 보존을 유지합니다.

# 연어OCR 1.0.1 · 대조 편집 저장·복사와 찾기·바꾸기

책갈피 대조 편집에서 줄바꿈·탭 때문에 저장이 막히는 상황을 바로잡고, **찾기·바꾸기(Ctrl+H)**를 추가합니다. 예를 들어 `皰`를 찾아 `疱`로 한 번에 바꿀 수 있습니다.

- 현재 문단·현재 구획·문서 전체에서 바꿀 범위를 선택합니다. 변경 건수와 수정 전후를 확인하고 적용한 다음 **변경 확인·저장**으로 기존 교정본에 저장합니다.
- 제목·책갈피·필드 등 편집할 수 없는 문단은 제외하고 건수를 알립니다. 현재 창에서 이미 수정한 내용도 함께 보존하며, 미리보기나 적용만으로 파일을 덮어쓰지 않습니다.
- 문단 편집 중 실수로 줄바꿈·탭이 들어가지 않도록 입력을 처리합니다. 붙여넣기나 기존 입력에 줄바꿈·탭이 있으면 내용을 확인하고 공백으로 정리할 수 있습니다. 임의로 본문 글자를 삭제하지 않습니다.
- 저장할 수 없는 입력은 해당 문단과 위치를 안내합니다. 저장 실패 때 입력 내용이 창에 남으며, 기존 교정본과 수동 교정 기록은 유지됩니다.
- 오른쪽 교정문에서 선택한 글자는 **Ctrl+C** 또는 **마우스 오른쪽 버튼 → 복사**로 복사합니다. 저장 전 수정한 내용도 복사하며, 복사 작업은 본문과 저장 상태를 바꾸지 않습니다.
- 직접 고친 글자의 교정 표시 제거, 수정 사례 기록, 저장 전 사본, 외부 변경 확인을 유지합니다.

검증은 문단 입력·붙여넣기·찾기·일괄 바꾸기·수정 취소와 저장·재열기, 본문·서식·수동 수정 기록 보존 검사, 실행 파일 자체 검사, 1.0.0에서의 업그레이드·재설치·제거 확인으로 구성합니다. 최종 결과는 공개 릴리스 검증 기록에 남깁니다.

# 연어OCR 1.0.0 · 사람이 고친 글자의 교정 표시 정리

앱·설치판·포터블의 버전을 **1.0.0**으로 맞춥니다. 책갈피 대조 편집에서 직접 고친 글자를 저장하면 해당 글자의 OCR 교정 색상·배경색·밑줄 등을 제거하고 원래 문서의 글자 서식으로 되돌립니다.

- 한 문단에 글꼴·크기·강조 등 여러 서식이 섞여 있어도 사람이 수정한 글자의 표시를 정리합니다. 아직 수정하지 않은 글자의 OCR 표시는 유지합니다.
- 원래 문서에 있던 글꼴·크기·색상·강조는 보존합니다. 원래 서식을 안전하게 확인할 수 없는 경우에는 저장을 중단하고 서식별로 나눠 수정하도록 안내합니다.
- 수정 내용은 기존 `_교정.hwpx`에 저장하고, 저장 전 사본·외부 변경 확인·수동 수정 문단 보호와 `.manual.json` 수정 사례 기록을 유지합니다.
- 색상만 교정 표시, 기존 앱 메모 정리, 원본 PDF 커서 따라가기·글자 크기 맞춤 기능을 이어서 제공합니다.

이번 버전에서 저장하는 수정부터 적용합니다. 기존 파일에 남아 있는 표시를 버전 업데이트만으로 일괄 제거하지는 않습니다.

검증은 여러 서식이 섞인 문서의 수정·저장·재열기와 원문 및 수정 기록 보존 검사, 실행 파일 자체 검사, 0.12.5에서의 업그레이드·재설치·제거 확인으로 구성합니다. 최종 결과는 공개 릴리스 검증 기록에 남깁니다.

# 연어OCR 0.12.5 · 색상만 교정 표시와 기존 앱 메모 정리

책갈피 OCR의 기본 표시를 **색상만 표시**로 바꿉니다. 메모나 본문 설명을 새로 넣지 않고 초록(3차 자형 판별 근거)·파랑(자동 교정, 확인 권장)·빨강/노랑(원본 확인 필요)으로 구분합니다. 원래 글자·삽입 제안·근거 전체는 보고서에 남깁니다.

- 삭제 자리와 폭 없는 삽입 제안은 가까운 실제 글자에 표시합니다. 표시할 글자가 없는 항목은 보고서에 남기며, 표시를 위해 본문 글자를 추가하지 않습니다.
- **기존 앱 메모 정리** 버튼으로 기존 교정본의 앱 교정 메모를 한 번에 정리합니다. OCR 호출 없이 동작하며 정리 전 `.bak.hwpx` 사본을 만듭니다.
- 본문·서식·색상·책갈피·사용자 메모·일반 OCR 메모와 사람이 수정한 문단의 보호·수정 사례 기록을 보존합니다. 손상되거나 소유권이 불확실한 메모는 남기고 알립니다.
- 기존 기본 메모/글 속 설명 설정은 한 번만 새 기본값으로 옮깁니다. 명시적으로 선택했던 모든 메모 방식과 이후 사용자가 다시 고른 방식은 유지합니다. 일반 OCR 설정은 바꾸지 않습니다.
- 과거에 본문 글자로 넣은 `〔…〕` 설명은 메모 정리 버튼으로 지우지 않습니다. 기존 메모 방식도 설정에서 다시 선택할 수 있습니다.

검증은 합성 문서의 색상 표시·메모 정리·원문 및 사람 수정 기록 보존 검사, 실행 파일 자체 검사, 0.12.4 업그레이드·재설치·제거 확인으로 구성합니다. 최종 결과는 공개 릴리스 검증 기록에 남깁니다.

# 연어OCR 0.12.4 · 사람 수정 사례 기록과 다음 판독 참고

책갈피 대조 편집에서 사람이 글자를 고치고 저장하면 수정 전후 본문·문단·구획·시각을 교정본 옆 `.manual.json`에 함께 보관합니다. **수정 기록 보기**에서 저장된 이력을 확인할 수 있습니다.

- 같은 PDF의 다음 새 1차 판독에 최근에 저장한 유효한 짧은 수정 사례부터 최대 24개와 문맥을 전달합니다. 한자를 한글로 오인식한 뒤 사람이 바로잡은 경우도 기록합니다. 실제 글자는 원본 이미지로 확인하도록 안내하며 2차·3차 판독은 사례를 전달하지 않고 독립적으로 진행합니다.
- 되돌린 교정, 저장 실패로 문서에 반영되지 않은 내용, 상충하는 사례와 다른 PDF의 사례는 참고에서 제외합니다. 삽입·삭제·긴 수정도 이력에는 남기지만 짧은 글자 치환 사례만 판독에 보냅니다.
- 기존 완료 판독은 그대로 재사용합니다. 사례가 추가되었다고 자동으로 유료 재판독하지 않습니다. 새 쪽 판독이나 명시적 재판독부터 참고하며, 부분 재개에서는 실제 1차 판독에 사용했던 사례의 출처를 유지합니다.
- 이전 버전의 해시 기반 문단 보호는 유지합니다. 그 기록만으로는 실제 수정 전후를 알 수 없어 사례를 소급 생성하지 않습니다. 이 버전에서 저장하는 수정부터 전후 기록이 쌓입니다.
- 원본 보존·저장 전 사본·외부 변경 확인·수동 교정 문단 보호를 유지합니다. 사례는 교정본 옆에 저장되며, OCR 실행 시 선정된 짧은 사례만 선택한 판독기로 전달됩니다.
- 대조 편집 창을 처음 열 때 Windows 테마의 분리선 두께를 반영해 좌우 패널 너비를 균등하게 맞춥니다. 사용자가 이후 조절한 분할 비율은 유지합니다.

이 기능은 저장한 수정 사례를 판독에 참고시키는 방식이며 모델 가중치를 재학습하지 않습니다. 실제 인식률 개선 수치는 별도 평가가 필요합니다. 배포 검증은 수정 기록·재개·기존 교정 보존 회귀 검사, 실행 파일 자체 검사, 0.12.3 업그레이드·재설치·제거 확인으로 구성합니다.

# 연어OCR 0.12.3 · 대조 편집 커서 연동과 글자 크기 맞춤

책갈피 OCR 대조 편집에서 오른쪽 커서의 위치를 왼쪽 원본 PDF에 표시합니다. PDF의 화면상 글자 폭에 맞춰 교정문 글자 크기를 조절하고 대응 글자를 양쪽 화면의 비슷한 높이에 배치합니다.

- **커서 따라가기**가 기본으로 켜집니다. 클릭·방향키·입력으로 커서를 옮기면 대응 PDF 쪽과 줄을 찾습니다. 노란색은 대응 줄, 테두리는 확인된 글자 위치입니다.
- **PDF 글자 크기 맞춤**이 기본으로 켜집니다. PDF 확대·축소와 창 너비 변경에 맞춰 오른쪽 글자 크기도 바뀝니다. **가− / 가+**로 직접 조절하면 자동 맞춤이 꺼지며, 체크하면 다시 맞춥니다.
- 커서가 있는 줄의 화면 높이를 맞추고 오른쪽 스크롤을 따라갑니다. PDF와 HWPX는 줄바꿈·문단 구조가 달라 가로 위치와 전체 지면 배치까지 같아지는 것은 아닙니다.
- 반복 문장은 구획 문맥으로 확인합니다. 새로 입력한 글자 등 대응이 없는 위치는 주변 문맥만 표시하며, 모호하거나 글자층이 없는 PDF에는 임의의 정확한 글자 표시를 하지 않습니다. PDF 글자층은 위치 안내용이며 자동 교정 근거로 추가 사용하지 않습니다.
- 직접 PDF 쪽을 바꾸면 자동 이동을 멈추고, 오른쪽 커서를 다시 움직일 때 따라갑니다. **커서 따라가기**를 꺼서 자유롭게 탐색할 수 있습니다.
- 위치 표시·크기 맞춤은 문서나 서식을 바꾸지 않습니다. 기존 교정본 저장, 저장 전 사본, 외부 변경 확인과 사람 수정 보호는 유지됩니다. 추가 OCR 호출 없이 동작합니다.

배포 검증은 오프라인 회귀 검사, 소스·설치용 실행 파일·포터블의 커서 연동 자체 검사, 깨끗한 Windows에서 0.12.2 업그레이드·재설치·제거 확인으로 구성합니다. 최종 검사 결과는 공개 릴리스 검증 기록에 남깁니다.

# 연어OCR 0.12.2 · 책갈피 OCR 나란히 대조·편집

책갈피 OCR에서 선택한 구획의 원본 PDF와 현재 교정문을 한 창에 나란히 표시합니다. 오른쪽 문단을 직접 수정하고 변경 내용을 확인한 뒤 기존 누적 교정본에 저장할 수 있습니다.

- **나란히 대조·편집** 버튼과 구획 더블클릭으로 엽니다. 왼쪽은 PDF 쪽 이동·확대·축소, 오른쪽은 문단 편집·원문 차이 표시와 선택 문단 비교를 제공합니다.
- **변경 확인·저장** 또는 `Ctrl+S`로 수정 전후를 확인합니다. 기존 `_교정.hwpx`를 갱신하며, 교정본이 없으면 처음 저장할 때 만듭니다. 수정 전 사본을 보관하고 원본 PDF/HWPX는 유지합니다.
- 저장 전 문서 위치와 파일 변경 여부를 확인합니다. 외부 변경·저장 실패 때 입력한 수정문을 유지하고 덮어쓰지 않습니다. 미저장 내용이 있으면 닫기·다시 불러오기 때 확인합니다.
- 사람이 수정한 문단은 교정본 옆의 `.manual.json` 기록으로 보호합니다. 이후 자동 교정은 해당 문단을 바꾸지 않고 차이를 보고에만 남깁니다. 이 기록은 교정본과 함께 보관해야 합니다.
- 제목·필드 등 수정 위치를 안전하게 확인할 수 없는 문단은 읽기 전용입니다. PDF 쪽과 HWPX 문단은 각각 탐색하며, 문단 추가·삭제나 한글 전체 서식 편집은 지원하지 않습니다. 과거 OCR 보고와 메모는 작성 당시 기록으로 남습니다.

배포 검증은 오프라인 회귀 검사, 소스·설치용 실행 파일·포터블의 자체 검사, 깨끗한 Windows에서 0.12.1 업그레이드·재설치·제거 확인으로 구성합니다. 실제 검사 결과는 공개 릴리스 검증 기록에 남깁니다. 이번 기능은 문서 대조·수동 편집이며 OCR 모델의 정확도 향상을 의미하지 않습니다.

# 연어OCR 0.12.1 · 책갈피 구획 선택과 결과 확인 개선

책갈피 OCR에서 같은 위치의 책갈피·제목이 두 번 나타나거나, PDF 본문의 앞선 언급을 구획 시작으로 잘못 찾던 문제를 수정합니다. 선택한 구획의 교정 실행과 결과 확인을 구분합니다.

- 같은 문단의 책갈피와 제목 스타일을 한 구획으로 합치고 제목 계층을 유지합니다. 전체 교정에서 같은 위치를 중복 처리하지 않습니다.
- PDF 책갈피가 없는 구획은 본문 제목과 주변 범위를 확인합니다. 첫 문자열 등장만으로 엉뚱한 구획을 자동 선택하지 않으며 확인할 수 없으면 쪽 범위를 직접 지정하도록 안내합니다.
- 선택 구획의 이름·PDF 범위·HWPX 내용을 확인할 수 있고, 행 더블클릭은 결과 확인/미리보기로 동작합니다. 교정 재실행은 별도 실행 버튼으로 구분합니다.
- 구획 결과는 원본 문서와 구획 위치에 연결합니다. 가장 최근에 수정된 다른 구획의 보고를 열거나 같은 이름의 보고를 덮어쓰지 않습니다. 확인 가능한 기존 보고도 조회할 수 있습니다.
- 파일·제목 스타일·색인 기준이 바뀌면 기존 선택을 갱신해야 합니다. 실행 전 구획 이름과 시작 문단을 다시 확인합니다.

AI의 원시 응답·제안과 프로그램의 보호 판정, 사람이 확정한 이력을 분리한다. 과거 확정 이력은 소급 변경하지 않으며 보류 사유를 편집기에 표시한다. 선택한 번체 편집은 이미지 판독과 별도로 유지한다. 신규 요청은 `comparison-ai-v8`, 보호 정책은 `source-fidelity-v1`이며 저장 후 다시 열 때 원시 OCR 근거와 판정도 검증한다.

같은 PDF 3종의 기존 120개 범위·원시 OCR·실제 v7 AI 응답을 그대로 재적용했다. 공백 제외 한자 오류는 종전 AI 단계 578→542(원시 571), 전체 CER는 10.6721→10.6134%다. 순수 AI 완료 99개 범위에서 맞던 한자 손상은 89→0, 오교정 제안은 180→94이고 잔여 손상은 부호 93자다. 기존 도움 제안 45개도 보류되어 번체 한자 오류는 279→282로 소폭 악화했으며, 전체 CER는 로컬 후보만 적용한 10.2734%보다 여전히 높다. 미완료 21개의 기존 대체 결과는 그대로다. 평가용 정답을 추론에 사용하지 않았으며 이번에 새로운 유료 API·GPU 인식을 실행하거나 사람의 확정 이력을 만들지 않았다. 신규 v8 프롬프트 자체의 실제 유료 효과는 이 재적용 평가로 입증하지 않는다.

개인 평가 보고서와 원형 3,789파일 보존·독립 수치 감사는 `work/ocr-safety-replay-v2`에 둔다. 이전 시도 `work/ocr-safety-replay-v1`은 채점 전 합성 경계 문제를 발견한 기록으로 보존한다. 이번 변경은 개발 소스에 반영한 것이며 기존 설치 파일 교체나 GitHub 신규 배포를 의미하지 않는다.

최종 회귀 검사는 **80개 모듈·고유 테스트 1,331개 통과**, 실패·오류·건너뜀·미완료 0개다(`work/ocr-safety-replay-v2/regression-final/summary.json`). 세로 읽기·책갈피·이미지 OCR의 기존 검사와 신규 원본보존·채택 차단·재열기·원시 보존 검사를 포함한다. 소스 실행 자체 검사 27개와 전체 런타임 Ruff `E9,F63,F7,F82`도 통과했다. 네트워크를 차단한 기능 검사이며 실제 정확도는 위 재적용 평가와 구분한다.

# 연어OCR 0.11.0 · 교정 후보와 영역 재판독·GPU 작업 관리

원본 대조 편집기의 **로컬 교정·영역** 탭에서 GLM의 한자 차이와 EasyOCR의 부호 차이를 교정 후보로 만들고, 선택한 범위 또는 어려운 한글·한자 영역 두 개를 다시 읽는다. 실제 OCR 좌표와 양쪽의 유일한 원문을 확인할 수 있을 때만 대응하며, 사람이 수정한 자리를 덮어쓰거나 GLM에 글자 좌표를 만들어 넣지 않는다. 기존 세로 읽기·책갈피·이미지 OCR과 여섯 엔진 비교·기존 기준 판독은 유지한다.

영역 계획은 원본·렌더링·잘라낸 이미지·부모 판독·모델 설치·실행 환경·장치를 고정한다. `runs`, `region_readings`, `refinement_reviews`, `ai_reviews`, 사람의 결정과 `edits`를 구분한다. 완료·미완료·실패 원시를 보존하고 사용자가 채택해야 교정문이 바뀐다. 과거 요청의 미확정 근거도 저장·재열기에서 검증한다.

GPU 작업은 Windows 공통 FIFO에서 취소 가능하게 기다린다. 모델별 연속 쪽·영역 처리는 GLM·Surya·Paddle 전용 작업자·서버를 재사용하고, 기본 8회 뒤 임대를 반납한다. 페이지 사이에 대화 문맥을 넘기지 않으며 원시마다 요청·세션·작업자 정보와 고정 조건을 남긴다. 명시 CPU·CUDA가 다른 캐시는 같은 실행으로 재사용하지 않는다. 취소·시간 초과·종료 때 해당 작업이 만든 프로세스만 정리한다.

AI는 미확정 로컬 후보와 영역 원시·확대 이미지를 원본·문맥으로 다시 검증한다. 쪽 전체의 시각 검증을 선택할 수 있고, 간체의 번체 변환 기본값은 꺼져 있다. 이체자·원문 부호를 보존하며 일괄 전각화 같은 편집 양식 교정을 정답으로 강제하지 않는다. 동일 Gemini 모델·기존 120개 평가 범위만 사용한 실제 검증은 개인 작업 폴더 `work/refinement-validation`에 보관하고, HWPX·DOCX 정답은 추론·외부 전송에서 제외한다. 조합·AI 제안을 적용한 평가용 문장과 사람의 확정 이력을 구분하며 정확도 개선과 오교정을 별도로 계산한다.

실제 GPU 합성 A/B/A 아홉 요청에서 세 엔진의 작업자 재사용, GLM·Surya의 서버 재사용, 첫째·셋째 결과 일치와 소유 프로세스 정리를 확인했다. 오프라인 배포 자체 검사는 27개를 통과했다. 정확도 측정은 같은 개발 자료의 결과이며 독립된 새 검증 자료나 세로쓰기·복잡한 표로 일반화하지 않는다. 로컬 산출물과 GitHub 공개 배포 상태는 구분한다.

최종 회귀 검증은 **77개 모듈·고유 테스트 1,290개 통과**, 실패·오류·건너뜀·미완료 0개다. 모듈별 독립 프로세스와 네트워크 차단으로 실행한 증거는 `work/refinement-validation/regression-final-v3`에 보관한다. 실제 같은 평가 범위의 GLM CUDA 영역 재판독 **240회도 모두 완료**했으며, GPU 임대 31개에서 최대 8회씩 처리하고 전용 작업자·서버를 정리했다. AI 이후 정확도는 별도의 완결된 평가 보고서를 따르며 이 회귀 검사 수로 대신하지 않는다.

0.11.0의 전용 빌드 경로는 `work/windows-refinement-0.11.0`, 로컬 설치 파일·포터블·소스와 라이선스 ZIP의 경로는 `dist/0.11.0`이다. 소스·설치용 실행 파일·포터블의 자체 검사와 소스·리소스 일치 증거를 해당 빌드 폴더에 남긴다. 공개 0.9.0과 이전 로컬 빌드는 보존하며 이 기록은 GitHub 신규 게시를 의미하지 않는다.

# 연어OCR 0.10.0 · 로컬 모델 여섯 개와 문서별 주력

PaddleOCR 서버형·GLM-OCR·Surya를 기존 Tesseract·RapidOCR·EasyOCR와 같은 원본 대조 편집기로 연결한다. 권장/기존/전체/주력 모델 묶음, 여섯 원시 탭과 정상 완료 판독 세 개 이상의 AI 비교를 지원한다. 기존 세로 읽기·책갈피·이미지 OCR과 0.9.1의 AI 위치 복원·원시 응답 의미 검증은 유지한다.

같은 문헌의 가로 본문 120단위·공백 제외 정답 66,463자를 비교했다. 한글·한자 귀속 오류율을 최우선으로 혼용 Surya, 번체·간체 GLM-OCR을 새 쪽의 기준으로 선정했다. 번체는 부호를 포함한 전체 CER에서 EasyOCR가 우세하므로 권장 비교에도 유지한다. 수치·정책·범위는 [여섯 모델 비교](LOCAL_ENGINE_COMPARISON.md)를 따른다. 이 개발 자료의 결과를 세로쓰기·복잡한 표나 문헌 전체의 품질로 일반화하지 않는다.

원본·기존 원시 OCR·AI 응답/제안·사람의 교정 이력은 분리한다. 구형 프로젝트의 기준을 자동 교체하지 않고, 주력은 첫 checkpoint에 저장하여 중지·재열기에도 유지한다. 잘린 생성 결과와 실패 원문 증거는 보존하되 교정 근거에서 제외한다. GLM에 가짜 좌표·신뢰도를 만들지 않으며 Surya의 블록 좌표와 원래 HTML을 보존한다.

Windows 작업자는 일시정지 상태로 생성해 전용 Job Object에 연결한 뒤 시작하므로 취소·시간 초과 때 전용 모델 서버도 정리한다. 원자 저장의 일시 공유 잠금은 제한된 시간 안에서 재시도하며 매번 원본·타창 저장·보호 경로를 다시 확인한다. 대규모 런타임 inventory는 설치 manifest에 보존하고 쪽별 기록에는 검증한 지문을 둬 긴 프로젝트의 저장 용량을 줄인다.

개인 문헌·정답·원시 측정·실행 실패/복구 증거는 Git에서 제외한 `work/new-engine-comparison`에 둔다. 최종 비교는 기존 고정 원시 360건과 신규 모델 최종 원시 360건이며, 초기 설치 진단과 혼합하지 않는다. 이번 비교는 외부 AI 호출을 하지 않는다. 모델 가중치·실행 환경·개인 문서는 소스나 배포물에 포함하지 않는다. 로컬 빌드는 `work/windows-multi-engine-0.10.0`, 설치 파일·포터블은 `dist/0.10.0`이며 GitHub 공개 배포 상태와 구분한다.

# 연어OCR 0.9.1 · AI 응답과 교정 위치 처리 수정

AI 검증 요청을 작은 범위로 나누고 출력 예산과 Gemini 3 계열의 낮은 사고량을 명시한다. 단계별 응답 형식으로 시각 판독과 번체·부호 제안을 구분한다. 숫자 위치가 틀린 인용은 같은 승인 대상 내에 정확히 한 번 나타날 때만 검증용 위치를 복원하며, 원래 응답과 복원 근거를 모두 보존한다.

원시 OCR, AI 응답·제안, 사람이 확정한 교정의 저장 구조를 유지한다. 불완전한 응답이나 모호한 인용은 적용하지 않고, 제안이 유효해도 사용자 채택 없이 교정문을 바꾸지 않는다. 기존 공개 0.9.0을 대체해 GitHub에 게시한 것으로 해석하지 않는다.

Gemini 요청의 실제 REST 필드와 응답 형식 호환성을 검사했다. 새 기록은 원시 응답에서 검증용 위치와 제안을 다시 계산하므로, 복원 근거를 삭제하거나 제안만 바꾸고 기록 해시를 다시 계산한 파일도 거절한다. 구형 프로젝트는 이전 계약을 유지한다. 전송 확인창은 본문을 스크롤하고 시작·취소 버튼을 고정해 작은 화면에서도 조작할 수 있다.

사용자 문헌 3종의 재평가는 앞서 고정한 본문 118쪽·혼용 2영역의 원시 판독 360건을 재사용한다. AI 입력에는 원본 이미지와 OCR 문맥·문자 위치표만 포함하고 HWPX·DOCX 정답은 보내지 않는다. 단계별 오류율과 실패 시도·원시·사람 이력 보존 증거는 개인 문헌을 포함하므로 Git에서 제외한 `work/ai-review-fix-validation/report`에만 보관한다. 합성 자료로 진행한 실제 앱·SDK 오프라인 교정·채택·되돌리기·재열기 검증과 실제 유료 문헌 정확도는 구분한다.

로컬 설치 파일·포터블 출력 위치는 `dist/0.9.1`이며 빌드·코드 동일성 검사는 `work/windows-ai-review-0.9.1`에 보존한다. 기존 0.9.0 설치 파일과 이전 평가 자료를 덮어쓰지 않는다.

## AI 검증 흐름

기존 **설정**에서 Gemini·OpenAI·Claude 중 제공사·이미지 입력 모델·API 키를 선택합니다. 원본의 세 로컬 엔진 판독을 완료하고 **3엔진 비교·교정 → AI 검증**을 실행합니다. 대상 쪽·번체자·부호 정책과 요청 상한을 지정하고, 실제 전송 계획의 제공사·모델·원본·쪽·이미지·호출 수를 확인합니다. 범위를 준비하거나 설정 창을 여는 동작은 API를 호출하지 않습니다.

첫 단계는 불일치 위치를 원본 이미지와 엔진별 판독·문맥으로 검증합니다. 다음 단계는 선택한 문장 범위의 번체자·중문부호를 검사하며, 일반 쪽 범위에서는 세 엔진이 같은 글자로 읽은 부분도 검사합니다. 앞 단계의 판독은 잠정 AI 근거로 구분합니다. 세부 범위는 전송 계획에 표시합니다. [AI 검증 사용·저장 정책](AI_REVIEW.md)

원시 OCR은 `runs`, AI 요청·응답·제안은 `ai_reviews`, 사람의 채택·기각·되돌리기는 `ai_decisions`와 `edits`에 구분해 보존합니다. 원본 변경·이미지 좌표·수정 전 문자열·원시 판독 지문을 확인하고, 오래되거나 불확실한 제안을 현재 교정문에 적용하지 않습니다. 이체자·호환 한자·변형 선택자를 임의로 정규화하지 않습니다.

각 요청이 완료될 때 저장·복구 사본을 만들고 동일한 조건의 완료 기록은 재사용합니다. 호출 실패·거절·잘못된 응답은 성공한 교정으로 처리하지 않습니다. SDK 자동 재시도·다른 제공사나 모델 시험·환경 키 자동 선택을 사용하지 않고 승인한 작업의 호출 상한을 적용합니다. API 키와 이미지 Base64 본문은 프로젝트나 배포물에 넣지 않습니다.

개발 검증에는 사용자 API 키나 문서를 외부에 보내지 않습니다. 모의 공급사 응답으로 동작을 검증하며 실제 유료 AI의 인식 정확도와 구분합니다. 세 제공사의 실제 SDK 직렬화와 OpenAI의 거절 응답 보존도 네트워크를 차단한 메모리 HTTP 전송으로 검사했고, 개발 환경과 배포용 격리 환경에서 각각 4개 검사를 통과했습니다. 새 배포 파일은 `dist/0.9.0`, 빌드·검증 기록은 `work/windows-ai-0.9`에 둡니다. 이전 0.8.0 파일은 보존합니다.

# 연어OCR 0.7.4 · Windows

Windows 10/11 x64에서 Python 설치 없이 실행할 수 있는 설치판입니다.

## 이미지 입력을 비우고 다시 시작

세 번째 **[이미지(스크린샷) OCR]** 탭에 **[입력 비우기]**를 추가했습니다. 누르면 선택한 원본·쪽 범위·인쇄 쪽수 보정·강제 재판독과 저장 위치·진행 표시를 초기화하고 새 이미지 입력을 기다립니다. 이어서 **[이미지 고르기…]**로 PNG·JPG 등을 선택하거나 **[스크린샷 붙여넣기]** 또는 `Ctrl+Shift+V`로 새 캡처를 불러오십시오.

입력을 비워도 디스크의 원본 이미지·판독 기록·완성 HWPX와 화면의 진행 기록 이력은 남습니다. 다른 탭의 원본 선택과 API·모델·문서 설정도 유지합니다. 입력을 비우거나 붙여넣는 것만으로 API를 호출하지 않습니다.

## 이미지의 가로·세로 방향 자동 판정

이미지의 읽기 방향은 **자동 판정이 기본**이며 실제 그림의 글줄을 분석해 가로쓰기·세로쓰기를 결정합니다. 일반 OCR·책갈피 OCR의 방향과 이미지용 방향을 각각 기억하므로 PDF 작업에서 고른 방향이 새 이미지에 그대로 적용되지 않습니다.

기존 글자층을 먼저 활용하고, 없거나 부족하면 내 PC에서 이미지의 글줄 간격·배치를 분석합니다. 방향 판정에 추가 API 호출이나 요금은 없습니다. 빈 화면·그림 위주·가로와 세로 근거가 비슷한 경우에는 불확실한 이유를 알리고 세로쓰기 기본값을 사용합니다.

직접 방향을 지정하려면 이미지 탭의 **[설정 바꾸기]**를 눌러 **[읽기 방향]**을 고릅니다. 설정 화면은 현재 작업에 해당하는 방향을 바꾸며, **[설정 저장]·[OCR로 돌아가기]**로 저장하고 작업을 이어갑니다.

판정 근거가 없는 구버전의 세로쓰기 저장값은 이미지 근거가 확실할 때 다시 평가합니다. 완료·부분 판독 기록은 보존하고 자동으로 강제 재판독하지 않으며, 처리 내용은 진행 기록에 안내합니다. 직접 고른 읽기 방향은 유지합니다.

## 기존 작업과 결과 열기

**[일반 OCR]·[책갈피 OCR]·[이미지(스크린샷) OCR]·[설정]**의 네 탭, 원본 선택의 독립성, 공통 API·모델·문서 설정을 유지합니다. **[원본 보기]**로 확인한 뒤 **[한 번에 인식]**을 실행하고, 끝나면 **[HWPX 바로 열기]** 또는 **[저장 폴더]**로 결과를 확인합니다.

캡처의 기본 결과 경로는 `%LOCALAPPDATA%\YeonE_OCR\screenshots\screenshot-<hash>_png_YeonE_OCR\out\screenshot-<hash>.hwpx`입니다. `<hash>`는 캡처마다 달라집니다. 기존 저장 위치와 같은 캡처의 판독 기록을 유지하며, **[HWPX 저장]** 줄에서 실제 전체 경로를 확인할 수 있습니다.

Gemini·ChatGPT(OpenAI)·Claude(Anthropic) 선택, 제공사를 바꿔 중단 작업 이어 읽기, 최종 HWPX·DOCX의 번체·MSR·云/雲 문맥 교정도 유지합니다. 각 제공사의 API 키와 이용 권한이 필요하며 API 이용료는 별도입니다. ChatGPT·Claude 웹 구독과 API는 별개입니다.

## 다운로드와 업데이트

- **설치 권장:** `YeonE_OCR-0.7.4-Setup-x64.exe`를 실행합니다. 현재 사용자 계정에 설치하며 시작 메뉴에 연어OCR을 등록합니다.
- **단일 실행파일 사용자:** `YeonE_OCR-Windows-x64.exe`를 사용합니다. 기존 자동 업데이트용 파일명과 `update.json` 형식을 유지합니다.
- OCR 작업을 마치거나 [중지]로 기록을 저장한 뒤 업데이트하십시오. API 키·설정, 원본 옆 결과 폴더와 저장한 스크린샷은 유지합니다.
