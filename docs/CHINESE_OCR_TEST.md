# 간체·번체 로컬 OCR 비교 자료

기존 Tesseract·RapidOCR(PP-OCRv5 기본 mobile 인식)·EasyOCR와 새 PP-OCRv6 medium을 같은 원본으로 비교합니다. 원시 판독과 교정문은 분리하며, confidence를 엔진 간 정확도 순위로 사용하지 않습니다.

## 테스트 파일 먼저 만들기

소스 폴더에서 Pillow·reportlab이 있는 Python으로 실행합니다.

```powershell
python scripts/create_chinese_ocr_fixture.py
```

기본 출력 폴더는 `output/pdf/chinese_ocr_fixture`입니다. 이 폴더에는 이미지 전용 `chinese_ocr_fixture.pdf`, 쪽별 PNG, UTF-8 정답 텍스트, SHA-256이 포함된 `manifest.json`이 생깁니다. PDF 안에는 검색용 글자층이 없으므로 정답 텍스트 추출로 OCR을 우회할 수 없습니다. 출력 폴더는 Git·배포 소스에 포함하지 않으며 생성 스크립트로 재생성합니다.

1. 간체 가로쓰기: 일반 문장·약재명·숫자·혼동하기 쉬운 한자·간번체 병기.
2. 번체 가로쓰기: 일반 문장·약재명·이체자·중문 부호.
3. 번체 세로쓰기: 위에서 아래로, 오른쪽 열에서 왼쪽 열 순서.

문장은 테스트용으로 직접 작성했으며 의학적 권고나 고서의 인용문이 아닙니다. Windows 기본 SimSun을 이미지로 렌더링하며 폰트 파일은 배포하지 않습니다. 다른 운영체제에서는 `--font`로 로컬 CJK TrueType 폰트를 지정하십시오. 폰트 변경 시 이미지·PDF 지문이 달라질 수 있습니다.

## 화면에서 비교

1. 연어OCR의 **로컬 엔진 비교·교정**에서 생성한 PDF를 엽니다.
2. **엔진 폴더…**와 **설치 확인**으로 모델을 확인합니다.
3. **PP-OCRv6 medium**을 기존 엔진과 함께 선택합니다.
4. 1쪽은 간체·가로쓰기, 2쪽은 번체·가로쓰기, 3쪽은 번체·세로쓰기로 각각 실행합니다.
5. 원시 판독 탭과 정답 파일을 대조합니다. 저장된 비교 프로젝트는 다시 열어 검수할 수 있습니다.

## 정답 대비 오류율 측정

앱 소스와 의존성을 사용할 수 있는 Python에서 실행합니다. 명령 자체는 엔진을 설치하거나 인터넷을 사용하지 않습니다.

```powershell
python -m scripts.benchmark_chinese_ocr --engine-root "C:\OCR엔진"
```

`--engines tesseract rapidocr ppocrv6`처럼 일부 엔진만 지정할 수도 있습니다. 기본은 네 엔진입니다. 완료한 결과는 재사용하고 `--force`로 다시 읽습니다. 없는 엔진은 실패로 기록하며 다른 엔진 결과는 계속 저장합니다.

출력 폴더에 `comparison.yeone-compare.json`과 `benchmark.json`이 저장됩니다. 전자는 앱에서 열 수 있고 후자는 쪽별 엄격한 CER와 공백만 제거한 CER, 삽입·누락·치환 내역, 시간·모델 지문을 포함합니다. 간체·번체·이체자·문장부호는 동일 문자로 접지 않습니다. CER는 낮을수록 좋으며 세로쓰기의 순서 오류도 포함합니다. 시간은 모델 로딩을 포함한 해당 실행의 값으로 일반적인 속도 순위를 뜻하지 않습니다.

이 자료는 깨끗한 합성 글꼴 3쪽의 기능 확인용입니다. 실제 고서·흐린 스캔·희귀 한자 전체에 대한 정확도를 입증하지 않습니다.

## 2026-10-24 재실행 결과 — v6 세로 열 순서 수정 후

같은 PDF·정답 파일·모델과 200 DPI 설정으로 `--force`를 지정해 네 엔진을 모두 다시 실행했습니다. PDF SHA-256은 수정 전과 동일한 `57863bf04cb406ad06e568974c5f57ec86f21da8fa8ddec885350756998a9db5`입니다. 아래는 공백만 제거한 CER(%)입니다.

| 자료 | Tesseract | RapidOCR/v5 기본 mobile 인식 | EasyOCR | PP-OCRv6 medium |
|---|---:|---:|---:|---:|
| 간체 가로쓰기 | 11.76 | 0.59 | 22.35 | 0.00 |
| 번체 가로쓰기 | 11.25 | 3.12 | 28.75 | 0.62 |
| 번체 세로쓰기 | 21.31 | 90.16 | 96.72 | **0.00** |

v6는 세로쓰기 설정에서 좌표로 열을 오른쪽부터 왼쪽으로, 한 열의 조각은 위에서 아래로 정렬합니다. 이 자료에서는 여섯 열의 원래 배열 인덱스가 `[5, 4, 3, 2, 1, 0]` 순서로 바뀌었고, 각 열의 글자·좌표·confidence는 보존됐습니다. 세로 정답 61자와 줄바꿈까지 일치해 엄격한 CER도 0.00%입니다. 간체·번체 가로쓰기 및 다른 세 엔진의 오류율은 모두 수정 전과 같습니다. 이 결과는 이 합성 자료의 순서 문제 해결을 확인한 것이며 복잡한 고서 전체의 정확도 평가로 확대하지 않습니다.

수정 전 보고서는 `benchmark-before-vertical-order.json`, v6만 정렬한 재실행 보고서는 `benchmark-after-v6-vertical-order.json`에 보존했습니다. `comparison.yeone-compare.json`에는 수정 전후 판독 이력이 모두 남고, 새 v6 세로 결과의 `engine_metadata.raw_engine_result`에는 정렬 전 문자열과 좌표가 보존됩니다. 정렬 정책 `vertical-columns-rtl-top-to-bottom-v1`을 요청·결과에 기록해 수정 전 캐시와 구분합니다. 이 단계의 관련 자동 테스트 200개와 하위 사례 55개가 통과했습니다.

## 2026-10-24 재실행 결과 — v5·EasyOCR에도 세로 열 순서 적용

PP-OCRv5(RapidOCR)와 EasyOCR에도 같은 정렬을 적용하고, 동일한 PDF·정답 파일·모델·200 DPI 설정에서 `--force`로 네 엔진을 모두 다시 실행했습니다. PDF와 정답 파일의 SHA-256, 엔진별 모델 지문이 이전 실행과 일치함을 확인했습니다. 아래는 공백만 제거한 CER(%)입니다.

| 자료 | Tesseract | RapidOCR/v5 기본 mobile 인식 | EasyOCR | PP-OCRv6 medium |
|---|---:|---:|---:|---:|
| 간체 가로쓰기 | 11.76 | 0.59 | 22.35 | 0.00 |
| 번체 가로쓰기 | 11.25 | 3.12 | 28.75 | 0.62 |
| 번체 세로쓰기 | 21.31 | **6.56** | **95.08** | **0.00** |

- v5 세로쓰기: **90.16% → 6.56%**. 11개 검출 조각을 오른쪽 열부터 읽도록 정렬했습니다. 정답 61자 중 네 글자(`曰→日`, `黃→黄`, `朮→术`, `巳→已`)의 치환 오류가 남았고 문자 누락·삽입은 없습니다. 검출 조각 사이 줄바꿈을 유지했으므로 줄바꿈까지 비교하는 엄격한 CER는 13.64%입니다.
- EasyOCR 세로쓰기: **96.72% → 95.08%**. 인식한 세 글자는 `讀`, `書`, `當` 순서로 정렬됐습니다. 빈 문자열인 큰 검출 영역도 그대로 보존했습니다. 이 설정에서는 정답 61자 중 58자가 누락돼, 순서 수정만으로는 이 자료의 세로 판독이 충분하지 않습니다.
- v6 세로쓰기는 **0.00%**를 유지했습니다. 가로쓰기의 모든 엔진과 Tesseract 세로쓰기의 오류율도 이전과 같습니다.

새 v5·EasyOCR 결과의 정렬 전 문자열·좌표·confidence는 이전 실행과 일치했고, 정렬 과정에서 글자를 바꾸거나 누락 영역을 채우지 않았습니다. 이 단계의 보고서는 `benchmark-after-all-vertical-order.json`에 보존했습니다. 이 시점의 비교 프로젝트는 쪽마다 총 12개의 판독 기록(세 번의 실행 × 네 엔진)을 보존했습니다. 정렬을 적용하지 않은 v5·EasyOCR 세로 캐시는 다음 실행에서 갱신되고, 같은 정책을 기록한 v6 캐시는 재사용됩니다. 관련 자동 테스트 202개와 하위 사례 58개가 통과했습니다.

## 2026-10-24 재실행 결과 — EasyOCR 세로 글자 누락 수정

### 원인과 수정

동일한 3쪽을 단계별로 검사했습니다. CRAFT 검출기는 9개 영역(낱글자 3개와 긴 세로 영역 6개)을 찾았습니다. 그러나 기본 `group_text_box`의 가로쓰기 병합이 긴 세로 영역들을 `[253, 85, 1597, 1225]`의 큰 상자 하나로 합쳤고, 이 상자는 빈 문자열로 인식됐습니다. 가로 병합은 상자 높이를 기준으로 거리·크기를 판단합니다. [EasyOCR v1.7.2 병합 코드](https://github.com/JaidedAI/EasyOCR/blob/v1.7.2/easyocr/utils.py), [공식 검출·인식 API](https://www.jaided.ai/easyocr/documentation/).

병합만 끈 실험에서도 긴 세로 영역 6개는 빈 문자열이었습니다. 인식기 입력의 높이는 64픽셀로 고정되므로, 예를 들어 폭 64·높이 871인 세로 열은 유효 글자 영역이 약 5×64픽셀로 축소됩니다. 글자 여러 개가 들어 있는 세로 열을 가로 인식 모델에 그대로 전달하는 문제가 함께 있었습니다. [입력 크기 처리](https://github.com/JaidedAI/EasyOCR/blob/v1.7.2/easyocr/recognition.py), [모델 입력 높이](https://github.com/JaidedAI/EasyOCR/blob/v1.7.2/easyocr/config.py).

세로쓰기 경로는 가로 병합을 끄고, 검출한 열을 빈 공간 기준으로 나눈 뒤 똑바른 글자 조각을 가로 띠에 이어 붙여 인식합니다. 이번 자료는 9개 검출 영역에서 61개 조각을 얻어 6개 열을 인식했습니다. 글자 수·좌표·정답을 하드코딩하거나 다른 엔진의 문자열을 사용하지 않았습니다. 원본 픽셀을 회전·확대·축소하지 않고 옮겼으며, 저장된 좌표 대응으로 띠를 다시 만들었을 때 모든 픽셀 SHA-256이 일치했습니다. 결과 좌표는 원본 페이지의 열 영역입니다.

### 같은 파일의 네 엔진 비교

기존 PDF·정답·모델과 200 DPI를 유지하고 네 엔진을 모두 `--force`로 재실행했습니다. PDF SHA-256은 `57863bf04cb406ad06e568974c5f57ec86f21da8fa8ddec885350756998a9db5`로 동일합니다. 아래는 공백만 제거한 CER(%)입니다.

| 자료 | Tesseract | RapidOCR/v5 기본 mobile 인식 | EasyOCR | PP-OCRv6 medium |
|---|---:|---:|---:|---:|
| 간체 가로쓰기 | 11.76 | 0.59 | 22.35 | 0.00 |
| 번체 가로쓰기 | 11.25 | 3.12 | 28.75 | 0.62 |
| 번체 세로쓰기 | 21.31 | 6.56 | **8.20** | **0.00** |

EasyOCR 세로쓰기는 **95.08% → 8.20%**, 누락은 **58자 → 0자**로 개선됐습니다. 정답 61자에 대해 출력도 61자이며, 다섯 글자(`芪→茛`, `朮→尤`, `爲→為`, `士→土`, `已→己`)의 치환 오류가 남았습니다. 이체자를 같은 문자로 접지 않았고, 삽입 오류는 없습니다. 열 단위 줄바꿈도 일치하며 공백을 포함한 엄격한 CER는 7.58%(5/66)입니다. 가로쓰기의 모든 엔진과 다른 세 엔진의 세로 결과는 직전 실행과 같습니다. 이 수치는 깨끗한 합성 자료의 결과이며, 붙은 글자·기울어진 글줄·복잡한 고서 배치의 정확도를 입증하지 않습니다.

최신 결과는 `benchmark.json`, 직전 결과는 `benchmark-after-all-vertical-order.json`, 단계별 검출 진단은 `easyocr-diagnostics/detection-diagnosis.json`에 있습니다. 비교 프로젝트는 쪽마다 16개의 판독 기록(네 번의 실행 × 네 엔진)을 보존합니다. 새 EasyOCR의 `vertical_preprocessing`에 원본 검출 영역·조각 대응을, `recognition_policy`에 `easyocr-vertical-unmerged-upright-reflow-v1`을 기록합니다. 관련 자동 테스트 213개와 하위 사례 61개가 통과했습니다.

## 2026-10-24 재실행 결과 — EasyOCR의 남은 다섯 오인식 분석

### 원인과 개선 범위

설치된 EasyOCR 1.7.2의 모델 출력 문자 목록을 검사했습니다. 번체 `chinese.pth`의 5,380자 목록에는 `芪`, `朮`, `爲`가 없습니다. 간체 `zh_sim_g2.pth`의 6,718자 목록에는 `芪`가 있지만 `朮`, `爲`는 없습니다. `士`, `已`는 양쪽 모델 모두 지원합니다. 전처리·allowlist만 바꿔서는 모델 출력층에 없는 코드 포인트를 만들 수 없습니다. [공식 모델 구성과 문자 목록](https://github.com/JaidedAI/EasyOCR/blob/v1.7.2/easyocr/config.py), [EasyOCR 인식 API](https://www.jaided.ai/easyocr/documentation/).

| 원문 | 이전 출력 | 원인·실험 결과 | 이번 출력 |
|---|---|---|---|
| 芪 | 茛 | 번체 모델 문자 목록에 없음. 간체 보조 모델은 원본·흰 여백 입력에서 모두 芪로 인식 | **芪** |
| 士 | 土 | 지원 문자지만 가까운 자형을 혼동. 번체 낱글자 점수 0.423, 보조 모델은 두 입력 모두 士로 인식 | **士** |
| 朮 | 尤 | 두 중국어 모델 모두 원래 코드 포인트를 지원하지 않음 | 尤 — 남음 |

각 글자의 유사도 0.98 이상·차순위와 차이 0.03 이상을 요구하고, 판독한 문자열 전체를 같은 글꼴·크기·시작점으로 재렌더링해 원본과 다시 대조합니다. 줄 전체 유사도가 0.98 이상이어야 적용합니다. 앞쪽 잉크를 버리거나 뒤에 읽지 않은 잉크가 남으면 채택하지 않습니다. 실제 공백·애매한 자형·불확실한 글꼴이 있으면 원래 검출 조각과 판독을 유지합니다. 세로쓰기의 한 글자 보완과 달리 가로 줄의 전체 대응을 확인하므로, 기본 판독에서 누락된 글자나 문장부호도 이미지 근거가 있을 때만 복원합니다.

화면 명칭은 **EasyOCR + 자형 보완**입니다. 기본 EasyOCR 신경망의 문자 지원을 학습으로 확장한 결과가 아니라 로컬 자형 보조 인식을 포함한 결과입니다. `horizontal_preprocessing.raw_engine_result`에 원래 EasyOCR 출력·좌표·confidence를, `regions`에 원래 조각 인덱스·줄 좌표·후보와 채택·보류 이유를 저장합니다. 후보별 자형 유사도·글자 폭·위치, 글꼴·크기·시작점, 원본·재렌더링 픽셀 지문을 기록합니다. 검증한 줄의 최종 confidence는 `null`로 두고, 기본 신경망 점수는 원래 기록에 보존합니다. 한글 가로쓰기에는 적용하지 않습니다.

### 기본 모델의 오류와 비교 실험

실제로 사용하는 v5 경로는 **server 검출 + mobile 인식**입니다. 간체·번체에 같은 중국어 인식 모델을 쓰며 별도의 간번체 변환 코드는 없습니다. 오류는 간체 가로 1개(`巳→已`), 번체 가로 5개(`朮→术`, `裏→里`, `爲→為`, `幹→乾`, `巳→已`), 번체 세로 4개(`黃→黄`, `朮→术`, `曰→日`, `巳→已`)였습니다. 모두 치환이며 누락·삽입은 없습니다. 세로는 이미 오른쪽 열부터 읽지만 11개 검출 조각 사이 줄바꿈이 남았습니다.

| 경로 | 간체 가로 CER | 번체 가로 CER | 번체 세로 CER |
|---|---:|---:|---:|

### 적용한 보완

**PP-OCRv5 mobile + 자형 보완**으로 표시하고, 기본 모델·설정·모델 지문은 유지했습니다. 가로쓰기는 공통 로컬 자형 인식으로 글자 모양·폭·부호 위치를 확인하고, 판독 문자열 전체의 재렌더링이 원본 줄과 일치하는 경우만 보완합니다. 이는 기본 신경망과 별도의 이미지 대조 단계입니다. 설치 글꼴의 전체 CJK 후보를 사용하며 정답 파일이나 EasyOCR·v6의 문자열을 인식 근거로 사용하지 않습니다.

세로는 가까운 같은 열의 조각을 모으고, 겹친 검출 영역의 합집합을 **한 번만 분할**합니다. 조각을 각각 나누면 겹치는 부분에 잡힌 이웃 글자의 일부가 중복 조각이 될 수 있기 때문입니다. 글자 사이 빈 공간으로 얻은 조각 수와 판독 코드 포인트 수가 맞고, 변경하지 않은 글자까지 모두 자형 유사도 0.98 이상·다른 후보와 차이 0.03 이상이어야 보완하고 열 단위로 이어 붙입니다. 큰 빈 간격은 나눠 처리하며 한 글자라도 불확실하면 해당 묶음의 기본 판독과 줄바꿈을 유지합니다.

### 확인한 오류와 시범 실행

직전 번체 가로쓰기 결과의 남은 오류는 다섯 번째 줄의 `爲→為` 치환 1개였습니다. 기본 줄은 `異體與近形：臺台、裏裡、羣群、為為、乾幹干。`였고, 공백 제외 CER은 1/160 = 0.625%였습니다. 실제 PP-OCRv6 medium 디코더에는 blank·공백을 포함해 18,710개 항목이 있으며 `爲`(인덱스 8801), `為`(8580)를 모두 지원합니다. 문자 목록 누락이나 앱의 간번체 변환이 원인은 아닙니다.

[RapidOCR 공식 모델 안내](https://rapidai.github.io/RapidOCRDocs/latest/model_list/)와 별도로 실제 설치 모델·후처리 코드를 확인했습니다. ONNX 내부 문자 목록을 사용하고 CTC argmax로 출력하며, 이 경로에 OpenCC 변환은 없습니다. 같은 원본 줄의 사각형 영역, 여백 추가, 두 배 확대 등 다섯 입력을 검출기 없이 같은 인식기로 읽으면 모두 올바른 `爲為`를 반환했습니다. 문자 목록·입력·출력·점수는 `ppocrv6-diagnostics/native-probes.json`에 보존했습니다.

기본 인식기에 실제 전달된 이미지를 추가로 포착해 유발 조건을 분리했습니다. 검출 사각형은 `[[104,818],[1134,817],[1134,869],[104,870]]`로 좌우에 **1픽셀 기울기**가 있었습니다. 기본 원근 보정 크롭은 높이 52×폭 1030픽셀, 원본의 축에 맞춘 사각형 크롭은 53×1030픽셀이었습니다. 보정 이미지는 단독으로 읽어도, 원래 배치에서 읽어도 `為為`를 반환했습니다. 원본 사각형 크롭은 단독으로 읽어도, 원래 배치의 해당 입력만 교체해도 `爲為`를 반환했습니다. 따라서 이 사례는 배치 분할만의 문제가 아니라 **기울기 보정·재표본화된 입력에서 근접 이체자를 혼동하는 모델의 민감성**으로 좁혔습니다. 모델 내부의 학습 원인까지 입증한 것은 아닙니다. 비교 입력 PNG와 네 실험은 `ppocrv6-diagnostics/input-diagnosis.json`, `warped-line.png`, `axis-line.png`에 남겼습니다.

거의 수평인 번체 줄을 원본 해상도로 다시 자르고, 원본과 흰 여백을 추가한 두 입력에서 같은 PP-OCRv6 후보가 나와야 검증합니다. 기본 판독과 길이가 같아야 하며 기존 로컬 자형 검증의 전체 줄 재렌더링 결과까지 그 후보와 정확히 같을 때만 채택합니다. 글꼴 단계에서만 나온 다른 문자열을 반환하지 않습니다. 원래 판독과 같거나 불확실한 줄은 기본 점수·좌표까지 유지합니다. 특정 글자 치환·정답 사전·다른 엔진 출력은 사용하지 않습니다.

### 메모리 문제를 해결한 실행 방식

시범 실행 뒤 Windows 커밋 여유가 약 50MB까지 줄어 ONNX의 `bad allocation`, Python의 `MemoryError`와 프로세스 종료가 발생했습니다. 다른 프로그램을 종료하거나 시스템 설정을 바꾸지 않고 작업을 분리했습니다. 비교 파일 로더는 작은 파일에도 256MB를 요청하던 단일 읽기 대신 1MB 이하 청크로 읽도록 수정했습니다. 기존 파일 크기 제한·JSON 검증·해시는 유지하며 회귀 테스트로 확인했습니다.

평가는 `OPENBLAS_NUM_THREADS=1`, `OMP_NUM_THREADS=1`로 순차 실행했습니다. 기본 ONNX Runtime의 명시적 스레드 설정과 EasyOCR의 CPU 2개 스레드는 유지했습니다. ## 2026-10-24 PP-OCRv6 추가 6개 조건의 네 오류 개선

### 원인과 입력 실험

이전 추가 평가의 네 오류는 **Microsoft JhengHei(`msjh.ttc`) 28·44 크기에서 각각 두 번씩 `爲→為`로 읽은 것**입니다. 오류 줄의 정답은 `爲為、為爲；羣群、裏裡、臺台、己已巳。`이고, 기본 판독은 `為為、為為；羣群、裏裡、臺台、己已巳。`였습니다. 출력 문자 목록은 두 글자를 모두 지원합니다. 설치 글꼴의 두 글자 마스크 SHA-256도 달라 이미지에서 구별 가능한 자형임을 확인했습니다.

원본 사각형 크롭과 작은 여백에서는 기본 모델이 같은 오인식을 반환했습니다. 여백을 늘리면 두 `爲`를 맞히지만 `、`를 누락해 `爲為為爲；羣群裏裡臺台己已巳。`처럼 읽었습니다. 크기·여백 방향·여백 양을 바꾼 실험에서도 완전한 정답 문자열을 반환하는 후보를 얻지 못했습니다. 이 결과는 원문의 부호를 변환한 것이 아니라, 재표본화 조건에 따라 근접 한자와 작은 부호의 인식이 달라지는 경우입니다. 실험은 `ppocrv6-diagnostics/remaining-native-probes.json`에 남겼습니다.

기존 v1은 **문자열 전체의 합의**만 허용했기 때문에 올바른 한자 후보가 있어도 부호 누락으로 보완을 보류했습니다. 또 이 줄의 첫 글자부터 오인식했으므로, 기본 판독의 첫 글자를 그대로 자형 검증 앵커로 쓰면 올바른 후보의 검증을 막을 수 있습니다.

### 적용한 v2 보완

전체 문자열 합의 경로는 유지합니다. 여백 입력이 기본 판독과 다른 한자를 제시했지만 부호를 일부 누락하면, **여백을 1픽셀 더 늘린 두 번째 입력**을 같은 PP-OCRv6 medium 인식기로 읽습니다. 서로 다른 두 여백 입력의 한자 순서·개수가 정확히 같고 기본 한자 개수와도 같을 때만 한자 치환 후보를 만듭니다. 부호는 기본 판독의 위치를 유지하되, 재인식 부호가 기본 부호의 순서를 유지한 부분 목록인지 확인합니다. 새 부호·순서 변경·한자 누락·삽입은 허용하지 않습니다.

이 경로는 한자와 Unicode 문장부호만 있는 줄에 한정합니다. 영문·숫자·실제 공백·결합 문자·이체자 선택자가 섞이면 보류합니다. 제안한 모든 한자는 같은 OCR 모델의 두 판독에서 가져오고, 유지한 부호는 기본 모델 판독에서 가져옵니다. 특정 글자 쌍의 일괄 치환이나 정답 파일·다른 엔진 판독은 사용하지 않습니다.

합의된 후보의 첫 글자를 자형 검증 앵커로 사용하고, **전체 줄의 한자·부호·글자 폭·위치를 재렌더링해 검증**합니다. 자형 인식이 후보와 다른 문자열을 반환하거나 근거가 부족하면 기본 판독을 유지합니다. 부호를 단순히 복사한 결과를 검증 없이 채택하지 않습니다. `candidate_source`, `candidate_text`, `punctuation_retry`에 후보 구성 방식·추가 입력·점수·픽셀 지문을 보존하며 기본 문자열·좌표·점수는 계속 `model_result`에 남깁니다. 보완 영역의 최종 confidence는 `null`입니다.
