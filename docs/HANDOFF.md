# 연어OCR 개발 인수인계

## 2026-11-12: 1.2.8 쪽 나눠 보내기

`local_first._command`의 쪽 반복에서 엔진 뒤 AI 부분(체크포인트 기록·AI 쪽 판독·prepare_plan·run_plan·제안 반영·기록)을 `ai_stage`로 옮겼다. 선택을 끄면 반복 안에서 그대로 부른다. `--local-ai-split`이고 구독 세션이 있으면 `_SplitPlans`가 로그인된 구독마다 `Session`(record_provider는 실행의 제공사)·쪽 판독기·작업자 1개를 두고, 엔진을 마친 쪽을 빈 작업자에 맡긴다. 프로젝트 저장·상태 파일·쪽 그림 그리기는 각자 잠금이 있어 쪽마다 다른 스레드가 써도 된다. 호출 수는 `tally`(잠금). 중지·반환 때 `finally`에서 작업자를 기다린다. `Session.request`는 받은 모델 이름이 그 계정 것이 아니면 계정의 모델을, `_as_first`는 기록 제공사 기준 완료 표시를 쓴다.

## 2026-11-12: 1.2.7 동시 AI 요청

`comparison_ai.run_plan(parallel=N)`: 묶음 처리를 prepare(계획 차례·주 스레드: 이미지·프롬프트·기록 틀) → start(클라이언트·중지/범위 확인·호출 수) → send(요청만, N>1이면 작업 스레드) → finish(계획 차례·주 스레드: 응답 검증·기록·checkpoint)로 나눴다. N=1은 예전과 같은 차례로 같은 함수를 부른다. 치명적 실패·중지·상한 오류는 새 요청 없이 이미 보낸 답을 기록한 뒤 처리한다. editorial 묶음이 있으면 늘 1. `local_first`는 구독 세션이면 `--local-ai-parallel`(기본 3), API 키면 1을 넘긴다. 창 설정 `local_ai_parallel`.

## 2026-11-12: 1.2.6 빠른 이어하기 · 「이어서 할 때」

`local_first._record`가 `local_first.resume_key`(`_resume_key`: 판독 조건·기준 run id·`project.text` 지문·AI 설정)를 남긴다. 쪽 반복에서 엔진이 하나도 다시 돌지 않았고(`outcome["completed"]` 비어 있음) 열쇠가 같고 검증 상태가 `RESUME_DONE`이면(AI 쪽 판독이 켜져 있으면 그 요약도 있어야) 계획·쪽 판독·기록 쓰기 없이 넘어간다. `--local-resume continue`는 local-first 기록이 있는 쪽을 엔진 단계 전에 그대로 넘기고, `all`은 빠른 길을 끈다. `_save_record`는 이전 local-first 실행의 쪽 그림이 있으면(입력 보정 없음) 다시 그리지 않는다. 창: `RESUME_LABELS`, 실행 카드 `cb_resume`(기록 있는 책에서만, 실행 중 잠김), 설정 「인식」의 `resume` 줄.

## 2026-11-12: 1.2.5 설정 탭을 기능별로 재배치 · 판 번호 · [업데이트 확인]

설정 갈래(`App.SET_RAIL`)를 작업 차례대로 바꿨다: 인식(인식 방식·로컬 문서 종류·두 단·줄 다시 확인·EasyOCR·기록 있는 쪽 다시 판독) · AI 판독기(① 구독 계정·로그인 상태 → ② 판독기·모델·API 키 → ③ 로컬 뒤 AI 검증·API 키로 넘어가기, 세부 설정(접힘), 판독 뒤 모델 단계 — 이전 '모델 단계' 섹션) · 이 책 · 문서 만들기(만들 파일 · 표시 · 쪽·문단 묶음) · 자동 교정 · 책갈피 교정. 행 열쇠(`_set_rows`)와 변수·설정 열쇠는 그대로이고 만드는 차례와 섹션만 바뀌었다. 묶음 머리는 `_build_settings_tab`의 `subhead`. 두 열은 왼쪽 인식·AI 판독기·이 책 | 오른쪽 문서 만들기·자동 교정·책갈피 교정. 새 설정 `local_ai_api_fallback`(끄면 `--no-local-ai-api-fallback`). 로그인 상태(`App.refresh_plans`)는 설정 탭을 처음 열 때와 [상태 확인]으로 뒤에서 확인한다. 실행 카드·설정 요약의 AI 표시는 `App._ai_summary`(구독 → API 차례). 명령 띠의 이름 옆에 판 번호 알약(`l_version`, 누르면 업데이트 확인), 설정 바닥 줄에 [업데이트 확인](`b_update`).

## 2026-11-12: 1.2.4 겹친 검증 대상 식별자 · 요청 거부

`comparison_ai._target`의 식별자는 (쪽, 종류, 위치, 글자, 출처)로 만들어 상자를 넣지 않는다. 같은 단어 뒤의 '읽지 못한 먹 자국'(unrecognized-ink-region)이나 빈 판독의 먹 자국(empty-ocr-with-ink)은 같은 빈 위치라 식별자가 겹쳤고, 묶음 4개(구독 기본)에서 한 묶음에 들어가면 응답 스키마 enum 중복(Claude Code·엄격 구조화 출력이 거부)과 프로젝트의 검증 기록 거부로 이어졌다. `_unique_ids`가 겹치는 것만 상자로 다시 만든다(첫 식별자는 그대로라 이어 쓰기 유지). CLI가 요청을 거부한 오류는 `claude_subscription.RequestRejected`로 계정 넘김 없이 그 요청만 실패(fatal 아님)로 둔다. 오류 안내는 `failure()`가 원문을 붙인다. 진행 기록의 쪽별 상태는 `local_first.REVIEW_STATUS_LABELS`로 한국어 표기한다(기록 값은 그대로; 측정 도구 정규식도 맞춤).

## 2026-11-12: 1.2.3 [다음 구독으로 넘기기]

진행 카드의 AI 연결 줄(`gui.App._show_ai_link`, `switch_subscription`)이 실행 중인 `subscriptions.Session`을 옮긴다. `local_first`가 세션을 `subscriptions.activate`로 알리고 실행이 끝나면 `deactivate`한다. 창은 같은 프로세스에서 명령을 돌리므로 `subscriptions.ON_CHANGE`(창이 실행 동안 거는 콜백)로 상태를 받는다. `Session.switch(target)`은 쓰던 계정을 이번 실행의 '넘김'으로 표시하고, 세션이 띄운 CLI(세션의 `_run`으로 실행, Windows는 `taskkill /T`, 그 밖은 프로세스 묶음)를 끈 뒤 고른 계정(로그인 안 됐으면 순서대로)이나 순서의 다음, 남은 구독이 없으면 API 키에 연결한다. 끊긴 요청은 `Session.request`가 계정이 바뀐 것을 보고 새 연결로 다시 보낸다.

## 2026-11-12: 1.2.2 ChatGPT·Gemini 구독 계정 연결, 한도 시 다른 구독 → API 키

`yeone_ocr/subscriptions.py`가 구독 계정을 고른다: claude(Claude Code `claude -p`), chatgpt(OpenAI Codex CLI `codex exec`, Sign in with ChatGPT), gemini(Gemini CLI `gemini -p`, Login with Google). 각 전송은 `claude_subscription.py`와 같은 계약(`status`, `SubscriptionClient.request(...) -> (text, complete, finish_reason, tokens, model)`)이고, 구독 표지 키(`subscriptions.KEYS`)로 `comparison_ai.create_client`가 고른다. `local_first`의 기본값 판단·쪽 판독·의심 구간 검증이 모두 이 선택을 따른다. 자동 순서는 Claude → ChatGPT → Gemini(기본 설정을 Claude로 쟀으므로).

원칙은 Claude와 같다: 공식 프로그램만 실행하고 토큰 파일은 읽지 않는다(Gemini는 로그인 방식 확인에 settings.json만 읽음), 자식 프로그램 환경에서 API 키를 뺀다, 요청마다 빈 임시 폴더. Codex 옵션 조합과 Gemini 옵션(`-o json --approval-mode plan -e none --allowed-mcp-server-names none --skip-trust`, `GEMINI_SYSTEM_MD`)은 codex-cli 0.167.2·gemini-cli 0.68.0 실물로 인자 해석과 로그인 단계 도달까지 확인했다. 개발 환경의 네트워크 제한으로 실제 로그인 호출은 하지 못했으므로, Windows에서 `yeone-ocr plans` 뒤 한 쪽으로 첫 실측이 필요하다. 테스트는 `tests/conftest.py`가 세 CLI 경로를 모두 없는 파일로 돌려 실제 프로그램을 띄우지 않는다. 안내: `docs/SUBSCRIPTION_PLANS.md`.

실행 중 실패(한도·로그인 만료·CLI 없음)는 `subscriptions.Session`이 받아 다음 구독으로 같은 요청을 다시 보내고, 남은 구독이 없으면 `comparison_ai.ApiTransport`(설정의 제공사·모델·키, `--local-ai-max-calls` 상한)로 넘긴다. 다른 제공사로 넘어간 완료 응답의 finish_reason은 첫 구독 제공사의 값으로 맞춘다(검토 기록의 위치 복원 검사가 기록의 provider로 대조하므로). 실제 모델과 전송 경로는 metadata의 actual_model·transport에 남는다.

## 2026-10-21: 1.0.6 교정본 파일 교체 잠금 처리

대조 편집의 `SectionEditSession.save`는 임시 HWPX 검증 후 원자 교체하므로, 한글에서 교정본을 열어 두고 삭제 공유를 허용하지 않으면 Windows가 파일 교체를 거부한다. WinError 5/32/33에 한정한 짧은 재시도를 적용하고, 재시도 직전 현재 transaction 단계에 맞는 파일 지문을 재검증한다. 영구 잠금·읽기 전용·권한 문제는 강제로 우회하지 않고 `SaveAccessError`와 실제 차단 경로로 전달한다.

실패 시 기록 롤백은 현재 기록이 앱이 쓴 intent와 같은 경우에만 수행하며, 다른 저장자의 변경을 덮어쓰지 않는다. UI는 현재 입력과 수정 취소 상태를 유지하고 기존 저장·본문 내보내기 동작으로 안내한다. 실제 사용자 문서의 잠금 조회는 읽기 전용으로 수행하고, 원자 교체 검사는 합성 파일과 실제 Windows 공유 잠금으로 수행한다. 개인 감사 자료는 `work/private-save-lock-audit/`, 배포 검증은 `work/release-1.0.6/`에 둔다.

## 2026-10-21: 1.0.5 공백만 달라진 수동 교정 문단 보호

수동 교정 보호는 문단 전체 텍스트의 정확한 해시만 인정하여, 이후 일반 공백을 지운 문단도 외부 문자 변경과 동일하게 차단했다. 대상 파일·문단 개수·signature 검증과 정확한 해시 일치는 유지한다. 해시가 다른 경우에만 유효한 correction_events에서 동일 문단·signature 및 보호 기록에 등록된 before/after 해시를 확인하고, U+0020만 다른 본문을 보호 대상으로 인정한다. 일반 공백 외 문자·탭·줄바꿈·유니코드 정규화는 허용하지 않는다. 본문 없는 구형 기록이나 잘못된 학습 기록으로는 이 예외를 인정하지 않는다.

확인 과정에서 HWPX·수동 기록을 쓰지 않고 현재 문단 전체를 자동 교정에서 제외한다. 학습 사례의 정확한 현재 본문 일치 규칙은 유지하며, 외부 공백 변경을 새 사례로 자동 추가하지 않는다. 실제 문헌의 읽기 전용 차이 분석은 `work/private-manual-conflict-audit/`, 배포 결과는 `work/release-1.0.5/`에 보관한다.

## 2026-10-21: 1.0.4 일반·이미지 OCR 대조 편집과 교정본 서식 표시

일반 OCR과 이미지 OCR의 실행 카드에서 완성된 HWPX를 공통 대조 편집창으로 연다. 진입 시 활성 원본·결과 폴더·출력 HWPX를 고정하고, 생성 문서의 원본 쪽 정보로 편집 범위를 정한다. 원본 OCR 결과는 보존하고 같은 위치의 `_교정.hwpx`에 누적 저장한다. 새 판독은 하지 않으며, 문단 대응·외부 변경·수동 수정 이력 보호를 유지한다. 쪽 이동에도 미저장 수정 보호를 적용한다.

새 작성기는 `META-INF/yeone-ocr-edit.json`에 OCR 등급 서식과 원래 서식 ID의 대응만 기록한다. 양식의 기존 색상 서식과 OCR 표시가 시각적으로 같아도 서로 다른 ID를 사용해 작성자 색상을 OCR 표시로 오인하지 않는다. 경로·본문·개인 설정은 이 메타데이터에 넣지 않는다. 예전 출력은 원본과 일치하는 작업 기록 및 서식 대응을 확인할 수 있는 경우에만 표시를 제거한다. 이미지 커서 연결은 원본 지문이 일치하는 기존 OCR 영역을 사용하며, 글자 좌표가 없는 영역은 정확한 커서나 글자 크기 추정으로 바꾸지 않는다.

기존 대조 편집의 `_highlight`는 원본과 현재 글자의 문자열 차이만 파란색으로 표시했다. 교정 HWPX의 빨강 확인 표시는 원문 글자를 바꾸지 않는 경우가 많아 누락됐고, 사람 수정도 원본과 다르다는 이유로 다시 파랑이 됐다. 저장된 `charPrIDRef`의 색·배경·굵게·밑줄과 본문 위치를 읽고, 같은 교정본 스냅샷의 표시를 화면에 전달한다. 원본과의 비교는 하단 원문 대조에 남긴다.

미저장 수정은 불러온 교정문에서 그대로인 구간에만 기존 표시를 대응하고, 사람이 바꾼 위치에는 OCR 표시를 다시 만들지 않는다. 저장 후 최신 서식을 다시 표시한다. 입력·저장·취소·다시 불러오기와 구획 밖 일괄 수정에서도 본문·수정 기록·원본 보호 규칙은 유지한다. 실제 문헌 검증 및 배포 결과는 `work/private-color-display-audit/`, `work/release-1.0.4/`에 보관하며 개인 문헌을 공개하지 않는다.

## 2026-10-21: 1.0.3 여러 서식에 걸친 수정 저장과 배포 병렬화

대조 편집 저장에서 `_replace_text`가 글자 수가 다른 치환 구간에 여러 `charPrIDRef`가 있으면 저장을 막았다. OCR 표시도 별도 서식이므로, 원본이 단일 서식이어도 교정문의 평범한 수정이 거부됐다. 길이가 달라지는 치환은 기존 글 조각의 순서와 길이에 비례해 배분하고, 원본 서식 대응에도 같은 규칙을 사용한다. 동일 글자는 기존 위치·서식을 유지하고 삽입은 해당 위치의 서식을 이어받는다. 빈 문단의 복원은 실제 삽입 슬롯과 같은 마지막 원본 슬롯 서식을 사용한다.

사람이 바꾼 글자의 앱 OCR 표시만 제거하며, 원래 글꼴·크기·강조, 수정하지 않은 표시, 메모·책갈피·형광펜 XML 노드와 비선택 문단을 보존한다. 저장 전 사본·외부 변경 검사·원자 저장·수정 기록 보호는 유지한다. 합성 회귀와 배포 자체 검사에 여러 서식에 걸친 길이 변경 후 저장·재열기를 포함한다. 실제 문헌 확인은 작업 폴더 복사본에 한정한다.

문단별 Text 위젯은 마우스 선택이 다음 문단으로 이어지지 않는다. 구획 전체 복사와 본문 내보내기를 별도 조작으로 제공해 미저장 수정도 옮길 수 있게 한다. 내보내기는 현재 구획/교정본 문서 전체 중 선택하며, 불러온 교정본의 본문에 현재 미저장 수정과 다른 구획의 일괄 바꾸기 초안도 적용한다. 수정 전 내용·문단 번호·비교 설명은 내보낸 본문에 섞지 않는다. 수정하지 않은 문단과 제목도 포함한다. 변경 확인창은 검토를 위해 전후를 표시하지만 내보내기 파일은 현재 본문만 담는다. TXT 보관은 HWPX 저장·수동 교정 기록 반영을 대신하지 않는다. 보관·복사·취소·실패는 현재 수정 내용과 dirty 상태를 바꾸지 않는다. 한글 입력 상태의 전체 선택도 물리 A 키로 처리한다.

공개 CI는 회귀와 빌드·설치 검증을 독립 작업으로 실행한다. 회귀는 `--workers 2 --fail-fast --prioritize`로 관련 검사를 먼저 실행하고, 명시적으로 검토한 비화면 모듈만 병렬화한다. 미검토·GUI 모듈은 단독 실행한다. 실패 후 이미 실행 중인 자식의 결과를 수집하고 대기 모듈은 `unrun_modules`에 남긴다. 모든 모듈을 완료하지 않은 실행은 성공으로 취급하지 않는다.

`tools/verify_release_bundle.py`는 동일 커밋의 공개 자산 6개와 별도 영수증 해시를 검증한다. 게시 작업은 회귀·빌드가 모두 성공한 뒤 지정 artifact ID의 파일을 받아 해시·버전·소스 커밋을 확인한다. 새로 빌드하지 않는다. 수정 중에는 관련 검사만 실행하고, 최종 전체 회귀와 배포 빌드는 공개 CI에서 수행한다. 로컬 확인도 CI의 같은 파일을 사용한다. `work/release-1.0.3/`에 실제 소요 시간과 원본 검사·빌드·배포 증거를 모아 둔다.

## 2026-10-21: 1.0.2 대조 편집 초기 배치 복구

숨긴 동안 미룬 렌더링은 다시 표시할 때 재개한다. 패널 폭이 같아도 최초 이미지 또는 현재 쪽·확대율의 렌더링이 빠질 수 있으므로, 분할 위치 변경 여부만으로 재렌더링을 결정하지 않는다.

1.0.1의 문단 입력 복구, 구획·문서 전체 찾기·바꾸기, 복사, 사람 수정 기록과 원래 서식 복원도 유지한다. `work/release-1.0.2/`에 합성 자료 기반 배치·회귀·실행 파일·설치·공개 자산 검증 기록을 보관한다. 공개 결과는 해당 릴리스의 최종 검증 기록을 기준으로 한다.

## 2026-10-20: 0.12.5 색상만 표시와 앱 메모 정리

일반·이미지 OCR(`run`·`build`)도 `--memo none`이 기본이며 쪽 고지·글자 메모·범례를 문서에 넣지 않는다(고지는 검수 화면에 남고, `notice`·`all`·`inline`은 선택). 책갈피 `--memo none`이 기본이며 메모·범례 메모·본문 설명을 추가하지 않는다. 삭제·폭 없는 제안은 인접 글자에 표시하고 원문 글자는 추가하지 않는다. 보고서에는 모든 근거와 제안을 보관한다. 일반 OCR 메모 기본값은 유지하며 책갈피의 이전 notice/inline 설정만 최초 한 번 none으로 이행한다.

가로 검출도 기존 문자 영역 밖은 검사하지 않는다. 소주를 한 블록으로 저장한 경우에는 처리하지만 각 행을 별도 영역으로 나눈 경우에는 두 행 조건을 만족하지 못한다. 큰 본문이 없는 독립 주석, 흐림·기울기·글자 크기가 비슷한 배치도 놓칠 수 있다. 표·그림과 유선표는 제외하지만 큰 왼쪽 셀과 작은 다중행 오른쪽 셀처럼 소주와 같은 형태의 무선표는 의미상 구별할 수 없다. 후보는 검수 대상이며 누락 확정이나 자동 교정 승인이 아니다.

실측은 기존 설정의 Gemini `gemini-3.1-pro-preview`로 1·2차 판독 3회와 줄별 재판독 11회, 총 14회 호출했다. 실제 baseline의 4개 소주 영역을 그대로 검출에 제공해 4후보·11행을 찾았다. 기존 판독도 이미 4곳·11행을 모두 포함했다. 정답 bbox와 baseline·후보 bbox를 IoU 0.5 이상으로 각각 일대일 대응하고 해당 영역의 모든 텍스트를 비교했다. 동일 4영역의 원문 코드 CER는 **16/348=4.60% → 33/348=9.48%**, 공백 제외는 **13/288=4.51% → 25/288=8.68%**로 악화했다. baseline의 공백 제외 13개 차이는 전부 NFC 등가 호환 한자→통합 한자 차이로, 시각 오독으로 단정하지 않는다. 신규 후보는 이 차이를 유지하면서 한자 이체자 변경, 문장부호 치환, 원문에 없는 문구 추가도 보였다. 후보 점수는 본문 수정 후 점수가 아니다. 기존 판독 바이트·원본 HWPX/PDF·정답은 불변이며 실제 자료의 자동·사람 확정 삽입은 0건이다.

공간 대응 baseline 전체 영역 CER는 baseline의 영역 구조를 확인한 뒤 추가한 사후 계측이다. 정답으로 substring을 골라 맞추지 않으며 미매칭 영역은 이 지표에서 미산출한다. 동일 문구가 반복되는 소주는 각기 다른 영역과 대응하고, 별도의 문자열 출현 지표도 겹치지 않는 출현을 소비한다. 이 표본에서는 누락 회복과 재판독 정확도 개선을 입증하지 못했다. 세부 결과는 `work/small-annotations-user-sample-20261019/report.md`, 원시·영역별 점수는 `evaluation.json`, 원본·기록 보존과 실행 소스 변경 내역은 `preservation-receipt.json`에 보관한다. 모델 호출 뒤 추가한 반복 행 소비 수 보호는 같은 응답을 오프라인으로 재확인하며, 새 API 호출이나 본문 변경으로 이어지지 않는다.

## 2026-10-19: 쌍행소주 영역 검출·재판독·명시적 삽입

Document AI 없이 기존 이미지 판독기를 재사용한다. `small_annotation_detection.py`는 본문·설명문·기존 소주 bbox 내부를 국소 창으로 검사해 좁은 세로 두 소열을 찾는다. 큰 글자의 열 격자와 작은 글자 폭·먹 분포를 확인하고, 오른쪽/왼쪽 bbox·근거·제한 사항을 돌려준다. OCR 텍스트를 검출 근거로 쓰지 않는다. 도판·가로쓰기 영역은 제외하고 쪽당 후보를 최대 64개로 제한한다. 기록이 없는 쪽은 이미지 전체를 검사한다. 기존 영역 밖, 아주 짧은 소주, 낮은 해상도, 번짐·기울기·획 분리·후보 끝부분에서는 미검출·오탐·부분 잘림이 남는다.

`small_annotations.py`는 `annotations/pNNN.json`에 검출과 소열별 원시 재판독 이력을 별도로 저장한다. 각 소열은 작은 세로 한 줄 전용 지시로 읽고, 원래 코드포인트를 그대로 보존하며 오른쪽→왼쪽으로 제안한다. 이미지·좌표·제공사·모델·지시문 지문이 같은 성공 응답만 재사용한다. 부분 실패·호출 상한·취소 뒤에는 완료한 소열부터 이어진다. 모델을 바꿀 때 서로 다른 설정의 두 소열을 섞지 않는다. 호출 상한은 기본 12이며 재시도도 포함한다. 일반 OCR을 중지했던 신호가 새 작업을 막지 않도록 취소 이벤트를 실행 범위 안에서 교체·복원한다.

검출·재판독은 기존 `readings/`를 쓰지 않는다. 반영은 사람이 본문 열과 삽입 위치를 명시한 경우에만 허용하며, 현재 열·기록 전체·원본 지문을 검사하고 원문을 교체하지 않고 삽입한다. 한 소열만 이미 있으면 사람이 빠진 소열을 선택하여 그쪽만 추가한다. 기존 글과 중복되거나 기록이 바뀌었으면 중단한다. 쓰기 직전에도 현재 기록 바이트를 재검사한다. `readings/prev/`에 수정 전 바이트 그대로 사본을 두고 `small_annotation_history`에 원본·이미지·조각·요청·삽입 위치·이전 열·선택 소열을 남긴다. 이전 pass1/pass2·확정 판별·알 수 없는 옛 필드도 유지한다. 이전 단계의 교정 보존 정책 덕분에 이후 재비교에서도 삽입한 소주가 유지된다. 자동으로 사람 검수 완료를 붙이지 않는다.

앱 고급 도구의 **쌍행소주 검수**는 원본 조각·쪽 안 위치·두 소열·기존 열·삽입 미리보기를 보여 준다. 불러오기는 자동, 검출·유료 재판독·반영은 명시 실행이다. 별도 작업 스레드와 중지를 지원하고 모달 창으로 일반 OCR과 호출 상한이 겹치지 않게 한다. 명령줄 `annotations`는 검출, `annotations --reread`는 별도 재판독을 수행하고 `annotations/review.html`을 만든다. 문서 재생성은 기존 기능을 사용한다. 작은 글씨의 쌍행 서식 복원은 이 기능의 범위가 아니다.

실책 검증은 [공개 원본 『四書集註 [1]』](https://da.dl.itc.u-tokyo.ac.jp/portal/assets/b161c2dd-5b01-7e3a-5485-0cacd1201d3f)(도쿄대 종합도서관, 1766년 일본 간행 한문본)의 이미지 012를 개발용, 020·040의 오른쪽 반면을 보류 검증용으로 사전 분리했다. 검출 결과·OCR을 보기 전에 고른 5개 소주 63한자의 잠정 시각 전사를 별도 gold에 동결했다. 이는 사용자 확정 정답이나 한국 고서 대표 표본이 아니다. `tools/measure_small_annotations.py`는 이미지 전용 취득과 정답 채점을 분리하고, 같은 모델의 기존 1·2차 판독에 대한 완전 소주 포함 여부와 신규 후보의 정확 문자 오류를 각각 잰다. baseline에는 글자별 좌표가 없으므로 소주별 baseline CER을 산출하지 않으며, 일부 소주만 표지했으므로 전체 쪽 검출 정밀도도 산출하지 않는다. 실측 작업·출처·지문은 `work/small-annotations-20261019/`에 보관한다.

실측 결과: 선정 5곳 중 3곳을 IoU 0.5 이상으로 검출했다(60%). 기존 판독에는 **5곳 모두 이미 존재**하고, 그중 1곳에 `〔潜/潛〕` 후보 표시가 있었다. 정확 코드의 소주 전체 포함은 기존 4/5에서 기존+새 후보 4/5로 그대로였다. 신규 후보만의 CER은 미검출을 삭제 오류로 포함해 48/63=76.19%였으며, 이는 전체 본문의 전후 CER이 아니다. 새 후보에도 오독과 끝부분 잘림이 남았다. 정답 밖 후보의 사후 질적 확인에서도 누락 회복은 확인하지 못했다. 별도 실제 세로 혼용 선언서 음성 대조군에서는 글자의 획을 소열로 잘못 잡은 후보 2개가 나왔다. **누락 감소나 정확도 향상은 입증하지 못했다.** 자동 파이프라인에 넣지 않고 원본 확인·명시적 삽입을 위한 검토 보조로 제공한다. 실제 호출은 기존 판독 5회+소열 재판독 16회=21회, 실패 0회이며 두 기준 판독 파일의 바이트 지문은 불변이다. 실제 자료에 대한 자동·사람 확정 삽입은 0건이다.

회귀 검증은 **103개 모듈·1,658개 테스트 통과**, 최종 실패·오류·건너뜀·미완료 0개다(신규 61개). 초기 6개 실패 중 5개는 Windows 하드링크·프로세스 간 잠금·공유 GPU 대기열의 샌드박스 제약이었고, 동일 테스트를 제한 밖에서 재실행해 통과했다. 나머지 1개는 새 CLI 명령의 상단 도움말 목록 누락으로, 모듈 docstring 한 줄을 추가한 뒤 관련 29개 테스트를 재검증했다. 초기 103개 소스·테스트 지문을 복원 검증했고 도움말 외 실행 AST가 동일함을 확인했다. 최종 바이트로 전체를 두 번째 실행했다고 주장하지 않는다. 결과·재검증·도움말 변경 예외의 감사 기록은 `work/small-annotations-20261019/FINAL_VALIDATION.json`이다. 설치판 재빌드·배포는 하지 않았다.

당시 v3의 같은 PDF 3종·120범위 보고서는 `work/ocr-punctuation-recall-v2/replay/reports/report.html`이다. 직전 v2 대비 공백 제외 전체 오류는 **7,382→7,087자**, CER는 **11.1069→10.6631%**, 부호 오류는 **6,845→6,550자**로 개선됐다. 한자 536자·한글 1자 오류는 동일하다. AI 완료 99범위에서 도움 제안은 251→525건, 오교정과 맞던 부호 손상은 각각 **38→17건/자**, 맞던 한자 손상은 **0→0자**다. 393건 중 올바른 교정 312건을 복원했지만 기존 도움 38건을 새로 보류했고 이전 보류 오교정 6건도 살아났다. 기존 오교정 27건을 차단하여 순 오교정은 21건 줄었다. 이전 v1의 CER 10.6134%와 로컬 후보만의 10.2734%보다 전체 CER는 아직 높다.

AI 완료 99범위·미완료 21범위와 원래 AI 제안 1,512개를 고정한 재적용 평가다. 미완료 범위의 대체 결과를 바꾸지 않았으며 새 API·GPU 인식·사람 확정은 0건이다. 이전 개발 자료 진단으로 정책을 설계하고 새 채점 전에 고정했으므로 독립 검증 자료가 아니며, v10 프롬프트의 새 실제 응답 효과를 입증하지 않는다. 참고 정답은 원본 HWPX·DOCX에서 추출한 잠정 정답이고 전부 사람이 이미지 대조한 것은 아니다. 변경은 개발 소스에 반영했으며 설치 파일 교체·공개 배포와 구분한다. 이전 v2의 393건 과잉 보류와 81개 모듈·1,364개 검사는 `work/ocr-punctuation-recall-v1`에 그대로 보존한다.

앞선 소스 수정은 AI가 맞던 한자를 바꾸는 문제에 대한 `source-fidelity-v1` 보호 검사와 `comparison-ai-v8` 요청을 추가했다. 이미지 판독의 간번체·이체자 변경은 보류하고, 그 밖의 한자 교정에는 기준을 제외한 독립 OCR 두 계열의 유일한 양쪽 4자 문맥과 정확한 변경 위치 동의를 요구한다. RapidOCR·Paddle 서버형은 한 계열이다. 보류한 판독을 후속 번체·부호 편집으로 우회 적용하지 못하며 UI에 사유를 표시한다. 선택한 번체 편집은 별도 정책으로 유지한다. 아래는 앞선 v1 보호 수정의 역사적 측정 결과다.

원래 AI 응답·제안·불확실성은 수정하지 않는다. 새 기록은 원시 OCR 근거·정책·사전 지문과 기계 판정을 별도 보존하여 재열기에서 검증하고, 과거 미확정 후보는 현재 보호 검사를 동적으로 거친다. 과거 사람이 확정한 이력은 소급 변경하지 않는다. 같은 PDF 3종의 기존 이미지·OCR·실제 AI 응답을 고정한 재적용 평가는 `work/ocr-safety-replay-v2/reports/report.html`에 보존한다. 이는 새 모델 응답을 생성한 시험과 구분하며 평가용 정답은 보호 판정에 사용하지 않는다. v1은 채점 전 합성 이체자 선택자 경계 문제를 발견한 시도의 기록으로 남긴다.

이 재적용 평가의 공백 제외 전체 120단위 한자 오류는 원시 571, 종전 AI 단계 578, 보호 후 542다. 순수 AI 완료 99단위의 맞던 한자 손상은 89→0, 오교정 제안은 180→94이며 잔여 손상 93자는 부호다. 미완료 21단위의 기존 로컬·영역 대체 결과는 바꾸지 않았다. 기존 도움 제안 45개도 보류하여 번체 한자 오류는 279→282로 소폭 악화했다. 전체 CER는 10.6721→10.6134%로 개선됐으나 로컬 후보만 적용한 10.2734%보다 높다. 사람 확정 0건의 평가용 적용이며 신규 유료 API 호출·v8 프롬프트 실제 효과 시험은 하지 않았다. 독립 검증 자료·문헌 전체 품질로 일반화하지 않는다.

원본 한자 보호 수정의 최종 회귀 검사는 **80개 모듈·1,331개 통과**, 실패·오류·건너뜀·미완료 0개다(`work/ocr-safety-replay-v2/regression-final/summary.json`). 소스 실행 자체 검사 27개와 런타임 Ruff도 통과했다. 아래 77개 모듈·1,290개는 수정 전 0.11.0의 역사적 검증 수치다.

0.11.0의 로컬 후보는 `comparison_refinement.py`, 편집 탭은 `comparison_refinement_ui.py`가 담당한다. 현재 교정문과 양쪽의 유일한 정확 원문, 실제 OCR 좌표를 확인하며 GLM에 글자 좌표를 만들어 넣지 않는다. 세로쓰기 자동 영역은 검증 전이므로 보류한다. 영역 계획은 원본·픽셀·잘라낸 PNG·부모 판독·실행 조건을 고정하고 완료·실패·미완료 원시를 따로 저장한다. 후보 채택만 사람의 `edits`와 `refinement_decisions`를 변경한다.

`gpu_queue.py`는 PC 공통 FIFO와 취소 가능한 GPU 임대를, `worker_sessions.py`와 `RecognitionSession`은 전용 작업자·서버 재사용을 담당한다. 기본 8회 뒤 임대를 반납하고 다음 요청은 다시 대기한다. 설정·모델·장치가 바뀌면 같은 세션을 계속 쓰지 않는다. `run_pages`는 같은 엔진으로 여러 쪽을 연속 처리하며 각 결과를 저장한다. 개인 재평가 자료와 실패·복구 증거는 `work/refinement-validation`, 실제 합성 GPU 재사용 증거는 `work/gpu-session-validation`에 보관한다. 새 평가와 배포 완료 상태는 최종 릴리스 기록으로 확인한다.

0.11.0 최종 회귀 검사는 **77개 모듈·1,290개 통과**이며 실패·오류·건너뜀·미완료는 없다(`work/refinement-validation/regression-final-v3`). 같은 자료의 어려운 영역 240회 재판독을 모두 완료했고 원시 결과와 조건·부모 판독을 보존했다. AI가 로컬 후보를 생략한 것은 승인이 아니며, 평가의 AI 완료 단계에는 원래 기준문에 AI가 명시적으로 제안한 변경만 적용한다. 실제 문자 오류율·원래 맞던 글자의 손상·미완료를 포함한 범위는 개인 평가 보고서를 따른다. 전용 로컬 빌드는 `work/windows-refinement-0.11.0`, 산출물은 `dist/0.11.0`이며 GitHub 신규 공개 여부와 구분한다.

모델 묶음은 권장·기존 세 개·전체 여섯 개·주력 하나다. 새 쪽만 문서 종류별 주력을 적용하고 기존 파일의 기준 판독·교정은 보존한다. AI는 같은 조건으로 정상 완료된 판독 세 개 이상을 사용한다. GLM의 좌표 없음과 Surya의 블록 좌표를 구분하고 생성 미완료 원시는 보존하되 비교·AI 기준에서 제외한다. 중지 시 전용 모델 서버도 정리한다. 새 설치는 독립된 `tools` 환경에 두며 원래 AB_OCR 소스·실행 환경을 수정하지 않는다.

최종 120단위·66,463자 비교에서 혼용 Surya, 번체·간체 GLM-OCR을 한글·한자 귀속 오류율 기준으로 선정했다. 번체 전체 CER는 EasyOCR가 더 낮으므로 GLM·Surya·EasyOCR를 권장 비교로 둔다. 혼용은 Surya·GLM·Tesseract다. 세로쓰기는 측정하지 않아 종전 Tesseract/세 엔진 기준을 유지한다. 개인 측정 자료는 `work/new-engine-comparison`, 로컬 0.10.0 빌드는 `work/windows-multi-engine-0.10.0`, 산출물은 `dist/0.10.0`이다.

0.9.1은 실제 0.9.0 시험에서 관측한 AI 응답 잘림과 숫자 위치 오류를 수정하는 로컬 수정판이다. 작은 요청·명시적 Gemini 사고량·출력 예산·문자 위치표와 단계별 응답 형식을 사용하고, 같은 승인 대상 내 유일한 정확 인용에 한해 위치를 복원한다. 원본 응답·복원 근거·사용자 결정을 분리하며 잘린 JSON이나 모호한 인용을 자동 복구하지 않는다. 새 기록은 재열기에서 원시 응답·계약·파생 제안의 의미도 재검증한다. 실제 재평가 산출물은 Git에서 제외한 `work/ai-review-fix-validation`에 보존한다. 로컬 0.9.1 빌드는 `work/windows-ai-review-0.9.1`, 설치 파일·포터블은 `dist/0.9.1`에 둔다. 공개 배포 완료 여부와 실제 정확도 측정은 아래 0.9.0의 과거 기록과 구분한다.

AB 코드의 원본 파일 해시는 `docs/AB_OCR_PROVENANCE.json`에 기록했다. 원래 AB_OCR 프로젝트는 수정하지 않는다. 연어OCR 코드는 다른 프로젝트의 Python 소스를 가져오지 않는다. 현재 개발 PC에서는 기존 AB 설치의 공개 모델·별도 실행 환경만 재사용한다. 설치판은 개발용 형제 프로젝트 탐색을 하지 않는다.

통합 전 AB_OCR 0.3.0의 공개 소스 52개와 파일 해시 목록은 `references/AB_OCR_0.3.0`에 보존한다. [보존 안내](../references/README.md)를 확인한다. `references`는 기록과 비교를 위한 비활성 소스 사본이며 런타임 import 경로가 아니다. 앱이 사용하는 통합 코드는 루트의 `ab_ocr`와 `yeone_ocr/comparison*.py`다. 보존 사본은 소스 ZIP에 포함하고 개인 문서·판독 기록·엔진 실행 환경·모델 가중치는 제외한다.

## 지켜야 할 데이터 정책

- 원본 PDF·이미지와 기존 연어 판독 기록을 새 비교 작업으로 덮어쓰지 않는다.
- 각 엔진의 원시 Unicode·부호·좌표와 모델 해시를 보존한다. 공백 차이 분류도 원문 수정으로 연결하지 않는다.
- 교정문, 수정 전후·시각·사유·되돌리기, 후보 결정, 사람이 확인한 검수 상태를 별도 이력으로 저장한다.
- 여러 엔진의 같은 결과를 자동으로 정답 처리하지 않는다. 한국어 모델의 한자 누락과 중국어 모델의 한글 미지원을 판단에서 제외한다.
- 기존 연어 기록은 과거 정규화가 적용됐을 수 있다. 원래 JSON과 가져오기 출처를 함께 남긴다. AB 이전 인식·교정 상태도 스냅샷으로 보존한다.
- 저장은 임시 파일·fsync·원자적 교체로 수행하고 원본 변경·다른 창의 저장 충돌을 확인한다. 완료한 쪽·엔진의 복구 사본을 유지한다.
- 개인 원본, 판독문, 스크린샷, API 키를 소스·로그·공개 테스트·배포물에 넣지 않는다. 실제 문서 검증 결과는 Git에서 제외한 `work` 아래에 둔다.

로컬 세 엔진 인식은 외부 전송 없이 실행한다. 별도 AI 검증 실행은 현재 설정의 제공사·모델과 선택한 문서·쪽 범위·번체자·중문부호 정책만 사용한다. 실제 전송 계획을 확인한 뒤 두 단계로 실행하고, AI 응답·제안은 `ai_reviews`, 사용자의 결정은 `ai_decisions`와 `edits`에 분리한다. 기존 AI 판독의 전역 취소·호출 상한·프롬프트를 변경하지 않는다. 공급사·모델 자동 대체나 사용자 확정 없는 교정문 덮어쓰기를 추가하지 않는다.

## 검증과 현재 상태

새 테스트는 `tests/test_comparison*.py`, `tests/test_local_runtime.py`에 있다. 원문·좌표·원본 변경·저장 충돌·복구·취소·이력·내보내기 문자 보존, 실제 SDK의 오프라인 HTTP 직렬화, AI 응답 형식·범위·세대·근거 계보와 사용자의 결정 보존을 확인한다. 기존 테스트는 세로 판독, 책갈피 대조, 이미지·캡처 처리, HWPX·검색 PDF와 설치판 실행 경계를 포함한다. 간체·번체·한글 한자 혼용의 실제 로컬 인식 검증과 AI 모의 응답 동작 검증은 구분한다. 전체 테스트 결과와 로컬 배포 상태는 `docs/release-notes.md`를 확인한다.

```powershell
python -B -X utf8 tools/check_regression.py
python -B -X utf8 -m yeone_ocr compare-engines "D:\문헌\원본.pdf" --pages 1 --profile traditional --direction horizontal --work "D:\문헌\작업" --engine-root "D:\OCR엔진"
```

0.9.0 기능 통합 기준 검증은 61개 모듈·고유 테스트 1,080개 통과이며, 공개 소스 정리와 추가 검사 뒤의 최종 결과는 [릴리스 기록](release-notes.md)에 이어 기록한다. Windows 배포판은 `tools/build_windows.ps1`로 만들며 소스·설치용 실행 파일·포터블에서 각각 오프라인 자체 검사 26개를 통과했다. 두 실행 파일의 앱 모듈 각각 75개, 리소스 17개, 라이선스 참조 162개의 일치를 확인했다. 문서·소스가 바뀌면 재빌드하고 이 검사를 다시 실행한다.

배포 파일은 `dist/0.9.0`, 빌드 보고서는 `work/windows-ai-0.9`에 둔다. 공개 소스 커밋에서 소스·라이선스 ZIP과 `update.json`·SHA-256 목록을 만들고, 배포 후 [v0.9.0 다운로드 주소](https://github.com/kyengilam-coder/YeonE_OCR_release/releases/tag/v0.9.0)에서 확인한다. 문서의 링크만으로 공개 완료를 판단하지 말고 실제 GitHub 릴리스와 자산·해시를 확인한다. 이전 0.8.0·0.7.x의 검증·배포 기록은 역사로 보존한다. 소스에서 실행하는 방법은 README를 따른다.

AI 연결의 동작 검증과 실제 인식 정확도 평가는 구분한다. 유료 제공사·모델·문서 범위가 별도로 선택되지 않은 개발 시험은 모의 응답을 사용한다. 실제 AI 판독 정확도와 세로·복잡한 표의 품질은 대표 원본과 독립 정답으로 추가 측정해야 한다. 교정 제안을 최종 정답으로 자동 확정하지 않는다.
