# 인식률·속도 개선 방안 (1.1.0 기준)

1.1.0 소스를 읽고 쓴 제안서입니다. **아래 세 가지만 코드에 넣었고(각 절에 "적용함"으로 표시), 나머지는 아직 제안입니다**: 신뢰도 문턱의 척도(2.1) · 공백뿐인 불일치를 자동 검증 대상에서 제외(2.5 의 첫 항목) · 프로젝트 저장의 즉효 방안(3.2). 같은 시기에 한 화면 개편은 [릴리스 기록](release-notes.md) 맨 위에 따로 적었습니다.

이전 연구 세 편([인식률 제고 방안](인식률_제고_방안.md) · [정확성·안전성·신속성 검토](정확성_안전성_신속성_검토.md) · [한 번에 인식 개선 연구](한번에인식_개선_연구.md))은 0.6.x 의 "AI 전체 쪽 판독" 경로를 다뤘습니다. 1.1.0 의 기본 경로는 **로컬 엔진 먼저 → 어려운 구간만 AI 검증**이고, 이 경로는 그 연구들의 개선(3차 눈가림 · 합의 의심 · ultra_high)을 거치지 않습니다. 그래서 이 문서는 로컬 우선 경로를 중심으로 다시 봤습니다.

## 0. 접근 방법 — 세 갈래로 보고 겹치는 결론만 채택

| 갈래 | 한 일 | 한계 |
|---|---|---|
| A. 코드 정독 | `ab_ocr/` 전체, `yeone_ocr/local_first.py` · `automatic_ocr.py` · `comparison*.py` · `cli.py` 의 실행 경로를 끝까지 따라 읽음 | 읽은 것만 말할 수 있음 |
| B. 저장된 실측 | `docs/benchmarks/real-corpus-0.11.0-20261024.json`(실제 문헌 76쪽 · 엔진 판독 287건)의 CER·쪽당 시간을 코드와 대조 | 가로쓰기 인쇄본 300dpi · 1회 시행. 세로쓰기·스캔·촬영본 수치는 없음 |
| C. 재현 실험 | 엔진 없이 돌릴 수 있는 부분(검증 대상 선정 · 입력 해상도 · 누락 감지 · CPU 쪽 단계)을 합성 입력으로 직접 실행 | OCR 엔진 · API 키 · GPU 가 없어 **실제 인식률과 엔진 추론 시간은 새로 재지 못함** |

세 갈래가 같은 곳을 가리킨 것을 위 순위에 두었습니다. 한 갈래에서만 나온 것은 "측정 필요"로 표시했습니다.

## 1. 결론 먼저

**인식률**: 로컬 우선 경로의 본문은 쪽마다 고른 로컬 엔진 **하나**의 판독 그대로입니다(AI 답은 제안으로만 저장). 그래서 인식률은 ① 어느 엔진이 후보에 드는가 ② 쪽별 선택이 맞는가 ③ 읽기 순서 ④ 입력 픽셀 ⑤ 의심 구간이 실제로 AI·사람에게 올라가는가 — 다섯 곳에서 정해지고, 다섯 곳 모두에서 손실을 확인했습니다. 그중 하나는 **확정 버그**입니다(신뢰도 척도 불일치 — 2.1).

**속도**: 벽시계는 로컬 엔진 추론이 지배합니다. 실측에서 자동 선택은 쪽당 평균 75.8초, PP-OCRv6 하나는 18.5초였습니다. 엔진을 전부 차례로 돌린 뒤 하나를 고르는 구조가 가장 큰 비용입니다.

| 순위 | 방안 | 겨냥 | 근거(갈래) | 위험 · 선행 조건 |
|---|---|---|---|---|
| 1 | 신뢰도 문턱의 척도를 맞춤(0–1 → 0–100) + 공백뿐인 불일치는 검증 대상에서 뺌 | 저신뢰 구간이 AI 검증으로 가지 않음 | A · C(재현) | 고치면 검증 대상이 늘어 호출 상한 배분(2.5)과 함께 다뤄야 함 |
| 2 | 우선 엔진 하나를 먼저 돌리고, 실패 신호가 있을 때만 다음 엔진 | 쪽당 시간(75.8초 → 18.5초 수준, 추정) · 선택 오류 | A · B | 엔진 우선순위는 문헌마다 다를 수 있어 고정 기준으로 재측정 |
| 3 | 가로쓰기 다단 읽기 순서 재구성 | 2단 쪽의 CER 89–94% | A · B | 표·주석 섞인 쪽의 오정렬 — 같은 기준 문헌으로 전후 비교 |
| 4 | 혼용(한글·한자) 문서에 Surya · GLM-OCR 을 후보로 | 혼용은 Tesseract 하나뿐 | A · B(별도 120단위 비교) | GPU · 별도 설치 필요. 세로쓰기 실측이 먼저 |
| 5 | 세로쓰기 누락 감지(열 방향 투영) | 통째로 빠진 열이 표시되지 않음 | A · C(재현) | 괘선·도판 오탐 → 쪽당 상한 |
| 6 | 원본 해상도 보존(내장 스캔을 300dpi 로 다시 그리지 않음) | 600dpi 스캔이 반으로 줄고, 사진 폴더는 실패 | A · C(재현) | 좌표계 — 미리보기와 같은 틀 유지 |

## 2. 인식률

### 2.1 [확정 버그] 신뢰도 척도 불일치 — 저신뢰 구간이 AI 검증에 올라가지 않음

- **지금**: `yeone_ocr/comparison_ai.py` 의 엔진별 문턱은 0–1 척도입니다(`rapidocr .85` · `easyocr .55` · `ppocrv6 .85` · `paddle_server .85`). 그런데 워커는 0–100 으로 저장합니다(`ab_ocr/rapidocr_worker.py` 의 `float(score) * 100` — PP-OCRv6 도 같은 함수, `ab_ocr/easyocr_worker.py` 의 `float(confidence) * 100`). `comparison.py` 와 `local_engines.py` 의 검증도 0–100 범위입니다. Tesseract(70.0)만 맞습니다.
- **재현**: 워커가 내는 값 그대로 40.0 을 넣으면 검증 대상 0건, 같은 값을 0.4 로 넣으면 `low-confidence-ppocrv6` 1건. 시험은 0–1 가짜 값을 써서 통과하고 있습니다.
- **영향**: 설치판 기본인 PP-OCRv6 단독 구성에서는 `□` 같은 깨진 글자가 없는 한 검증 대상이 0이 되어 "API 필요 없음"으로 끝납니다. 워커가 `text_score 0.0` 으로 저점수 줄을 모두 남기므로 도판·얼룩에서 나온 줄도 표시 없이 본문에 들어갑니다.
- **적용함**: 문턱을 워커와 같은 0–100 척도로 옮겼습니다(`LOW_CONFIDENCE_BELOW` — RapidOCR · PP-OCRv6 · PaddleOCR 서버형 85.0 · EasyOCR 55.0 · Tesseract 70.0). 시험의 가짜 판독도 0–100 으로 고치고, 워커가 실제로 내는 값으로 저신뢰 대상이 생기는지 확인하는 시험을 넣었습니다. **문턱 값 자체는 예전 값을 척도만 바꾼 것**이라 실측으로 다시 정해야 합니다.
- **달라지는 점**: 지금까지 "API 필요 없음"으로 끝나던 쪽에서 저신뢰 구간이 검증 대상에 오릅니다. 같은 호출 상한(기본 20회)에서 대기로 남는 쪽이 늘 수 있습니다.

### 2.2 [구조] 엔진을 다 돌린 뒤 고르는 자동 선택이 "항상 PP-OCRv6"보다 나쁨

- **지금**: `automatic_ocr.py` 의 점수는 `.35 품질 + .20 다른 엔진과의 일치 + .10 길이 + .15 문자 종류 + .20 검출 면적 − .10 중복`. 일치 점수는 같은 계열·약한 엔진끼리 서로 올려 주고, 신뢰도는 쓰지 않습니다.
- **실측**: 75쪽 중 45쪽만 오류가 가장 적은 엔진을 골랐습니다(중국어 59쪽 중 33쪽). 번체 55쪽에서 자동 선택 37.49% · PP-OCRv6 36.16%. 초창결에서는 PP-OCRv6 4.15%(지원하는 51쪽) · 자동 선택 7.87%(56쪽 전체 — 쪽 집합이 달라 그대로 견줄 수는 없음).
- **방안**: 우선 엔진을 기본으로 두고 휴리스틱은 **실패 감지**에만 씁니다 — 빈 판독, 길이가 기대의 70% 미만, 깨진 글자가 있을 때만 다음 엔진으로. 3.1 의 속도 방안과 같은 변경입니다.

### 2.3 [구조] 가로쓰기 다단의 읽기 순서를 다시 짜지 않음

- **지금**: 열 정렬은 세로쓰기에만 있습니다(`ab_ocr/reading_order.py`). 가로는 엔진이 낸 줄 순서 그대로이고, Tesseract 는 `comparison.py` 가 PSM 6(한 덩어리)으로 고정합니다.
- **실측**: 2단 문헌(의방집해 10쪽)은 모든 엔진이 89–94%. 채점할 때만 단을 다시 정렬하면 EasyOCR 10.66% · PP-OCRv6 16.26% · RapidOCR 17.54% 로 떨어집니다. Tesseract 는 줄 자체를 두 단에 걸쳐 읽어 51.72%.
- **방안**: 줄 상자의 x 구간으로 단을 나누고 단 안에서 위→아래로 정렬(세로쓰기 열 묶기의 좌우 대칭). Tesseract 는 가로에서 PSM 3·4 를 시험. 개발 정리 문서가 "우선 개선"으로 적었지만 1.1.0 에 들어가지 않은 항목입니다.

### 2.4 [구조] 혼용 문서는 Tesseract 하나뿐 — 더 정확했던 엔진이 후보에 없음

- **지금**: `automatic_ocr.py` 의 후보는 `("ppocrv6", "rapidocr", "easyocr", "tesseract")` 이고, 프로필이 혼용이면 Tesseract 말고는 모두 뺍니다. `ab_ocr/engine_registry.py` 는 주력을 혼용 Surya · 번체/간체 GLM-OCR 로 정해 놓았지만 이 경로는 그 목록을 쓰지 않습니다.
- **실측**: 가로 혼용 17쪽에서 Tesseract 34.57%. 별도 120단위 비교([로컬 엔진 비교](LOCAL_ENGINE_COMPARISON.md))에서 혼용 오류율은 Surya 2.0% · Tesseract 20.0%.
- **방안**: 설치돼 있으면 등록부의 권장 엔진을 후보에 넣습니다. GLM-OCR 은 좌표가 없으므로 기준 판독이 아니라 비교 증인으로. 프로그램의 주 용도인 **세로쓰기 혼용은 실측이 전혀 없으므로** 기준 문헌을 먼저 만들어야 합니다.

### 2.5 [재현] 검증 대상 구성 — 공백 차이도 유료 호출, 쪽 단위로 전부 아니면 전무

- **지금**: 엔진끼리 줄바꿈·공백만 달라도 제안이 되고(`kind: "whitespace"`), 검증 대상은 종류를 가리지 않습니다. 대상 1개가 호출 1회(`batch_size=1`)이고, 한 쪽의 호출 수가 남은 상한을 넘으면 그 쪽 전체가 대기로 남습니다. 상한 기본값은 실행 전체 20회.
- **재현**: 글자는 같고 줄바꿈만 다른 두 판독에서 대상 6건(공백 4 · difflib 부산물 2).
- **적용함**: 자동 선택 검증에서 공백뿐인 불일치(`kind: "whitespace"`)는 대상에서 뺍니다. 제안은 비교·교정 창에 그대로 남고, 사람이 그 항목을 직접 골라 검증을 요청하면 이전처럼 보냅니다.
- **남은 방안**: 위험 순(글자 불일치 → 저신뢰 → 누락)으로 정렬해 남은 예산만큼만 보냄. 한 호출에 여러 대상을 묶음(`batch_size` 는 4까지 허용됨).

### 2.6 [재현] 세로쓰기에서 통째로 빠진 열을 찾지 못함

- **지금**: 누락 감지는 행 방향 투영으로 먹 띠를 만들고, 인식된 상자와 겹치지 않는 띠만 누락으로 봅니다. 세로쓰기에서는 모든 행 띠가 인식된 열과 겹칩니다.
- **재현**: 세로 3열 중 가운데 열을 놓친 쪽 → 대상 0건. 가로에서 한 줄을 놓친 쪽 → 1건 검출.
- **방안**: 세로쓰기는 열 방향 투영. `layout.uncovered_ink_boxes` 가 이미 있어 다시 쓸 수 있습니다.

### 2.7 [재현] 로컬 경로는 원본 해상도와 무관하게 300dpi 로 다시 그림

- **지금**: AI 전체 판독 경로는 내장 스캔 비트맵을 그대로 쓰지만, 로컬 경로는 `ab_ocr/ocr.py` 가 쪽을 `get_pixmap(dpi=300)` 으로 다시 그립니다.
- **재현**: 600dpi 스캔(4960×7016) → 2481×3509 로 절반. 96dpi 태그 화면 캡처 → 3.12배 확대. 72dpi 태그 휴대전화 사진(3024×4032) → "페이지가 너무 큽니다" 오류로 실패.
- **방안**: 쪽을 꽉 채운 내장 이미지는 그 비트맵의 해상도로(판단 코드는 `pdfio` 에 이미 있음). 쌍행소주 같은 작은 글자에 영향이 클 것으로 보이나 크기는 측정이 필요합니다.

### 2.8 그 밖 — 측정이나 정책 결정이 먼저인 것

- **기본 프로필**: `--local-profile` 기본이 번체이고 읽기 방향과 연동되지 않습니다. 세로 혼용 책을 기본값으로 돌리면 한글이 오독됩니다. 번체 판독에 한글이 일정 비율 이상 나오면 경고하는 것부터.
- **한자 수정 제안의 채택 조건**: 기준 외 두 계열이 같은 자리에서 동의해야 채택할 수 있습니다. 엔진이 하나인 구성(혼용 · PP-OCRv6 단독)에서는 AI 가 맞는 글자를 내도 보류로만 남습니다. 의도된 보수성이므로 풀려면 정밀도를 먼저 재야 합니다.
- **AI 검증 조각**: 확대 없이 보내고 후보·앞뒤 문맥을 함께 줍니다. AI 전체 판독의 3차는 0.6.5 에서 문맥에 끌린 오확정을 막으려고 문맥을 숨기고 6배 확대하도록 바꿨습니다. 같은 방식을 한두 글자 불일치에 쓰는 것을 실측으로 비교.
- **Tesseract 입력**: 기울기 보정 · 괘선 제거 · 이진화 없이 렌더 그대로. 혼용 기준 문헌으로 A/B.
- **EasyOCR 세로 글자 분할**: 획 사이가 넓은 글자(二 꼴)를 둘로 쪼갭니다(재현). 조각 높이가 폭보다 훨씬 작으면 이웃과 합치도록.

## 3. 속도

**측정 조건.** 엔진 추론 시간은 저장된 실측(`docs/benchmarks/real-corpus-0.11.0-20261024.json` — Core Ultra 7 265K · 32GB · 300dpi · 1회 시행 · 가로쓰기 인쇄본)을 그대로 옮겼습니다. 그 밖의 숫자는 이 분석 환경(4코어 Linux · Python 3.12)에서 **엔진을 0초짜리 가짜로 바꾸고** 실제 `run` 명령을 합성 스캔 PDF(A4 300dpi · 쪽당 1.7MB)로 돌려 잰 것입니다 — "합성 실측"으로 적었습니다. 엔진·GPU·API 가 없어 추론과 API 지연은 새로 재지 못했고, 절감량 가운데 재지 못한 것은 "추정"으로 적었습니다.

### 3.0 결론

로컬 우선 경로의 시간은 두 곳에서 나갑니다.

1. **엔진을 전부 차례로 돌림** — 저장된 실측에서 자동 선택은 쪽당 평균 75.8초, 그중 57%가 EasyOCR 입니다.
2. **추론 둘레의 반복 작업** — 엔진을 0초로 바꿔도 쪽당 15~40초가 들고, 쪽이 늘수록 커집니다(합성 실측). 대부분이 비교 프로젝트 파일을 매번 통째로 다시 쓰는 데서 나옵니다.

| 저장된 실측 | 쪽당 평균 | 중앙값 | 76쪽 합계 |
|---|---:|---:|---:|

### 3.1 [구조] 엔진을 전부 돌린 뒤 고름

- **지금**: 자동 선택은 언어·방향을 지원하는 설치 엔진을 "한 번에 하나씩" 모두 실행한 뒤 쪽마다 하나를 고릅니다([자동 OCR](AUTOMATIC_OCR.md)).
- **방안**: 2.2 의 계단식 실행. 저장된 실측의 번체 55쪽에서는 PP-OCRv6 단독(36.16%)이 자동 선택(37.49%)보다 나았으므로, 인식률을 잃지 않고 시간을 크게 줄일 가능성이 가장 높은 항목입니다. 읽기 순서가 깨진 2단 문헌에서는 둘 다 93%대라 차이를 말할 수 없고(2.3 을 먼저 고쳐야 함), 혼용은 지금도 Tesseract 하나라 해당하지 않습니다. 다만 다른 엔진이 없으면 엔진 간 불일치 신호도 없어지므로, 2.1 의 신뢰도 문턱 수정이 선행돼야 의심 구간이 계속 표시됩니다.
- **곁들일 것**: EasyOCR 작업자의 `--threads` 기본값이 2이고 호스트가 값을 넘기지 않습니다(`ab_ocr/easyocr_worker.py`). 코어 수에 맞춰 넘기면 EasyOCR 시간이 줄 것으로 보이나(추정 · 미검증) 스레드 수가 결과를 바꾸지 않는지 고정 기준으로 확인해야 합니다.

### 3.2 [성능 결함] 비교 프로젝트 전체를 체크포인트마다 다시 씀

- **지금**: `yeone_ocr/local_first.py` 가 엔진 결과마다, 쪽 끝마다, API 호출마다 `project.save()` 를 부릅니다(합성 실측 쪽당 약 5회). `comparison.py` 의 `save` 는 매번 전 쪽을 `deepcopy` 하고, `json.dumps(indent=2)` 로 직렬화하고, 기존 파일 전체를 두 번 다시 읽어 파싱합니다.
- **합성 실측**: 53.6MB 프로젝트에서 저장 한 번 3.76초(복사 0.61 · 직렬화 1.18 · 다시 읽기 약 1.4). 40쪽 실행에서 쪽당 저장 시간이 3.2초 → 28.5초로 늘었고, 전체 1,095초 가운데 614초가 저장이었습니다.
- **저장된 실측과의 대조**: 실제 문헌 56쪽 · 판독 219건의 프로젝트가 103MB(쪽당 1.84MB), 저장 한 번 3.93초(더 빠른 PC). 같은 밀도면 **약 140쪽에서 `MAX_BYTES = 256_000_000` 을 넘어 저장이 실패**합니다(추정 — 엔진 수가 적으면 쪽당 크기도 작아 더 늦게 닿음). 상한을 8MB 로 줄여 재현하면 이후 모든 쪽이 "프로젝트가 허용 크기를 넘습니다"로 실패했습니다.
- **적용함(즉효 방안)**: 복사 없이 락 안에서 바로 직렬화하고 들여쓰기를 뺍니다. 기존 파일은 바이트의 SHA 가 이 창이 마지막으로 읽거나 쓴 것과 같으면 파싱하지 않고, 다르면 이전처럼 파싱해 "다른 창에서 변경" · "다른 프로젝트"를 가립니다. 같은 53.6MB 프로젝트에서 저장 한 번이 3.76초 → 0.43초, 파일 크기는 34%(53.6MB → 18.3MB)가 됐습니다. 들여쓰기가 있는 예전 파일은 그대로 열리고, 다시 저장하면 새 형식이 됩니다. 저장되는 값은 같습니다.
- **남은 한계**: 여전히 저장할 때마다 전체를 다시 쓰므로 쪽 수에 따라 커지는 성질은 남습니다(기울기만 약 9분의 1). 256MB 상한에 닿는 쪽 수는 약 3배로 늦춰집니다(추정).
- **근본 방안**: 쪽별 파일(또는 덧붙이는 저널) + 색인. 한 쪽 직렬화는 0.02초입니다.
- **위험**: 인식 결과에는 영향이 없습니다. 파일 형식과 "다른 창이 그 사이 바꿨는가" 검사를 건드리므로 회귀 시험이 필요합니다.
- **같은 뿌리**: 비교·교정 창이 글자를 고칠 때마다 복구본을 같은 방식으로 창 스레드에서 씁니다(`comparison_editor.py` — 53.6MB 에서 2.0~3.4초 멈춤, 합성 실측).

### 3.3 [성능 결함] 자형 검증 은행을 프로세스마다 다시 만듦

- **지금**: `ab_ocr/glyph_verifier.py` 가 CJK 통합·확장A 전 글자 × 글꼴 2종을 파이썬 루프로 그립니다. 중국어 가로 쪽마다 RapidOCR 작업자 · EasyOCR 작업자 · Tesseract(창 프로세스 안)에서 한 번씩 만들어집니다.
- **합성 실측**: 한 번 22.1초(Noto CJK 글꼴 · 이 환경). 같은 행렬을 `.npy` 로 읽으면 0.07초.
- **방안**: 글꼴 SHA · 정책 · 그리는 라이브러리 판을 열쇠로 사용자 데이터 폴더에 캐시. 행렬이 같으면 결과도 같습니다.
- **주의**: Windows 글꼴(simsun · msjh)로는 재지 못했습니다. 저장된 실측에서 번체 쪽이 혼용 쪽보다 엔진당 7~8초 더 걸리는 것이 이 몫인지는 분리해 확인하지 못했습니다.

### 3.4 [구조] 쪽·엔진마다 새 프로세스로 모델을 다시 올림

- **지금**: 로컬 우선 경로는 쪽마다 엔진 작업자를 단건으로 실행합니다. 세션(상주 작업자) 구조는 있지만 이 경로가 쓰지 않고, PP-OCRv6 · EasyOCR 작업자에는 세션 모드(`--session-root`)가 없습니다(RapidOCR · GLM-OCR · Surya 에는 있음). [개발 정리](DEVELOPMENT_CHECKPOINT_0.11.0.md)도 "쪽마다 모델을 새로 로드한다"고 적었습니다.
- **방안**: 두 작업자에 세션 모드를 넣고 쪽 루프 밖에서 유지. 메모리가 부족하면 몇 쪽 단위로 엔진을 바꿔 가며.
- **절감**: 엔진당 2~6초로 봅니다(추정 — 엔진이 없어 재지 못함). 상주 메모리가 늘어납니다(실측 최대: EasyOCR 6.8GB · PP-OCRv6 4.1GB).

### 3.5 [합성 실측] 같은 쪽을 6~9번 렌더하고 PNG 로 다시 씀

- **지금**: 엔진마다 PDF 를 다시 열어 렌더하고 PNG 로 씁니다. 기록 저장과 검증 계획이 한 번씩 더, 검증 호출마다 또 한 번 렌더합니다.
- **합성 실측**: 300dpi 스캔 한 쪽의 렌더 + PNG 가 1.64초(렌더 0.10 · PNG 쓰기 1.53). 네 엔진 기준 쪽당 약 11.6초. PNG 압축 수준을 6 → 1 로 낮추면 1.50초 → 0.44초이고 크기는 같았습니다(무손실).
- **방안**: 쪽당 한 번만 렌더해 모든 엔진 · 계획 · 조각이 그 한 장을 쓰게. AI 전체 판독 경로에는 이미 들어가 있는 최적화입니다.
- **주의**: 검증 조각의 PNG 바이트는 계획 지문에 들어가므로 그 압축 수준은 그대로 둬야 완료한 검증을 재사용합니다. 편집·출력 PDF 는 스캔보다 PNG 가 싸서 절감이 작습니다.

### 3.6 [합성 실측] 그 밖의 반복

- **끝난 쪽 재처리**: 완료된 12쪽을 그대로 다시 실행(OCR 0회 · API 0회)하면 242.6초, 쪽당 20.2초. 손대지 않은 기록도 렌더 · 계획 · 저장을 다시 탑니다. 조건 지문이 같고 상태가 최종이면 바로 건너뛰게.
- **원본 전체 해시**: 쪽당 약 28회. 204MB 원본에서 쪽당 약 4초이고 파일 크기에 비례합니다. 모델 파일에 이미 쓰는 "경로 · 크기 · 수정 시각" 캐시를 원본에도. 크기와 수정 시각을 보존한 변조는 중간 검사에서 놓치므로 안전 정책 판단이 필요합니다.
- **검증 계획**: 대상마다 쪽 전체를 복사합니다(프로파일에서 쪽당 86회). 호출 상한을 넘는 쪽도 조각 이미지를 다 만든 뒤 버립니다. 쪽당 5.6~11.6초.
- **검증 호출의 부대 비용**: API 를 0초로 바꿔도 호출당 6.4초(저장 3.5 · 재렌더 1.8 · 범위 검사). 3.2 · 3.5 를 고치면 함께 줍니다.
- **문서 만들기**: 자를 도판이 없어도 모든 쪽 PNG 를 디코드합니다(20쪽 3.84초 중 3.3초).

### 3.7 이미 잘 된 것

- 주 창은 큐로 받아 그리고, 수치 세기 · 쪽 띠 · 표 채우기는 작업 스레드에서 합니다. 무거운 모듈은 늦게 불러 창 모듈 import 가 0.15초입니다.
- AI 전체 판독 경로에는 동시 판독(4 → 8 자동 조절) · 준비 병행 · 빠른 PNG · 3차 묶음·병렬이 들어가 있습니다. 이전 연구의 속도 권고 가운데 남은 것은 "1차 생각 수준 낮춤"과 "3차 flash 우선"(둘 다 선택지만 있고 기본은 아님 — 정확도 실측이 먼저)입니다.
- 엔진 판독끼리의 정렬·비교는 쪽당 수십 ms 로 병목이 아닙니다.
