# 로컬 우선 인식과 선택 구간 AI 검증

현재 개발 소스의 **일반 OCR·이미지 OCR·`run` 기본 경로는 `local-first`**다. 로컬 엔진으로 먼저 읽은 뒤 AI 사용 설정을 적용한다. 사용 가능한 구독 로그인이 있고 구독 계정 판독을 켜 둔 기본 설정에서는 **쪽 전체 AI 판독(`prefer`)과 검증 제안 자동 반영**도 동작한다. 구독 자동 경로를 사용하지 않는 기본 구성에서는 의심 구간만 검증하고 제안은 사람이 채택한다. 명시한 옵션이 자동 기본값보다 우선한다. 이전 전체 쪽 AI 처리 방식 `--ocr-strategy ai-full`과 로컬 우선 경로의 추가 쪽 판독 `--local-ai-page`는 서로 다른 기능이다.

| 원하는 동작 | CLI 설정 | 본문 변경 |
|---|---|---|
| 기본 자동 | `--local-ai-page auto` | 사용 가능한 구독이 있으면 짧은 AI 차이와 확실한 검증 제안을 자동 반영 |
| 의심 구간 제안만 | `--local-ai-page off --no-local-ai-accept` | AI 제안은 사람이 채택; 원시 엔진 판독 보존 |
| 로컬 전용 | `--local-ai-page off --local-ai-auth api --no-local-ai-review` | AI 호출 없음; 별도 출력 정규화 설정은 적용될 수 있음 |

GUI에서 로컬 전용으로 읽으려면 **[구독 계정 판독]과 [로컬 뒤 AI 검증]을 모두 끈다**. 의심 구간 검증만 꺼도 쪽 AI 판독은 남을 수 있다. 구독을 쓸 수 없을 때 다른 구독·유료 API로 넘어가는 기능은 별도 설정이며, API 전환은 `--no-local-ai-api-fallback`으로 끈다.

## 처리 순서

### 기존 결과를 유지하며 미완료 검증만 실행

`run`에 `--local-review-only`를 추가하면 저장된 로컬 판독으로 미완료 구간만 검증한다.
로컬 엔진 재실행, 쪽 전체 AI 재판독, 교정안 자동 적용, PDF/HWPX 재생성을 하지 않는다.
기존 판독 기록과 교정 이력은 유지하고 검증 상태·제안·사용량만 갱신한다.
완료된 쪽은 건너뛰며, 중단한 쪽의 동일한 완료 요청도 다시 보내지 않는다.
새 검증 제안은 비교·교정 창에서 확인하여 채택한다. GUI에서는 실행 카드 또는 설정의
「이어서 할 때」에서 「미완료 검증만 · 기존 결과 보존」을 선택하고 실행한다.

좌표가 없는 기준 판독은 같은 조건으로 완료된 다른 엔진의 단어 좌표를 활용한다.
공백·줄바꿈을 제외한 텍스트 정렬, 고유 문구, 충분한 일치, 좌표 범위와 엔진 간 위치 일치를
확인한 구간만 연결한다. 모호한 구간은 미완료로 유지하며 원시 판독을 덮어쓰지 않는다.
같은 이미지·문맥·모델·정책의 완료 요청은 다른 구간의 추가만으로 무효화하지 않는다.

### 일반 인식

1. 원본·쪽 범위·읽기 방향을 확인한다. 이미지 폴더·붙여넣기 묶음은 작업 폴더 `local-input`에 원본 지문으로 이름을 정한 PDF 사본을 만든다. 원본 이미지를 변경하거나 외부로 보내는 단계가 아니다.
2. 설치·언어·메모리 조건에 맞는 엔진을 실행한다. CPU 엔진은 PP-OCRv6·RapidOCR/v5·EasyOCR·Tesseract이며 자원 여유에 따라 병렬 실행한다. 가로쓰기에서는 EasyOCR을 기본 제외한다. 혼용 문서는 Tesseract를 사용하고, 지원되는 CUDA 엔진이 있으면 자동 선택에 하나를 추가한다(혼용은 Surya 우선). 지원 엔진이 없으면 설치 오류로 기록하며 기존 `ai-full` 경로로 자동 전환하지 않는다.
3. [자동 선택 정책](AUTOMATIC_OCR.md)으로 한 쪽의 로컬 결과 하나를 선택한다. v6 하나만 설치되어 있어도 진행할 수 있다. 원시 결과·직접 교정·사람의 기준 선택을 보존하며, API 호출 전에 로컬 판독을 저장한다.
4. 선택 결과와 호환되는 최신 엔진 결과에서 어려운 구간을 찾는다. 엔진 간 명시적 불일치, 낮거나 없는 confidence, `�`·`□`·`〔판독불명〕` 등 알 수 없는 글자, 좌표 누락, 글자는 검출하지 못했지만 먹이 있는 지역을 대상으로 삼는다.
5. 의심 구간 검증은 원본 크롭과 제한된 문맥을 사용한다. 위험 신호가 없으면 **이 검증 단계의 호출은 0회**지만, 별도로 켜진 쪽 AI 판독은 실행될 수 있다. 좌표를 안전하게 연결할 수 없으면 검수 대기로 남긴다. 의심 구간이 많다는 이유로 이 단계 자체를 전체 쪽 검증으로 확대하지 않는다.
6. 검증 제안은 저장하며, 자동 반영이 켜져 있으면 적용 가능하고 불확실하지 않은 제안을 채택 이력(`actor=auto`)과 함께 반영한다. 꺼져 있으면 사람이 채택한다. 쪽 AI 판독의 `prefer`는 병합 규칙을 통과한 짧은 차이를 출력문에 반영하고 `witness`는 차이를 표시한다. 원시 엔진 판독은 보존한다. HWPX·DOCX·검색 PDF·검수 화면·보고는 저장된 판독으로 만들며, 기존 전체 쪽 1·2차·3차 판별·문서 문맥 모델 경로를 추가로 실행하지 않는다.

AI 검증 완료나 높은 confidence는 사람의 원본 대조 완료를 뜻하지 않는다. 서로 다른 엔진의 confidence를 비교하거나 정확도로 표시하지 않는다.

## 어려운 구간의 기준

confidence 경계는 API로 보낼 구간을 정하는 초기 휴리스틱이며 실측 인식률이 아니다. 선택한 기준 엔진의 자체 척도에서만 판단한다.

| 기준 엔진 | 낮은 confidence |
|---|---:|
| Tesseract | 70 미만, 자체 0–100 척도 |
| RapidOCR/v5 | 0.85 미만, 자체 0–1 척도 |
| PP-OCRv6 | 0.85 미만, 자체 0–1 척도 |
| EasyOCR | 0.55 미만, 자체 0–1 척도 |

confidence가 없는 구간도 검증 대상으로 본다. 일부 자형 보완 결과는 원래 모델 점수를 보존하고 최종 confidence를 `null`로 두므로 이 경로에 포함될 수 있다. 단순 검은 선·그림도 먹 검출에 잡힐 수 있다. 이미지 근거가 불명확하면 AI의 불확실 제안과 사람의 검수 상태를 확인해야 한다.

## 호출 상한과 이어 읽기

`--local-ai-max-calls` 기본값은 **이번 명령 전체의 유료 API 호출 20회**다. 구독에서 API로 넘어간 쪽 판독도 이 상한을 공유한다. 구독 사용량 한도는 별도다. 쪽별 20회가 아니며, `--max-calls`가 양수이면 두 상한 중 작은 값을 함께 적용한다. 완료한 요청은 원본·쪽·선택 기준·모델·정책·크롭 지문으로 재사용한다. **호출 상한만 바꾸거나 다음 실행의 남은 호출 수가 달라져도 완료한 검증을 다시 구매하지 않는다.** 원본·판독·모델·실제 검증 정책이 바뀌면 재검증 대상이 될 수 있다.

API 키가 없어도 로컬 인식·출력은 진행한다. AI 대상이 남거나 호출 상한·검증 실패로 검증을 마치지 못하면 종료 코드 `4`로 알리고 저장된 결과와 검증 계획을 보존한다. 깨끗해서 대상이 없으면 키가 없어도 성공이다. `--no-local-ai-review`는 의심 구간 검증만 끈다. 로컬 전용으로 읽으려면 `--local-ai-page off --local-ai-auth api --no-local-ai-review`를 함께 지정한다. 검수할 곳이 있다는 기록은 보존한다.

| 종료 코드 | 뜻 |
|---|---|
| `0` | 선택한 로컬·AI 작업과 출력 완료. 사람 검수 완료를 의미하지 않음 |
| `3` | 일부 쪽의 로컬 인식 실패. 완료된 쪽과 원시 결과는 보존 |
| `4` | 로컬 결과는 있으나 요청한 선택 구간 AI 검증이 대기·미완료 |
| `2` / `130` | 입력·설정 오류 / 사용자 중지 |

출력 생성 자체가 실패하면 해당 출력 오류 코드가 우선한다. 비교 프로젝트는 작업 폴더 `comparison`, 검증 계획은 `local-first-review`, 상태 집계는 `state.json`의 `local_first_last_run`에 남는다. 원문·AI 응답·제안·사람 채택 이력을 구분해 저장한다.

## 중간에 멈춘 뒤: 읽은 쪽까지 문서 만들기

[한 번에 인식 (HWPX 만들기)]를 [■ 중지]로 멈추면 문서는 만들어지지 않고 판독 기록만 남는다. 그때까지의 기록으로 HWPX를 만들려면:

- 멈춘 직후 묻는 창에서 **[예]**, 또는 실행 카드의 **[읽은 쪽까지 HWPX 만들기]**(판독 기록이 있고 남은 쪽이 있는 책에서만 보임).
- 명령줄: `yeone-ocr build 원본.pdf --no-context-model` (쪽 범위를 주면 그 안의 읽은 쪽만).

판독 기록이 있는 쪽만 문서에 들어가고 파일 이름에 쪽 범위가 붙는다(`이름_p001-193.hwpx`). 모델을 부르지 않는다(문맥 교정 모델 없음 · 요금·사용량 없음). 엔진만 읽고 AI 검증 차례를 기다리던 쪽은 엔진 판독 그대로 들어가고, AI 검증이 보류된 구간은 문서의 확인 표시로 남는다. [HWPX 열기]는 가장 최근에 만든 것을 연다. 남은 쪽은 [한 번에 인식]을 다시 누르면 이어서 읽고, 끝나면 전체 문서(`이름.hwpx`)가 만들어진다 — 부분 문서 파일은 그대로 남는다.

## 명령줄 예

프로젝트 가상환경의 Python으로 실행한다. API 제공사·모델·키 설정은 기존 설정을 사용한다. 키를 명령줄 인수에 넣지 않는다.

```powershell
# 번체 가로쓰기: 로컬 인식 → 어려운 구간만 API → HWPX
.\.venv\Scripts\python.exe -m yeone_ocr run "책.pdf" --local-profile traditional --mode horizontal_zh --work "work\책"

# 로컬 전용. 지원되는 엔진을 설치한 뒤 사용
.\.venv\Scripts\python.exe -m yeone_ocr run "책.pdf" --local-ai-page off --local-ai-auth api --no-local-ai-review --local-engine-root "C:\OCR엔진"

# 한글·한자 혼용 세로쓰기, 검색 PDF, 이번 실행 최대 5회
.\.venv\Scripts\python.exe -m yeone_ocr run "혼용문헌.pdf" --local-profile mixed --mode vertical --pdf-only --local-ai-max-calls 5

# 이전 전체 쪽 AI 판독 경로를 명시적으로 사용
.\.venv\Scripts\python.exe -m yeone_ocr run "책.pdf" --ocr-strategy ai-full
```

엔진 설치·언어 범위는 [로컬 엔진 안내](LOCAL_OCR.md), 제안·개인 자료 저장 정책은 [AI 검증 안내](AI_REVIEW.md)를 함께 따른다.

## 속도: 상주 작업자와 엔진 병렬 실행

- **상주 작업자**: 로컬 우선 인식은 PP-OCRv6·RapidOCR·EasyOCR 작업자를 실행 동안 띄워 두고, 한 작업자로 최대 16쪽을 읽은 뒤 새로 띄웁니다(기존 세션 규약 그대로). 쪽마다 모델을 다시 올리고 모델 파일 해시를 다시 확인하지 않습니다. 가로쓰기 쪽만 해당하며, 세로쓰기 쪽과 Tesseract는 지금처럼 쪽마다 작업자를 띄웁니다(그 결과에 필요한 후처리가 그 경로에 있음). 끄려면 환경 변수 `YEONE_OCR_RESIDENT_WORKERS=0`.
- **엔진 병렬**: 한 쪽의 엔진들을 동시에 실행합니다. 동시 개수는 코어 4개당 엔진 1개, 빈 메모리(이미 떠 있는 작업자 제외)가 가장 무거운 엔진들의 예산을 넘지 않을 만큼입니다. 결과는 늘 엔진 순서대로 기록하므로 프로젝트·비교·선택 결과는 차례로 실행할 때와 같습니다. `--local-engine-parallel N`(0=자동, 1=차례로) 또는 `YEONE_OCR_ENGINE_PARALLEL`로 정합니다.
- **반복 작업 제거**: 한 쪽 렌더 결과를 엔진·미리보기·AI 조각이 함께 쓰고, 원본 해시는 크기·시각·inode가 그대로이고 2초 넘게 바뀌지 않은 파일에만 재사용합니다. 글꼴 해시는 파일마다 한 번, 프로젝트 중간 저장은 저장 자체가 느려지면 30초 간격으로 줄입니다(쪽 끝 저장은 늘 합니다).
- 이 최적화의 최신 전체 처리시간은 동일한 하드웨어·표본·캐시 조건에서 다시 측정해야 합니다. 아래 기록은 개발 당시 표본 결과입니다. 예전에 사용한 `ab_ocr/benchmark.py`는 1.2.17에서 삭제되어 현재 실행할 수 없습니다.

## 긴 책의 증분 저장

원본이 **64쪽 이상**이면 비교 프로젝트를 같은 `.yeone-compare.json` 파일 안의 SQLite 데이터베이스로 저장합니다. 한 쪽을 교정하거나 AI 검증이 끝났을 때, 그 쪽의 원시 판독·교정 이력·AI 응답·채택/기각·검토 상태만 압축하여 갱신합니다. 이미 저장한 다른 쪽을 다시 JSON으로 만들거나 압축하지 않습니다. 작은 문서는 기존 JSON/gzip 저장을 유지합니다.

- 기존 JSON·gzip 프로젝트는 그대로 열립니다. 긴 책을 처음 저장할 때 한 번 전체 내용을 새 형식으로 전환합니다. 전환용 임시 파일을 완성한 뒤 교체하므로, 전환 실패 시 기존 파일이 남습니다. 전환된 파일은 이전 배포판 1.2.17에서 열 수 없으며 이 변경이 포함된 실행본이 필요합니다.
- 이후 저장은 트랜잭션 단위입니다. 저장 오류나 프로세스 강제 종료가 발생하면 마지막으로 완료된 저장으로 복구합니다. 비정상 종료 직후 남은 `-journal` 파일은 다음에 열 때 복구에 쓰이므로 임의로 삭제하지 마십시오. 정상 저장 완료 후에는 프로젝트 파일 하나만 복사·이동하면 됩니다(원본 문서는 별도 유지).
- 정식 저장과 복구 저장은 각각 저장한 쪽의 상태를 추적합니다. 복구 저장은 정식 저장의 미저장 표시를 지우지 않으며, 원본이 사라진 상태에서도 받은 AI 응답과 교정 기록을 보존합니다. 다시 OCR·내보내기를 하려면 원본 검증을 통과해야 합니다.
- 이어하기의 완료 판정, 기존 기준 판독, AI 호출 재사용 정책은 유지합니다. 두 창에서 같은 파일을 수정하면 나중의 오래된 창은 다른 이름으로 저장하도록 안내합니다.
- 메모리 최적화 범위는 **저장 중 전체 책의 JSON 문자열·바이트를 새로 만드는 비용**입니다. 열린 프로젝트의 쪽별 기록은 여전히 메모리에 보유합니다. 쪽 하나의 이력이 매우 길면 그 쪽의 저장 비용은 커집니다. 처음 저장·형식 전환·새 이름으로 저장은 전체 쪽을 한 번 기록합니다.

저장 성능은 `tools/benchmark_comparison_storage.py`로 같은 합성 책과 변경 전 저장 모듈을 사용해 별도 프로세스에서 비교합니다. 실제 OCR·AI 호출은 실행하지 않습니다. 반복 저장 시간과 최초 전환 시간을 구분하고, 저장 중 프로세스 메모리를 외부에서 표본 측정합니다. Python 추가 할당 최대치는 시간 측정과 분리한 `tracemalloc` 실행으로 확인합니다.

### 저장 성능 실측 (2026-11-15)

Windows 11, Python 3.14.5, 논리 CPU 32개인 동일 PC에서 측정했습니다. 각 쪽은 합성 OCR 판독 3개와 교정 이력 2개, 반복 근거 문자열을 담으며, 압축 전 JSON은 각각 80.9/242.7/485.4 MB입니다. 기존 모듈과 변경 모듈이 같은 파일에서 시작해 한 쪽을 수정하고 5회 저장한 중앙값입니다. 최초 전환·불러오기·OCR 실행·저장 결과 재검증 시간은 반복 저장 시간에 포함하지 않았습니다. 시간 측정 중에는 다른 회귀 테스트를 실행하지 않았습니다.

| 책 길이 | 기존 전체 저장 | 쪽별 증분 저장 | 저장 중 추가 Python 할당 최대치: 기존 → 변경 |
|---|---:|---:|---:|
| 100쪽 | 0.231초 | 0.0096초 | 154.32 → 1.49 MiB |
| 300쪽 | 0.671초 | 0.0089초 | 462.95 → 1.49 MiB |
| 600쪽 | 1.366초 | 0.0089초 | 925.89 → 1.49 MiB |

600쪽에서 **저장 중 프로세스 전체 상주 메모리 표본 최대값**은 1,572 → 525 MiB, private 메모리는 1,574 → 522 MiB였습니다. 이는 저장 전부터 보유한 프로젝트 기록까지 포함한 값으로, 위 표의 추가 Python 할당과 다른 지표입니다. 외부 표본기는 2 ms 간격을 요청하지만 Windows 스케줄링 때문에 짧은 피크를 놓칠 수 있습니다. 추가 Python 할당은 별도 `tracemalloc` 실행으로 측정했습니다. OCR 모델·GPU 메모리와 전체 OCR 처리 속도는 이 측정 대상이 아닙니다.

최초 전환은 100/300/600쪽에서 각각 0.250/0.718/1.306초, 추가 Python 할당 최대치는 약 2.32~2.33 MiB였습니다. 600쪽 파일은 기존 gzip 32.62 MiB에서 SQLite 33.17 MiB로 약 1.7% 커졌습니다. 모든 측정에서 다시 연 프로젝트의 전체 쪽·원시 판독·교정 이력이 메모리의 저장 대상과 같은지 확인했습니다. 합성 자료 결과이므로 실제 책의 기록 밀도·디스크·백신 상태에 따라 절대 시간은 달라집니다.

상세 원자료는 작업 폴더 `work/incremental-storage/benchmark-verified/results.json`에 있습니다. 변경 전 모듈의 SHA-256은 `cca73b5b4e3cc85a32d64c3098f5aca82e37056f0bc009d7e0c51ab125a12ca6`이며, 재현 시 다음과 같이 새 출력 폴더를 지정합니다.

```powershell
python -B -X utf8 tools/benchmark_comparison_storage.py --baseline work/incremental-storage/comparison_before.py --output work/storage-benchmark-new --sizes 100 300 600 --repeats 5
```

검증은 전체 회귀 156개 모듈·2,655개 테스트가 실패·건너뜀 없이 통과했습니다. 이후 복구 저널 경로의 원본 보호를 보강하고 관련 저장·호환성·원자적 교체 테스트 24개를 다시 통과했습니다. 증분 저장 테스트에는 기존 JSON/gzip 전환, AI 채택·기각과 수동 교정 이력, 실제 프로세스 강제 종료 후 복구, 롤백 후 재시도, 두 창의 충돌, 원본 재연결, AI 응답 직후 중단·이어하기가 포함됩니다. 증거는 `work/incremental-storage/full-final/summary.json`, `work/incremental-storage/journal-fixed/summary.json`, `work/incremental-storage/final-journal/summary.json`에 보관합니다.

## 그래픽카드(CUDA) 엔진의 자동 선택 참여

- CUDA로 설치·활성화한 **Surya**(`scripts/install_surya_cuda.py --activate`), **GLM-OCR**(`scripts/install_glmocr.py`, CUDA 전용), **PaddleOCR server**(`scripts/install_paddle_server_gpu.py --activate`)가 있으면, 로컬 우선 인식의 자동 선택에 CPU 엔진과 함께 들어갑니다. 설치하지 않은 엔진은 조용히 건너뛰고, CPU로 설치된 Surya처럼 CUDA가 아닌 설치는 "CUDA 설치가 아니어서 제외"로 기록합니다.
- 가로·세로쓰기 모두 대상입니다. 현재 자동 경로는 사용 가능한 GPU 엔진 하나를 골라 CPU 엔진과 비교합니다. 혼용은 Surya, 중국어는 GLM-OCR을 우선하며 PaddleOCR server는 한국어 모델이 없어 혼용에서 제외합니다.
- GPU 엔진은 상주 CUDA 세션으로 실행하고, PC 전체 GPU 대기열(한 번에 하나)을 그대로 씁니다. CPU 코어 몫을 차지하지 않으므로 CPU 엔진과 동시에 돕니다.
- 세션을 시작하지 못하면(GPU 없음, 대기열 사용 불가) 한 번 알리고 그 실행의 나머지 쪽에서는 그 엔진을 빼고 CPU 엔진만 씁니다. 끄려면 `YEONE_OCR_GPU_ENGINES=0`.
- 세로쓰기 쪽에도 GPU 엔진을 씁니다(2026-11부터 기본). 끄려면 `YEONE_OCR_GPU_VERTICAL=0`(측정 세트 `no-gpu-vertical`).
- 2026-11 한글·한자 세로쓰기 표본(6쪽, CER / 쪽당 시간): Tesseract 단독 34.44% / 3.2초, Surya 함께 **2.39%** / 11.7초(6쪽 모두 Surya), GLM-OCR 함께 15.19% / 14.2초, 한글 전용 CPU 모델 함께 52.72% / 26.3초(6쪽 모두 RapidOCR이 뽑혔지만 한자를 못 읽음: 자동 선택 점수가 한자 누락을 가려내지 못함), 모두 함께 2.39% / 27.7초.
- 그래서 한글 전용 CPU 모델은 혼용 문서에서 계속 뺍니다(시험 세트 `korean-models`, `YEONE_OCR_MIXED_KOREAN_MODELS=1`). `glmocr-vertical`은 Surya 대신 GLM-OCR을 쓰는 시험 세트입니다.
- 선택 점수식은 바꾸지 않았습니다. 정확도 이득은 같은 표본에서 측정해야 합니다.

## 시험 옵션(측정 전, 기본은 모두 꺼짐)

정확도·속도 이득을 아직 재지 않은 기능입니다. 같은 표본에서 켜고 끈 결과를 `yeone-ocr eval`과 별도 실행시간 측정으로 견준 뒤 기본값으로 올릴지 정합니다. 켠 옵션은 실행 기록에 남고 쪽 기록의 `local_first.options`에도 적힙니다.

| 옵션 | 하는 일 | 주의 |
|---|---|---|
| `--local-engine-plan fast` | 처음 5쪽은 모든 엔진으로 읽고, 그 뒤로는 표본에서 20% 이상 이긴 엔진 1~2개만 먼저 읽음. 고른 판독의 점수가 0.55 미만이면 그 쪽만 모든 엔진으로 다시 읽음 | 엔진 수가 줄면 엔진 간 갈림 표시(빨강)도 줄어듦 |
| `--local-vote` | 적격 엔진 3개 이상 가운데 과반이 같게 읽은 글자를 기준 판독 대신 채택. 비교·교정 창의 후보 채택과 같은 기록이라 되돌릴 수 있고 문서에서는 초록 | 사람이 고친 쪽에는 적용하지 않음. 기존 설계는 투표를 쓰지 않았음 |

| `--local-textlayer-witness` | PDF에 이미 있던 글자층이 다르게 읽은 글자를 파랑으로 표시(공백 무시, 절반 이상 같을 때만) | 글자층도 다른 OCR일 수 있어 빨강이 아닌 파랑 |
| `--local-skip-blank` | 어두운 화소(회색 160 미만)가 0.02% 미만인 쪽은 엔진을 실행하지 않고 빈 기록을 남김 | 아주 흐린 글씨 쪽은 빈 쪽으로 볼 수 있음 |
| `--local-enhance contrast` | 엔진 입력에 자동 대비(0.5% 자름)를 적용. 크기·좌표는 그대로이고 미리보기·AI 조각도 같은 화소 | 보정 없는 판독 결과는 재사용하지 않고 다시 읽음 |
| `--local-exclude-engines 엔진…` | 자동 선택에서 지정한 엔진을 뺌(예: `easyocr`). 뺀 엔진은 쪽 기록의 제외 목록에 남음 | 엔진 간 갈림 표시와 다수결의 증인이 줄어듦 |
| `--local-easyocr-threads N`, `--local-easyocr-batch N` | EasyOCR CPU 스레드 수(기본 2)와 한 번에 읽는 줄 수(기본 1) | 스레드는 속도만 바꿈. 묶음은 글자가 조금 달라질 수 있어 오류율을 함께 봐야 함 |
| `--local-ai-batch N` | 의심 구간 AI 검증 한 호출에 구간 N개(1~4) | 호출 수는 줄지만 정확도는 미측정 |

구현하지 않은 것: 사람 교정 사례(교정 기억)를 로컬 우선 경로에 넣는 일과 AI 검증 호출의 동시 실행. 교정 기억은 지금 AI 전체 판독의 1차 질문에만 쓰는 구조라 로컬 엔진에 넣을 자리가 없고, AI 호출 동시 실행은 실행당 호출 상한 계산을 바꾸므로 측정과 함께 다룰 일입니다.


## 두 단 조판 정리 (기본 켬)

가로쓰기 두 단 조판에서는 엔진이 왼쪽 단 한 줄, 오른쪽 단 한 줄을 번갈아 내놓아 글이 섞입니다. 로컬 우선 인식은 이런 쪽을 찾아 결과 문서에서 왼쪽 단 → 오른쪽 단 차례로 놓습니다.

- **두 단으로 보는 조건**: 가운데에 세로 빈 띠가 있고, 그 띠를 가로지르는 줄(가운데 제목·머리말)은 줄 수의 15%(최소 2줄)까지입니다. 양쪽 단 모두 단 폭을 거의 채우는 긴 줄(쪽 폭 25% 이상, 단 폭 70% 이상)이 5줄 이상이고, 그런 줄이 그 단 줄의 절반 이상이어야 합니다. 그래서 표의 칸, 사진 밑 설명, 그림 옆 이름표는 두 단으로 보지 않습니다.
- **가로지르는 줄**: 전체 폭 줄과 같이 구역 경계로 씁니다. 구역마다 왼쪽 단, 오른쪽 단 순서입니다.
- **조각난 줄**: EasyOCR처럼 한 줄을 쉼표마다 여러 조각으로 내놓는 엔진에 대비해, 같은 높이에서 쪽 폭 1.2% 안으로 붙은 조각은 한 줄로 이어 붙인 뒤 긴 줄인지 봅니다.
- **바꾸는 범위**: 결과 문서(HWPX·글자층 PDF)의 순서만 바꿉니다. 비교·교정 창의 판독 순서는 그대로입니다.
- **확인한 범위** (2026-11, PDF 글자층과 실제 판독 기록으로 확인):
  - 의방집해 2~12쪽은 모두 두 단으로 판별했습니다. 12쪽 글자층 모의 오류율은 94.1% → 2.3%입니다. 실제 판독 기록은 2쪽(RapidOCR) 144.7% → 23.0%, 3쪽(EasyOCR) 83.0% → 16.0%, 5쪽(PP-OCRv6) 116.4% → 15.2%입니다.
  - 대조도감 10쪽(표·사진 설명)과 개보본초 12쪽(한 단, 들여 쓴 주석)은 한 쪽도 두 단으로 보지 않았습니다.
- **끄기**: 설정의 "두 단 조판", 또는 명령줄 `--no-local-columns`.


## 줄 다시 확인 (기본 끔)

PP-OCRv6는 번체 가로쓰기에서 줄마다 잘라 낸 그림을 2~3번 다시 읽고, EasyOCR는 한문 가로쓰기 줄을 윈도 글꼴로 대조합니다. 2026-11 측정에서 이 단계는 결과 글자를 바꾸지 않고 시간만 썼습니다.

| 문서 | 오류율 (켬 → 끔) | 쪽당 시간 (켬 → 끔) |
|---|---|---|
| 의방집해 (번체, 10쪽) | 16.95% → 16.95% | 152.8초 → 96.9초 |
| 중의역대약론선 test1 (번체, 3쪽) | 8.13% → 8.13% | 81.3초 → 53.9초 |
| 중의역대약론선 test2 (번체, 3쪽) | 19.5% → 19.5% | 65.3초 → 45.7초 |
| 중의역대약론선 test1 (간체, 3쪽) | 9.06% → 9.06% | 34.1초 → 33.9초 |

- 그래서 기본으로 끕니다. 설정의 "줄 다시 확인" 또는 `--local-line-verification`으로 켭니다.
- 측정한 문서는 모두 PDF 안 글자층이 정답과 거의 같은 깨끗한 문서였습니다. 흐린 실제 스캔본에서는 차이가 날 수 있으니, 그런 책은 켠 결과와 견줘 보십시오.
- 켠 판독과 끈 판독은 따로 저장되어 서로 재사용하지 않습니다. 그래서 이전 판으로 읽은 책을 다시 실행하면 PP-OCRv6·EasyOCR가 한 번 더 읽습니다.


## EasyOCR: 가로쓰기에서는 기본 제외

EasyOCR은 예전 엔진 비교에서 번체의 **문장부호까지 포함한** 오류율이 가장 낮았지만(5.98%), 한자만 보면 다른 엔진보다 많이 틀렸고 가장 느린 엔진입니다. 2026-11 측정(가로쓰기, 줄 다시 확인 끔)에서 EasyOCR을 빼고 읽은 결과는 다음과 같습니다.

| 문서 | 오류율 (포함 → 제외) | 부호 제외 | 쪽당 시간 |
|---|---|---|---|
| 의방집해 (번체, 10쪽) | 16.95 → 17.97% | 9.28 → 6.05% | 96.9 → 70.3초 |
| 중의역대약론선 test1 (간체, 3쪽) | 9.06 → 7.87% | 6.36 → 4.09% | 33.9 → 24.4초 |
| 중의역대약론선 test1 (번체, 3쪽) | 8.13 → 7.89% | 2.46 → 2.20% | 53.9 → 35.1초 |
| 중의역대약론선 test2 (번체, 3쪽) | 19.5 → 19.5% | 6.73 → 6.73% | 45.7 → 31.1초 |

- 한자가 우선이므로 **가로쓰기에서는 EasyOCR을 기본으로 쓰지 않습니다**. EasyOCR이 뽑히지 않던 문서도 좋아진 것은, 쪽 점수의 "엔진 간 일치도"에서 EasyOCR이 빠지며 다른 엔진이 뽑혔기 때문입니다.
- 문장부호 대조가 중요한 책은 설정의 "EasyOCR"(가로쓰기에도 쓰기) 또는 `--local-easyocr`로 켭니다. 의방집해에서는 문장부호를 포함한 전체 오류율이 1%p 나빠졌습니다.
- 세로쓰기는 EasyOCR 전용 처리(열 재배열·보조 모델)가 있고 아직 측정하지 않아 지금처럼 씁니다. `--no-local-easyocr`로 뺄 수 있습니다.
- 측정 문서는 모두 PDF 글자층이 정답과 거의 같은 깨끗한 문서였습니다.
- EasyOCR 스레드·묶음 조정(`--local-easyocr-threads 6 --local-easyocr-batch 8`)은 결과가 같고 5% 빨라지는 데 그쳐 기본값을 바꾸지 않았습니다.

## Claude 구독 계정으로 의심 구간 검증 (2026-11)

연어 포토 에디터(docs/07-claude-subscription.md)와 같은 방식입니다. 이 PC에 설치된 공식 Claude Code에 사용자가 직접 로그인해 두면, 연어OCR은 `claude -p`를 실행만 합니다. 토큰을 읽거나 저장하지 않고, 사용량은 Pro/Max 요금제 한도(5시간·주간)에서 차감됩니다(API 요금 없음). **개인 사용 전용**입니다. 남에게 배포하는 프로그램이라면 API 키를 쓰세요.

준비(한 번):

```powershell
irm https://claude.ai/install.ps1 | iex     # 공식 설치본 claude.exe (npm의 claude.cmd는 명령줄 길이 제한으로 안 됨)
claude auth login                           # 브라우저에서 Claude 계정 로그인
claude auth status                          # "authMethod": "claude.ai", "subscriptionType": "max" 확인
```

- `--local-ai-auth subscription`: 로그인된 Claude Code로만 검증합니다. 로그인이 안 되어 있으면 이유를 알리고 검증을 보류하며, 유료 API 키로 넘어가지 않습니다.
- `--local-ai-auth auto`(기본): `--reader anthropic`인데 API 키가 없으면 로그인된 Claude Code를 씁니다. 다른 제공사는 그대로입니다.
- `--local-ai-auth api`: API 키만 씁니다.
- 모델은 `YEONE_OCR_CLAUDE_MODEL`(기본 `opus`), 생각 수준은 `YEONE_OCR_CLAUDE_EFFORT`(기본 `medium`), 호출 제한 시간은 `YEONE_OCR_CLAUDE_CLI_TIMEOUT`(기본 300초)로 바꿉니다.
- 이 앱만 따로 로그인하려면 `YEONE_OCR_CLAUDE_CONFIG_DIR`을 지정하고 같은 폴더로 `claude auth login`을 합니다.
- Claude Code에는 도구·MCP·사용자 설정·세션 기록을 모두 끄고 빈 작업 폴더에서 실행합니다. 환경의 `ANTHROPIC_API_KEY`는 자식 프로세스에 넘기지 않습니다(-p 모드에서는 키가 로그인보다 우선하기 때문).
- 로그인 만료·한도 도달처럼 다시 해도 안 되는 오류는 그 쪽의 남은 호출을 멈추고, 쪽은 "확인 필요"로 남깁니다.

시험 반영 `--local-ai-accept`: AI 제안은 원래 비교·교정 창에서 사람이 고르는 "제안"입니다. 이 옵션은 확신한 제안 가운데 안전 검사(엔진·이미지 근거)를 통과한 것만 본문에 바로 반영해(초록, 되돌릴 수 있음) 측정할 수 있게 합니다. 쪽 기록 `local_first.review.ai_accept`에 반영·보류 개수가 남습니다.

측정 세트 `ai-subscription` = `--local-ai-auth subscription --local-ai-accept --local-ai-max-calls 100 --local-ai-batch 4`.

Surya·GLM-OCR처럼 확신도가 없는 엔진이 기준이면 그 블록 전체가 검증 대상이 되므로, 블록 안에서 다른 엔진과 어긋난 곳을 따로 보내지 않습니다(같은 글을 두 번 보내지 않음). 처음 측정(2026-11)에서는 세로쓰기 Tesseract와의 불일치가 너무 많아 호출 상한을 넘어 AI 검증이 전부 보류됐습니다. 보류되면 이제 쪽마다 이유를 로그에 남깁니다.

첫 실측(2026-11, 한글·한자 세로쓰기 6쪽, Claude Max 구독, opus·medium): CER 2.39% → **2.29%**(부호 제외 2.06% → 1.95%), 쪽당 11.0초 → 35.2초, 5시간 사용률 7% → 7%(눈에 띄는 차감 없음). 측정 도구는 이제 세트 폴더마다 `errors.txt`(정답 → 판독 차이)와 AI 검증을 쓴 세트에서 `ai_proposals.txt`(제안별 반영·보류와 이유)를 남기고, 호출·반영·보류 수를 화면에 보입니다.

오류 분석(같은 6쪽, `errors.txt`·`ai_proposals.txt`):
- Surya 오류 41곳 가운데 5곳은 인쇄된 쪽 번호(`-185-`)를 본문으로 넣은 것이었습니다(약 25자). 이제 쪽의 첫 줄이나 마지막 줄이 위·아래 가장자리에 있는 맨 숫자(`-185-`, `185`, `(185)`)뿐이면 `쪽번호`로 표시해 본문에서 뺍니다(기본, `local_options.mark_folios`).
- AI 제안 14개 중 3개만 반영됐고 10개는 "AI 불확실"로 보류됐는데, 그 10개 중 9개가 정답과 같았습니다(나→냐 3곳, 앉더러서→엎디려서, 쓸→씀, 더→터, 저→거, 밀→밑, 떨→덜). 원인으로 보는 것: 쪽 크기의 글 덩어리 이미지를 모델이 줄여서 보므로(Claude는 긴 변 1568화소) 작은 한글 획이 흐려짐. `--local-ai-detail-tile 1024`(세트 `ai-subscription-tiles`)는 큰 이미지에 원래 해상도 조각(겹침 48화소, 세로쓰기는 오른쪽부터)을 함께 보내고, 조각으로 획이 분명하면 uncertain=false로 답하라고 안내합니다. 조각이 없을 때의 프롬프트·검증 지문은 그대로입니다.
- AI가 고치지 않은 것: 한자 오독(穿→旁, 潤→濶, 辯→癖, 鬥→門, 丈→文, 粘→帖, 擔→撬)과 이체자 모양(說→説, 眞→真, 絶→絕, 緖→緒).

## 한국 표준 한자 모양 (기본, 2026-11)

한글·한자 혼용 문서(`--local-profile mixed`)는 문서에 넣을 때 한자를 한국 표준 모양(KS X 1001)으로 맞춥니다: 説→說, 真→眞, 絕→絶, 緒→緖, 脱→脫, 様→樣 등 284쌍(`yeone_ocr/korean_forms.py`). KS X 1001에 **없는** 모양만 그 안의 짝으로 바꾸므로 한국 책에 쓰일 수 있는 글자(欠·缺, 余·餘)는 건드리지 않고, 한 글자를 한 글자로 바꿔 위치·등급·AI 검증 범위가 그대로입니다. 비교·교정 창의 엔진 판독문은 바꾸지 않습니다. 끄려면 `--no-local-korean-forms`(측정 세트 `no-korean-forms`). 간체·번체 문서에는 쓰지 않습니다(대만 표준은 真·絕·緒).

## AI 쪽 판독 (시험, 2026-11)

`--local-ai-page prefer|witness` (측정 세트 `ai-page`, `ai-page-witness`). Claude 구독(로그인된 Claude Code)이 쪽 전체를 사람이 교정하듯 읽습니다: 글자가 있는 영역을 줄·단 사이의 빈틈에서 잘라 원래 해상도의 띠 여러 장으로 만들고(세로쓰기는 오른쪽부터, 띠 최대 8장, 줄이지 않음), 축소한 쪽 전체 그림 1장과 함께 보내 처음부터 끝까지 받아 적게 합니다. 획만으로 정해지지 않는 글자는 문장의 뜻과 분야 어휘로 고르고 `uncertain`에 적게 합니다. 쪽 번호·머리말은 빼고, 옛 표기·글자 모양은 인쇄된 그대로 적게 합니다.

엔진 판독(Surya 등)과 공백을 빼고 맞춰 봅니다(`yeone_ocr/ai_page.py` `merge`):
- 같은 글자: 서로 다른 두 판독이 같게 읽음.
- 6자 이하로 다른 곳: prefer는 AI 글자를 문서에 넣고 초록, witness는 엔진 글자를 두고 파랑.
- 더 긴 차이(순서가 다르거나 한 줄을 빠뜨림): 엔진 글자를 두고 빨강.
- 두 판독의 유사도가 0.7 미만이면 AI 판독을 쓰지 않습니다.

줄바꿈·공백은 엔진 판독을 따르고, 비교·교정 창의 엔진 판독은 바꾸지 않습니다(문서 글만). 판독 결과는 작업 폴더 `ai-page/`에 쪽 이미지·모델·프롬프트 기준으로 저장해 같은 쪽을 다시 돌려도 다시 부르지 않습니다. 쪽 기록 `local_first.ai_page`에 일치 글자 수·채택·보류·유사도가 남습니다. 의심 구간 AI 검증(`--local-ai-review`)과는 따로 동작하며, 측정 세트는 의심 구간 검증을 끈 상태로 비교합니다.

첫 실측(2026-11, 세로쓰기 6쪽, 한국 표준 한자 모양 켬, CER / 부호 제외 / 쪽당 시간):
default 1.39% / 1.44% / 8.8초 · ai-subscription-tiles 1.01% / 1.05% / 37.4초(호출 17회, 반영 9 · 보류 4) · ai-page 1.21% / **0.79%** / 21.4초 · ai-page-witness 1.39% / 1.44% / 17.5초. AI 쪽 판독은 글자는 가장 정확했지만 부호에서 오류가 늘었습니다. 세트 `ai-page+review`는 둘을 함께 씁니다.

AI 쪽 판독 오류 분석(`ai-page/errors.txt`, 33곳): 문장 끝 부호를 `·`로 적은 것 15곳(세로쓰기 인쇄의 마침표 위치 때문, 엔진과 정답은 `.`), AI 자신이 불확실 목록에 올린 글자(各已, 夯, 綳濶, 自薦之癖, 直門, 撬傘)가 대부분의 글자 오류, 나머지는 글자 모양(卽·槪·旣 — 정답 파일은 판독 초안에서 온 即·概·既). 그래서 이제 부호만 다른 곳과 AI가 불확실하다고 한 낱말은 엔진 판독을 두고, 불확실 낱말은 두 판독이 같아도 빨강으로 칠합니다. 한국 표준 모양 표에 概→槪, 既→旣를 더했습니다. 측정 도구는 "글자 모양도 무시" 오류율(정답과 판독 모두 한국 표준 모양으로 맞춘 뒤 부호 제외)도 보이고, 측정 세트끼리 AI 쪽 판독 저장본(`_ai-page-cache`)을 함께 써서 같은 쪽을 다시 사지 않습니다.

재측정(2026-11, 같은 6쪽, CER / 부호 제외 / 글자 모양도 무시 / 쪽당 시간): default 1.53% / 1.59% / 1.23% / 8.8초 · ai-subscription-tiles 1.25% / 1.3% / 0.94% / 36.3초 · **ai-page+review 0.76% / 0.76% / 0.4% / 36.5초**(5시간 사용률 26% → 26%, AI 쪽 판독은 저장본 재사용). 남은 오류는 정답 파일과 글자 모양이 다른 곳(即·概·既·脱·様, 정답이 판독 초안에서 온 모양)과 한자 오독 몇 곳(穿→旁, 潤→濶, 辯→癖, 鬥→門, 丈→文, 擔→撬)이며, 한자 오독은 AI가 불확실하다고 한 낱말이라 빨강으로 표시됩니다.

측정 도구: 목록 파일은 `<결과 폴더>/보고/<문서>/<세트>-errors.txt`에도 복사합니다. 세트 폴더는 다음 실행 때 지워지는데, 그 안의 파일을 열거나 올린 프로그램(파일 열기 창이 그 폴더를 현재 폴더로 잡음)이 있으면 Windows가 지우지 못합니다. 그럴 때는 새 폴더(`세트-날짜시각`)에서 읽습니다.

## 기본 동작: 사용 가능한 구독이 있으면 AI 판독 자동 (2026-11)

> 현재 자동 선택 순서는 Antigravity(Google) → ChatGPT(Codex CLI) → Claude다. `--local-ai-plan`·설정 「AI 판독기」에서 계정을 고른다. 아래 개발 표본 수치는 Claude로 잰 것이며 다른 계정의 성능을 뜻하지 않는다. [구독 계정 안내](SUBSCRIPTION_PLANS.md)

`--local-ai-page auto`(기본): 이 PC에 사용 가능한 구독 로그인이 있으면 세트 `ai-page+review`와 같은 설정을 자동으로 씁니다 — 쪽 판독 prefer, 의심 구간 검증은 구독으로 4개씩 묶어 1024화소 조각과 함께, 확신하고 안전 검사를 통과한 제안 반영, 이번 실행 호출 상한 1000(`--local-ai-subscription-calls`, 구독은 호출당 요금이 없어 API 호출 상한 대신). 로그인되어 있지 않으면 예전 기본과 같습니다. 직접 준 옵션이 항상 우선합니다. 끄기: 설정 「AI 판독기」의 「구독 계정 판독」 체크 해제, 또는 `--local-ai-page off --local-ai-auth api`, 또는 환경 변수 `YEONE_OCR_CLAUDE_AUTH=api`. 측정 도구의 세트는 `--local-ai-page`를 직접 주지 않으면 끔으로 실행하고, 기본 동작은 세트 `auto`로 잽니다. 전체 구성은 `docs/연어OCR_구성_정리.md`.


## 사용량 보고의 범위

쪽별 `usage`와 보고서는 현재 저장된 응답의 누적 사용량이다. 의심 구간 검증에 더해 전체 쪽 AI 판독을 합산하며, 병합에서 쓰이지 않은 완료 응답도 센다. 저장본을 재사용하면 원래 응답을 한 번만 세고 쪽 AI 정보에 재사용 여부를 표시한다. 재사용을 새 유료 호출로 계산하지 않는다.

이번 실행의 새 호출 수나 청구 금액과는 다르다. 제공사가 반환하지 않은 토큰, 저장되지 않은 실패·재시도 응답, 이전 판 기록에서 빠진 쪽 AI 사용량은 복원하지 않는다. 시간 합계는 쪽별 경과시간 합이며 병렬 실행의 전체 실경과시간이 아니다.
