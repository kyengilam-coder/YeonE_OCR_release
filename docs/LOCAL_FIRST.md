# 로컬 우선 인식과 선택 구간 AI 검증

현재 개발 소스의 **일반 OCR·이미지 OCR·`run` 기본 경로는 `local-first`**다. 설치된 로컬 엔진으로 먼저 읽고, 불일치하거나 어려운 구간에만 선택한 Gemini·OpenAI·Claude API를 사용한다. 기존 설치 파일에는 이 소스 변경이 반영되지 않았을 수 있다. 전체 쪽을 AI로 읽는 이전 경로는 `--ocr-strategy ai-full`로 명시한다.

## 처리 순서

1. 원본·쪽 범위·읽기 방향을 확인한다. 이미지 폴더·붙여넣기 묶음은 작업 폴더 `local-input`에 원본 지문으로 이름을 정한 PDF 사본을 만든다. 원본 이미지를 변경하거나 외부로 보내는 단계가 아니다.
2. 설치·언어·메모리 조건에 맞는 엔진을 **PP-OCRv6 → RapidOCR/v5 → EasyOCR → Tesseract** 순서로 하나씩 실행한다. 중국어는 네 엔진, 한글·한자 혼용은 Tesseract가 대상이다. 지원 엔진이 없으면 설치 오류로 기록하며 전체 쪽 AI 판독으로 자동 전환하지 않는다.
3. [자동 선택 정책](AUTOMATIC_OCR.md)으로 한 쪽의 로컬 결과 하나를 선택한다. v6 하나만 설치되어 있어도 진행할 수 있다. 원시 결과·직접 교정·사람의 기준 선택을 보존하며, API 호출 전에 로컬 판독을 저장한다.
4. 선택 결과와 호환되는 최신 엔진 결과에서 어려운 구간을 찾는다. 엔진 간 명시적 불일치, 낮거나 없는 confidence, `�`·`□`·`〔판독불명〕` 등 알 수 없는 글자, 좌표 누락, 글자는 검출하지 못했지만 먹이 있는 지역을 대상으로 삼는다.
5. 대상 구간의 원본 크롭과 제한된 앞뒤 문맥만 API로 검증한다. 깨끗한 높은 confidence 단일 엔진 결과나 위험 신호가 없는 일치 결과는 **API 0회**다. 좌표를 안전하게 연결할 수 없으면 검수 대기로 남긴다. 불일치가 많거나 좌표가 없다는 이유로 전체 쪽 이미지·문장 전체 검증으로 확대하지 않는다.
6. AI 응답은 수정 **제안**으로 저장한다. 비교·교정 창에서 채택·기각하기 전에는 본문을 덮어쓰지 않는다. HWPX·DOCX·검색 PDF·검수 화면·보고는 저장된 판독으로 만들며, 이 경로는 전체 쪽 AI 1·2차 판독·별도 3차 판별·문서 문맥 모델을 추가로 호출하지 않는다.

AI 검증 완료나 높은 confidence는 사람의 원본 대조 완료를 뜻하지 않는다. 서로 다른 엔진의 confidence를 비교하거나 정확도로 표시하지 않는다.

## 어려운 구간의 기준

confidence 경계는 API로 보낼 구간을 정하는 초기 휴리스틱이며 실측 인식률이 아니다. 선택한 기준 엔진의 자체 척도에서만 판단한다.

| 기준 엔진 | 낮은 confidence |
|---|---:|
| Tesseract | 70 미만, 자체 0–100 척도 |
| RapidOCR/v5 | 0.85 미만, 자체 0–1 척도 |
| PP-OCRv6 | 0.85 미만, 자체 0–1 척도 |
| EasyOCR | 0.55 미만, 자체 0–1 척도 |

confidence가 없는 구간도 검증 대상으로 본다. 일부 자형 보완 결과는 원래 모델 점수를 보존하고 최종 confidence를 `null`로 두므로 이 경로에 포함될 수 있다. 단순 검은 선·그림도 먹 검출에 잡힐 수 있다. 이미지 근거가 불명확하면 AI의 불확실 제안과 사람의 검수 상태를 확인해야 한다.

## 호출 상한과 이어 읽기

`--local-ai-max-calls` 기본값은 **이번 명령 전체 20회**다. 쪽별 20회가 아니며, `--max-calls`가 양수이면 두 상한 중 작은 값을 함께 적용한다. 완료한 요청은 원본·쪽·선택 기준·모델·정책·크롭 지문으로 재사용한다. **호출 상한만 바꾸거나 다음 실행의 남은 호출 수가 달라져도 완료한 검증을 다시 구매하지 않는다.** 원본·판독·모델·실제 검증 정책이 바뀌면 재검증 대상이 될 수 있다.

API 키가 없어도 로컬 인식·출력은 진행한다. AI 대상이 남거나 호출 상한·검증 실패로 검증을 마치지 못하면 종료 코드 `4`로 알리고 저장된 결과와 검증 계획을 보존한다. 깨끗해서 대상이 없으면 키가 없어도 성공이다. `--no-local-ai-review`로 로컬 전용을 명시하면 API를 호출하지 않고 로컬 결과를 만들며, 검수할 곳이 있다는 기록을 보존한다.

| 종료 코드 | 뜻 |
|---|---|
| `0` | 선택한 로컬·AI 작업과 출력 완료. 사람 검수 완료를 의미하지 않음 |
| `3` | 일부 쪽의 로컬 인식 실패. 완료된 쪽과 원시 결과는 보존 |
| `4` | 로컬 결과는 있으나 요청한 선택 구간 AI 검증이 대기·미완료 |
| `2` / `130` | 입력·설정 오류 / 사용자 중지 |

출력 생성 자체가 실패하면 해당 출력 오류 코드가 우선한다. 비교 프로젝트는 작업 폴더 `comparison`, 검증 계획은 `local-first-review`, 상태 집계는 `state.json`의 `local_first_last_run`에 남는다. 원문·AI 응답·제안·사람 채택 이력을 구분해 저장한다.

## 명령줄 예

프로젝트 가상환경의 Python으로 실행한다. API 제공사·모델·키 설정은 기존 설정을 사용한다. 키를 명령줄 인수에 넣지 않는다.

```powershell
# 번체 가로쓰기: 로컬 인식 → 어려운 구간만 API → HWPX
.\.venv\Scripts\python.exe -m yeone_ocr run "책.pdf" --local-profile traditional --mode horizontal_zh --work "work\책"

# 로컬 전용. 지원되는 엔진을 설치한 뒤 사용
.\.venv\Scripts\python.exe -m yeone_ocr run "책.pdf" --no-local-ai-review --local-engine-root "C:\OCR엔진"

# 한글·한자 혼용 세로쓰기, 검색 PDF, 이번 실행 최대 5회
.\.venv\Scripts\python.exe -m yeone_ocr run "혼용문헌.pdf" --local-profile mixed --mode vertical --pdf-only --local-ai-max-calls 5

# 이전 전체 쪽 AI 판독 경로를 명시적으로 사용
.\.venv\Scripts\python.exe -m yeone_ocr run "책.pdf" --ocr-strategy ai-full
```

엔진 설치·언어 범위는 [로컬 엔진 안내](LOCAL_OCR.md), 제안·개인 자료 저장 정책은 [AI 검증 안내](AI_REVIEW.md)를 함께 따른다.

## 속도: 상주 작업자와 엔진 병렬 실행

- **상주 작업자**: 로컬 우선 인식은 PP-OCRv6·RapidOCR·EasyOCR 작업자를 실행 동안 띄워 두고, 한 작업자로 최대 16쪽을 읽은 뒤 새로 띄웁니다(기존 세션 규약 그대로). 쪽마다 모델을 다시 올리고 모델 파일 해시를 다시 확인하지 않습니다. 가로쓰기 쪽만 해당하며, 세로쓰기 쪽과 Tesseract는 지금처럼 쪽마다 작업자를 띄웁니다(그 결과에 필요한 후처리가 그 경로에 있음). 끄려면 환경 변수 `YEONE_OCR_RESIDENT_WORKERS=0`.
- **엔진 병렬**: 한 쪽의 엔진들을 동시에 실행합니다. 동시 개수는 코어 4개당 엔진 1개, 빈 메모리(이미 떠 있는 작업자 제외)가 가장 무거운 엔진들의 예산을 넘지 않을 만큼입니다. 결과는 늘 엔진 순서대로 기록하므로 프로젝트·비교·선택 결과는 차례로 실행할 때와 같습니다. `--local-engine-parallel N`(0=자동, 1=차례로) 또는 `YEONE_OCR_ENGINE_PARALLEL`로 정합니다.
- **반복 작업 제거**: 한 쪽 렌더 결과를 엔진·미리보기·AI 조각이 함께 쓰고, 원본 해시는 크기·시각·inode가 그대로이고 2초 넘게 바뀌지 않은 파일에만 재사용합니다. 글꼴 해시는 파일마다 한 번, 프로젝트 중간 저장은 저장 자체가 느려지면 30초 간격으로 줄입니다(쪽 끝 저장은 늘 합니다).
- 실제 속도는 측정하지 않았습니다. 같은 표본에서 `ab_ocr/benchmark.py`로 전후를 재야 합니다.

## 그래픽카드(CUDA) 엔진의 자동 선택 참여

- CUDA로 설치·활성화한 **Surya**(`scripts/install_surya_cuda.py --activate`), **GLM-OCR**(`scripts/install_glmocr.py`, CUDA 전용), **PaddleOCR server**(`scripts/install_paddle_server_gpu.py --activate`)가 있으면, 로컬 우선 인식의 자동 선택에 CPU 엔진과 함께 들어갑니다. 설치하지 않은 엔진은 조용히 건너뛰고, CPU로 설치된 Surya처럼 CUDA가 아닌 설치는 "CUDA 설치가 아니어서 제외"로 기록합니다.
- 가로쓰기 쪽만 해당합니다(세로쓰기는 아직 측정하지 않음). 한글·한자 혼용 문서는 지금까지 Tesseract만 읽었지만, Surya·GLM-OCR이 있으면 함께 읽고 점수로 고릅니다(PaddleOCR server는 한국어 모델이 없어 혼용에서 제외).
- GPU 엔진은 상주 CUDA 세션으로 실행하고, PC 전체 GPU 대기열(한 번에 하나)을 그대로 씁니다. CPU 코어 몫을 차지하지 않으므로 CPU 엔진과 동시에 돕니다.
- 세션을 시작하지 못하면(GPU 없음, 대기열 사용 불가) 한 번 알리고 그 실행의 나머지 쪽에서는 그 엔진을 빼고 CPU 엔진만 씁니다. 끄려면 `YEONE_OCR_GPU_ENGINES=0`.
- 세로쓰기 쪽에도 GPU 엔진을 씁니다(2026-11부터 기본). 끄려면 `YEONE_OCR_GPU_VERTICAL=0`(측정 세트 `no-gpu-vertical`).
- 2026-11 한글·한자 세로쓰기 표본(6쪽, CER / 쪽당 시간): Tesseract 단독 34.44% / 3.2초, Surya 함께 **2.39%** / 11.7초(6쪽 모두 Surya), GLM-OCR 함께 15.19% / 14.2초, 한글 전용 CPU 모델 함께 52.72% / 26.3초(6쪽 모두 RapidOCR이 뽑혔지만 한자를 못 읽음: 자동 선택 점수가 한자 누락을 가려내지 못함), 모두 함께 2.39% / 27.7초.
- 그래서 한글 전용 CPU 모델은 혼용 문서에서 계속 뺍니다(시험 세트 `korean-models`, `YEONE_OCR_MIXED_KOREAN_MODELS=1`). `glmocr-vertical`은 Surya 대신 GLM-OCR을 쓰는 시험 세트입니다.
- 선택 점수식은 바꾸지 않았습니다. 정확도 이득은 같은 표본에서 측정해야 합니다.

## 시험 옵션(측정 전, 기본은 모두 꺼짐)

정확도·속도 이득을 아직 재지 않은 기능입니다. 같은 표본에서 켜고 끈 결과를 `yeone-ocr eval`·`ab_ocr/benchmark.py`로 견준 뒤 기본값으로 올릴지 정합니다. 켠 옵션은 실행 기록에 남고 쪽 기록의 `local_first.options`에도 적힙니다.

| 옵션 | 하는 일 | 주의 |
|---|---|---|
| `--local-engine-plan fast` | 처음 5쪽은 모든 엔진으로 읽고, 그 뒤로는 표본에서 20% 이상 이긴 엔진 1~2개만 먼저 읽음. 고른 판독의 점수가 0.55 미만이면 그 쪽만 모든 엔진으로 다시 읽음 | 엔진 수가 줄면 엔진 간 갈림 표시(빨강)도 줄어듦 |
| `--local-vote` | 적격 엔진 3개 이상 가운데 과반이 같게 읽은 글자를 기준 판독 대신 채택. 비교·교정 창의 후보 채택과 같은 기록이라 되돌릴 수 있고 문서에서는 초록 | 사람이 고친 쪽에는 적용하지 않음. 기존 설계는 투표를 쓰지 않았음 |

| `--local-textlayer-witness` | PDF에 이미 있던 글자층이 다르게 읽은 글자를 파랑으로 표시(공백 무시, 절반 이상 같을 때만) | 글자층도 다른 OCR일 수 있어 빨강이 아닌 파랑 |
| `--local-skip-blank` | 어두운 화소(회색 160 미만)가 0.02% 미만인 쪽은 엔진을 실행하지 않고 빈 기록을 남김 | 아주 흐린 글씨 쪽은 빈 쪽으로 볼 수 있음 |
| `--local-enhance contrast` | 엔진 입력에 자동 대비(0.5% 자름)를 적용. 크기·좌표는 그대로이고 미리보기·AI 조각도 같은 화소 | 보정 없는 판독 결과는 재사용하지 않고 다시 읽음 |
| `--local-exclude-engines 엔진…` | 자동 선택에서 지정한 엔진을 뺌(예: `easyocr`). 뺀 엔진은 쪽 기록의 제외 목록에 남음 | 엔진 간 갈림 표시와 다수결의 증인이 줄어듦 |
| `--local-easyocr-threads N`, `--local-easyocr-batch N` | EasyOCR CPU 스레드 수(기본 2)와 한 번에 읽는 줄 수(기본 1) | 스레드는 속도만 바꿈. 묶음은 글자가 조금 달라질 수 있어 오류율을 함께 봐야 함 |
| `--local-ai-batch N` | 의심 구간 AI 검증 한 호출에 구간 N개(1~4) | 호출 수는 줄지만 정확도는 미측정 |

구현하지 않은 것: 사람 교정 사례(교정 기억)를 로컬 우선 경로에 넣는 일과 AI 검증 호출의 동시 실행. 교정 기억은 지금 AI 전체 판독의 1차 질문에만 쓰는 구조라 로컬 엔진에 넣을 자리가 없고, AI 호출 동시 실행은 실행당 호출 상한 계산을 바꾸므로 측정과 함께 다룰 일입니다.


## 두 단 조판 정리 (기본 켬)

가로쓰기 두 단 조판에서는 엔진이 왼쪽 단 한 줄, 오른쪽 단 한 줄을 번갈아 내놓아 글이 섞입니다. 로컬 우선 인식은 이런 쪽을 찾아 결과 문서에서 왼쪽 단 → 오른쪽 단 차례로 놓습니다.

- **두 단으로 보는 조건**: 가운데에 세로 빈 띠가 있고, 그 띠를 가로지르는 줄(가운데 제목·머리말)은 줄 수의 15%(최소 2줄)까지입니다. 양쪽 단 모두 단 폭을 거의 채우는 긴 줄(쪽 폭 25% 이상, 단 폭 70% 이상)이 5줄 이상이고, 그런 줄이 그 단 줄의 절반 이상이어야 합니다. 그래서 표의 칸, 사진 밑 설명, 그림 옆 이름표는 두 단으로 보지 않습니다.
- **가로지르는 줄**: 전체 폭 줄과 같이 구역 경계로 씁니다. 구역마다 왼쪽 단, 오른쪽 단 순서입니다.
- **조각난 줄**: EasyOCR처럼 한 줄을 쉼표마다 여러 조각으로 내놓는 엔진에 대비해, 같은 높이에서 쪽 폭 1.2% 안으로 붙은 조각은 한 줄로 이어 붙인 뒤 긴 줄인지 봅니다.
- **바꾸는 범위**: 결과 문서(HWPX·글자층 PDF)의 순서만 바꿉니다. 비교·교정 창의 판독 순서는 그대로입니다.
- **확인한 범위** (2026-11, PDF 글자층과 실제 판독 기록으로 확인):
  - 의방집해 2~12쪽은 모두 두 단으로 판별했습니다. 12쪽 글자층 모의 오류율은 94.1% → 2.3%입니다. 실제 판독 기록은 2쪽(RapidOCR) 144.7% → 23.0%, 3쪽(EasyOCR) 83.0% → 16.0%, 5쪽(PP-OCRv6) 116.4% → 15.2%입니다.
  - 대조도감 10쪽(표·사진 설명)과 개보본초 12쪽(한 단, 들여 쓴 주석)은 한 쪽도 두 단으로 보지 않았습니다.
- **끄기**: 설정의 "두 단 조판", 또는 명령줄 `--no-local-columns`.


## 줄 다시 확인 (기본 끔)

PP-OCRv6는 번체 가로쓰기에서 줄마다 잘라 낸 그림을 2~3번 다시 읽고, EasyOCR는 한문 가로쓰기 줄을 윈도 글꼴로 대조합니다. 2026-11 측정에서 이 단계는 결과 글자를 바꾸지 않고 시간만 썼습니다.

| 문서 | 오류율 (켬 → 끔) | 쪽당 시간 (켬 → 끔) |
|---|---|---|
| 의방집해 (번체, 10쪽) | 16.95% → 16.95% | 152.8초 → 96.9초 |
| 중의역대약론선 test1 (번체, 3쪽) | 8.13% → 8.13% | 81.3초 → 53.9초 |
| 중의역대약론선 test2 (번체, 3쪽) | 19.5% → 19.5% | 65.3초 → 45.7초 |
| 중의역대약론선 test1 (간체, 3쪽) | 9.06% → 9.06% | 34.1초 → 33.9초 |

- 그래서 기본으로 끕니다. 설정의 "줄 다시 확인" 또는 `--local-line-verification`으로 켭니다.
- 측정한 문서는 모두 PDF 안 글자층이 정답과 거의 같은 깨끗한 문서였습니다. 흐린 실제 스캔본에서는 차이가 날 수 있으니, 그런 책은 켠 결과와 견줘 보십시오.
- 켠 판독과 끈 판독은 따로 저장되어 서로 재사용하지 않습니다. 그래서 이전 판으로 읽은 책을 다시 실행하면 PP-OCRv6·EasyOCR가 한 번 더 읽습니다.


## EasyOCR: 가로쓰기에서는 기본 제외

EasyOCR은 예전 엔진 비교에서 번체의 **문장부호까지 포함한** 오류율이 가장 낮았지만(5.98%), 한자만 보면 다른 엔진보다 많이 틀렸고 가장 느린 엔진입니다. 2026-11 측정(가로쓰기, 줄 다시 확인 끔)에서 EasyOCR을 빼고 읽은 결과는 다음과 같습니다.

| 문서 | 오류율 (포함 → 제외) | 부호 제외 | 쪽당 시간 |
|---|---|---|---|
| 의방집해 (번체, 10쪽) | 16.95 → 17.97% | 9.28 → 6.05% | 96.9 → 70.3초 |
| 중의역대약론선 test1 (간체, 3쪽) | 9.06 → 7.87% | 6.36 → 4.09% | 33.9 → 24.4초 |
| 중의역대약론선 test1 (번체, 3쪽) | 8.13 → 7.89% | 2.46 → 2.20% | 53.9 → 35.1초 |
| 중의역대약론선 test2 (번체, 3쪽) | 19.5 → 19.5% | 6.73 → 6.73% | 45.7 → 31.1초 |

- 한자가 우선이므로 **가로쓰기에서는 EasyOCR을 기본으로 쓰지 않습니다**. EasyOCR이 뽑히지 않던 문서도 좋아진 것은, 쪽 점수의 "엔진 간 일치도"에서 EasyOCR이 빠지며 다른 엔진이 뽑혔기 때문입니다.
- 문장부호 대조가 중요한 책은 설정의 "EasyOCR"(가로쓰기에도 쓰기) 또는 `--local-easyocr`로 켭니다. 의방집해에서는 문장부호를 포함한 전체 오류율이 1%p 나빠졌습니다.
- 세로쓰기는 EasyOCR 전용 처리(열 재배열·보조 모델)가 있고 아직 측정하지 않아 지금처럼 씁니다. `--no-local-easyocr`로 뺄 수 있습니다.
- 측정 문서는 모두 PDF 글자층이 정답과 거의 같은 깨끗한 문서였습니다.
- EasyOCR 스레드·묶음 조정(`--local-easyocr-threads 6 --local-easyocr-batch 8`)은 결과가 같고 5% 빨라지는 데 그쳐 기본값을 바꾸지 않았습니다.

## Claude 구독 계정으로 의심 구간 검증 (2026-11)

연어 포토 에디터(docs/07-claude-subscription.md)와 같은 방식입니다. 이 PC에 설치된 공식 Claude Code에 사용자가 직접 로그인해 두면, 연어OCR은 `claude -p`를 실행만 합니다. 토큰을 읽거나 저장하지 않고, 사용량은 Pro/Max 요금제 한도(5시간·주간)에서 차감됩니다(API 요금 없음). **개인 사용 전용**입니다. 남에게 배포하는 프로그램이라면 API 키를 쓰세요.

준비(한 번):

```powershell
irm https://claude.ai/install.ps1 | iex     # 공식 설치본 claude.exe (npm의 claude.cmd는 명령줄 길이 제한으로 안 됨)
claude auth login                           # 브라우저에서 Claude 계정 로그인
claude auth status                          # "authMethod": "claude.ai", "subscriptionType": "max" 확인
```

- `--local-ai-auth subscription`: 로그인된 Claude Code로만 검증합니다. 로그인이 안 되어 있으면 이유를 알리고 검증을 보류하며, 유료 API 키로 넘어가지 않습니다.
- `--local-ai-auth auto`(기본): `--reader anthropic`인데 API 키가 없으면 로그인된 Claude Code를 씁니다. 다른 제공사는 그대로입니다.
- `--local-ai-auth api`: API 키만 씁니다.
- 모델은 `YEONE_OCR_CLAUDE_MODEL`(기본 `opus`), 생각 수준은 `YEONE_OCR_CLAUDE_EFFORT`(기본 `medium`), 호출 제한 시간은 `YEONE_OCR_CLAUDE_CLI_TIMEOUT`(기본 300초)로 바꿉니다.
- 이 앱만 따로 로그인하려면 `YEONE_OCR_CLAUDE_CONFIG_DIR`을 지정하고 같은 폴더로 `claude auth login`을 합니다.
- Claude Code에는 도구·MCP·사용자 설정·세션 기록을 모두 끄고 빈 작업 폴더에서 실행합니다. 환경의 `ANTHROPIC_API_KEY`는 자식 프로세스에 넘기지 않습니다(-p 모드에서는 키가 로그인보다 우선하기 때문).
- 로그인 만료·한도 도달처럼 다시 해도 안 되는 오류는 그 쪽의 남은 호출을 멈추고, 쪽은 "확인 필요"로 남깁니다.

시험 반영 `--local-ai-accept`: AI 제안은 원래 비교·교정 창에서 사람이 고르는 "제안"입니다. 이 옵션은 확신한 제안 가운데 안전 검사(엔진·이미지 근거)를 통과한 것만 본문에 바로 반영해(초록, 되돌릴 수 있음) 측정할 수 있게 합니다. 쪽 기록 `local_first.review.ai_accept`에 반영·보류 개수가 남습니다.

측정 세트 `ai-subscription` = `--local-ai-auth subscription --local-ai-accept --local-ai-max-calls 100 --local-ai-batch 4`.

Surya·GLM-OCR처럼 확신도가 없는 엔진이 기준이면 그 블록 전체가 검증 대상이 되므로, 블록 안에서 다른 엔진과 어긋난 곳을 따로 보내지 않습니다(같은 글을 두 번 보내지 않음). 처음 측정(2026-11)에서는 세로쓰기 Tesseract와의 불일치가 너무 많아 호출 상한을 넘어 AI 검증이 전부 보류됐습니다. 보류되면 이제 쪽마다 이유를 로그에 남깁니다.
